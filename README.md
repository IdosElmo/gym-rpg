# Gym RPG 💪

אפליקציית אימוני היפרטרופיה (תוכנית של 1–7 ימים · ברירת מחדל A/B/C) בעברית,
RTL, **100% אופליין** —
עם שכבת משחק RPG מלאה שמתקדמת **רק** מאימונים אמיתיים.

> **סטטוס: הושלם.** כל מה שבמפרט קיים: מנוע XP ורמות לכל חלק גוף, דמות SVG
> שגדלה איתן, רצף שבועי, קרב אידל דטרמיניסטי, ארבעה עולמות עם **בוסי עולם
> ושערי אימון**, **חנות ציוד** במטבעות שמצטיירת על הדמות, **מגוון דמויות
> קוסמטי** (שני גופי בסיס חינם + סקינים בתשלום), **גביעים**, ומצב
> אלוף אינסופי אחרי זאוס — ומעליהם **תוכנית אימונים ניתנת לעריכה** ו**סנכרון
> ענן אופציונלי** עם חשבון Google.
>
> הסנכרון **כבוי כברירת מחדל**: כל עוד `src/sync/config.ts` ריק (וב‑`file://`
> תמיד) אין לקוח, אין מאזין ואין כרטיס חשבון — האפליקציה היא בדיוק האפליקציה
> האופליינית. ההפעלה היא ארבעה שלבים ידניים, ראו **"סנכרון בענן וחשבון
> Google"** למטה.

## מה יש כאן

הניווט הוא **שתי שכבות**: שורה ראשית של בדיוק **שלושה** טאבים קבועים (מרכזים),
ומתחתיה שורת תת‑טאבים של המרכז הפתוח. השורה הראשית לא נגללת ולא משנה סדר
לעולם; רק שורת תת‑הטאבים יכולה להיגלל, ורק כשתוכנית מגדירה יותר מארבעה ימי
אימון בשבוע. ראו **"ניווט דו‑שכבתי"** למטה.

| מרכז | תת‑טאבים | מה יש בו |
|---|---|---|
| 🏋️ **אימון** | טאב לכל **מופע אימון** בשבוע (`scheduleTabs`) | תיעוד סטים, ביצוע קודם, טיימר מנוחה צף עם צליל, `+XP חזה!` צף, מונה ⚡. כפתור ⚙️ בכותרת פותח את עורך התוכנית |
| 🎮 **קרב** | **קרב** · **דמות** | *קרב*: זירה, גלים, מיני‑בוסים, **קרבות בוסי עולם**, מד מהלך על, מטבעות, כרטיס שער הבוס. *דמות*: SVG שכבתי שגדל לפי הרמות, רמה ראשית, 6 פסי חלקי גוף, רצף, **רצועת דמויות** (החלפה חינם בין שני גופי בסיס + סקינים קוסמטיים), **חנות ציוד**, **מדף גביעים** |
| ⚙️ **הגדרות** | **הגדרות** · **היסטוריה** | *הגדרות*: **כרטיס החשבון** (התחברות, מצב סנכרון, ממתינים), כרטיס התוכנית + ⚙️, ייצוא/ייבוא/מחיקת JSON, שורת מידע על האפליקציה. *היסטוריה*: **יומן הרפתקה** מיומן האירועים + היסטוריית האימונים המתועדים |
| ⚙️ **תוכנית** (`PL`) | — | ניהול ימי התוכנית (הוספה, שינוי שם, הסרה, סידור, שיבוץ לימי השבוע), ובתוך כל יום: סטים, חזרות, מנוחה, סדר, הסרה ותרגילים משלכם. גם **תוכניות מוכנות**. אינו טאב — שייך למרכז 🏋️ ונכנסים אליו מ‑⚙️ בכותרת האימון או מכרטיס התוכנית בהגדרות |

**הכלל הזהב:** אי אפשר להתקדם במשחק בלי אימון אמיתי. אנרגיה נצברת רק מסטים
מסומנים, ורמות חלקי גוף — שהן היחידות שפותחות בוסים — נצברות רק מ‑XP אמיתי.

## הרצה, בנייה ופריסה

דרישות: Node 22, npm 10.

```bash
npm install        # התקנת תלויות
npm run dev        # שרת פיתוח (Vite) — http://localhost:5173
npm run build      # בדיקת טיפוסים + בנייה ל-dist/index.html (קובץ יחיד)

npm test           # Vitest
npm run typecheck  # tsc --noEmit
npm run verify     # מוודא ש-dist/index.html ללא הפניות חיצוניות
```

### קובץ יחיד (file://)

`vite-plugin-singlefile` מטמיע את כל ה‑JS וה‑CSS לתוך `dist/index.html`.
אפשר להעתיק את הקובץ הזה לטלפון/מחשב ולפתוח אותו ישירות — הכול עובד, כולל
הטיימר, הצליל וההיסטוריה. אין שום בקשת רשת, פונט חיצוני או CDN בזמן ריצה.

**`base: './'`** — מכיוון שהכול מוטמע, לא נשארות כתובות נכסים; ההפניות היחסיות
היחידות הן קבצי ה‑PWA (`manifest.webmanifest`, `sw.js`, `icon.svg`) שיושבים ליד
`index.html`. `base` יחסי עובד גם ב‑GitHub Project Pages (תחת `/gym-rpg/`) וגם
ב‑`file://`; `'/gym-rpg/'` היה שובר את `file://` ו‑`'/'` היה שובר את Pages.

### פריסה ל‑GitHub Pages

`.github/workflows/deploy.yml` רץ על כל push ל‑`main`:
typecheck → tests → build → verify → `configure-pages` → `upload-pages-artifact`
→ `deploy-pages`.

בהגדרות המאגר: **Settings → Pages → Source: GitHub Actions**.

### PWA

* `public/manifest.webmanifest` — התקנה למסך הבית (standalone, RTL, עברית).
* `public/sw.js` — Service Worker שמקדים‑מטמין (precache) את הקובץ הבנוי,
  cache‑first עם רענון ברקע ו‑fallback ל‑`index.html` בניווט.
* `public/icon.svg` — אייקון SVG (משקולת + דמות) על רקע `#121824`.
* רישום ה‑SW מוגן: הוא נרשם **רק** ב‑`http`/`https`, כך שגרסת הקובץ היחיד
  ב‑`file://` ממשיכה לעבוד.

## ניווט דו‑שכבתי

עד לגרסה הזו הייתה **שורה אחת שטוחה**: כל ימי האימון של השבוע ועוד דמות, קרב
והיסטוריה — שבעה טאבים לתוכנית A/B, וגלילה אופקית. שבעה דברים שנראים אותו דבר
בשורה אחת הם לא סרגל ניווט אלא רשימה: שום דבר לא אומר ש"רביעי" ו"היסטוריה" הם
**סוגים** שונים של יעד. לכן הסרגל התפצל לשתיים.

**שורה 1 — המרכזים (hubs).** בדיוק שלושה טאבים, רוחב שווה, ≥44px, בלי גלילה
ובלי סדר משתנה: 🏋️ אימון · 🎮 קרב · ⚙️ הגדרות. הפעיל צבוע במילוי `--accent`
המלא, המצב החזק ביותר באפליקציה, כי "באיזה חלק של האפליקציה אני" היא השאלה
שהסרגל חייב לענות עליה מיד.

**שורה 2 — תת‑הטאבים של המרכז הפתוח**, במשקל ויזואלי קל יותר בכוונה: גלולות
(`border-radius:99px`), `--card-2` במקום `--card`, ומצב פעיל **מתואר בקו** ולא
במילוי. אותם tokens, אותה שפה, דרגה אחת שקטה יותר — כדי שהעין תקרא "מרכז, ואז
בחירה בתוכו" ולא שתי שורות שמתחרות זו בזו.

| מרכז | תת‑טאבים | view ids |
|---|---|---|
| 🏋️ אימון | `scheduleTabs(program)` — מופע לכל אימון בשבוע | `A`, `d_alef`, `d_alef@3`… ובנוסף `PL` (שייך למרכז, בלי טאב) |
| 🎮 קרב | קרב · דמות | `BT`, `CH` |
| ⚙️ הגדרות | הגדרות · היסטוריה | `ST`, `H` |

### המרכז נגזר מה‑view — אין שדה חדש ב‑state

אין `hub` ב‑`UiState`. `hubOf(view)` ב‑`src/ui/nav.ts` היא פונקציה **טוטלית**
מעל כל view id שהאפליקציה שמרה אי פעם: `BT`/`CH` → קרב, `ST`/`H` → הגדרות, וכל
דבר אחר (כל מפתח יום, כולל מפתח שמכשיר אחר המציא, וגם `PL`) → אימון. זה מה
שהופך את השינוי לארגון מחדש של ה‑UI ולא למיגרציה: התקנה שנשארה על `'H'`, על
`'A'`, על `'d_alef@3'` או על `'CH'` נפתחת בדיוק על המסך ששמה — ועכשיו גם על
המרכז שהמסך הזה חי בו.

**`ST` הוא ה‑view id היחיד שנוסף** (הגדרות), כדי שאפשר יהיה להבחין בין שני
תת‑הטאבים של מרכז ההגדרות. הוא נכנס ל‑`RESERVED_VIEW_KEYS`, ולכן `normalizeUi`
מקבל אותו כמו את שאר המסכים השמורים, ו‑`'H'` — מה שכל גרסה קודמת שמרה — נשאר
תקף לחלוטין ומצביע על אותו מסך היסטוריה, בתוך מרכז ההגדרות.

### זיכרון תת‑טאב לכל מרכז

`ui/app.ts` מחזיק **בזיכרון** את תת‑הטאב האחרון של כל מרכז, כך שמעבר למרכז אחר
וחזרה נוחת על מה שהיה פתוח שם ולא על ברירת המחדל. ברירות המחדל, כשעוד לא היה
כלום: אימון → הטאב של היום (`defaultTabView`), קרב → `BT` (הזירה), הגדרות →
`ST`. עורך התוכנית (`PL`) **לא** נזכר: הוא מסך שנכנסים אליו מכפתור ויוצאים
ממנו ב‑←, ולכן חזרה למרכז אימון מחזירה לאימון שהיה פתוח ולא לתוך העורך.

מה ש**כן** נשמר לדיסק הוא `ui.view` כרגיל — כלומר המרכז שהייתם בו כשסגרתם את
האפליקציה, שהוא החלק שבאמת צריך לשרוד רענון.

### הקרב עוצר בכל יציאה מהזירה

`render()` קורא ל‑`stopBattle()` לפני כל מסך, ולכן הלולאה נעצרת גם במעבר
לתת‑הטאב **דמות** שלצידה וגם במעבר למרכז אחר לגמרי — שתי הדרכים החדשות לצאת
מהזירה. `visibilitychange` ממשיך לשמור על אותה הבטחה כשהטאב של הדפדפן מוסתר.

### מפתחות אחסון

| מפתח | תוכן |
|---|---|
| `gymrpg_state_v1` | תמונת מצב נוכחית (`AppState`) |
| `gymrpg_events_v1` | יומן אירועים append‑only |
| `gymrpg_device_v1` | מזהה **התקנה** (uuid) — מוטבע על כל אירוע שהמכשיר כותב |
| `gymrpg_sync_v1` | פנקס מנוע הסנכרון: `{v, deviceId, cursor, outbox: [id…], userId, lastSyncAt}`. **לא** נכנס לייצוא ו**שורד** מחיקה |
| `sb-<ref>-auth-token` | הסשן של Supabase (נכתב על ידי supabase-js). קיים רק אחרי התחברות |
| `hyp3_data_v1` | הנתונים הישנים — נקראים פעם אחת לייבוא, **לא נמחקים** |
| `hyp3_ui_v1` | מצב UI ישן (טאב נבחר, כרטיסים פתוחים) |

```ts
    },
    characters: {                                  // מגוון הדמויות (קוסמטי בלבד)
      owned:    ["robot", …],                      // סקינים שנקנו (גופי הבסיס תמיד פתוחים)
      selected: "hero_m"                           // הדמות שמשחקים בה כרגע
    }
  },
  plan: null | {                    // PlanDoc v2 — ראו "תוכנית ניתנת לעריכה" למטה
    version: 2, rev,
    days: [                         // מערך מסודר, 1–7 ימים — הסדר הוא סדר הטאבים
      { key: "A",                   // "A"/"B"/"C" ליום שהוסב מ‑v1, "d_…" ליום חדש
        label: "אימון A",           // שם עברי חופשי ("חלק א׳")
        weekdays: [0, 1],           // 0=ראשון … 6=שבת (רשות)
        exercises: [{id, sets, reps, rest}, …] },
      …
    ],
    weeklyTarget: 3,                // ימי אימון שונים בשבוע ל"שבוע מושלם" (1–7)
    customExercises: [{id: "cx_…", he, en, bodyPart, split?, unit, equip, muscle}]
  },
  meta: { legacyImported, legacyImportedAt?, createdAt, updatedAt }
}
```

`game` הוא **מטמון**: אפשר לבנות אותו מחדש במלואו מיומן האירועים
(`rebuildGame`), ולכן בלוב לא מוכר פשוט נבנה מחדש במקום להישבר. זהו גם **נתיב
המיגרציה הרשמי** של הבלוב הזה: `normalizeGame` דוחה גרסה ישנה (v1/v2), ו‑
`ensureGameState` בונה אותה מחדש מהיומן — ללא אובדן, כי כל עובדה היא אירוע.

משקלים וחזרות נשמרים כמחרוזות, בדיוק כמו במקור. חורים במערך הסטים נשמרים
כ‑`null` כדי לשמר את המבנה הישן במדויק.

### יומן אירועים (append‑only)

כל פעולה משמעותית נרשמת כאירוע
`{ id: uuid, ts: epochMs, type, payload, device? }` ונשמרת לצד תמונת המצב. זה מה
שמאפשר את הסנכרון בין מכשירים בלי לכתוב מחדש שורה אחת של UI: **סנכרון = איחוד
קבוצות האירועים + replay**.

| סוג | נרשם מתי |
|---|---|
| `set_logged` | הוקלד משקל/חזרות |
| `set_completed` / `set_uncompleted` | סומן/בוטל סימון של סט |
| `workout_finished` | כל הסטים של כל התרגילים ביום סומנו (פעם אחת ליום) |
| `legacy_import` | סיכום ייבוא `hyp3_data_v1` |
| `session_imported` | אימון היסטורי שיובא — כולל כל הסטים, עם `ts` של תאריך האימון |
| `data_imported` / `data_cleared` | ייבוא קובץ JSON / מחיקת הכול |
| `xp_gained` | כל הענקת XP — כולל הפיצול לחלקי גוף, `volume`, `factor`, `pr`, `retro` |
| `energy_gained` | אנרגיית קרב (10 לסט, 50 לסיום אימון) — נושא `key` למניעת תשלום כפול |
| `pr_achieved` | שיא אישי חדש בתרגיל |
| `level_up` / `streak_changed` | אינפורמטיביים (הרמה והדרגה **נגזרות**, ראו למטה) |
| `wave_cleared` | גל שנוצח — `{world, wave, miniBoss, enemyId, coins, energySpent, seed, durationMs}` |
| `boss_defeated` | בוס עולם הופל — `{world, wave, bossId, coins, energySpent, seed, durationMs, nextWorld, nextWave, endgame}` |
| `coins_spent` | רכישה בחנות — `{itemId, slot, cost}` (מוריד מטבעות ומוסיף ל‑`owned`) |
| `item_equipped` | הצטיידות/הסרה — `{slot, itemId \| null}` |
| `character_purchased` | נקנתה דמות קוסמטית — `{characterId, cost}` (מוריד מטבעות ומוסיף ל‑`characters.owned`; אידמפוטנטי לפי המזהה) |
| `character_selected` | הוחלפה הדמות — `{characterId}`. LWW לפי הסדר `(ts, id)`; מזהה לא מוכר או שלא בבעלות **מתעלמים** ממנו |
| `plan_updated` | תוכנית נשמרה — `{plan: PlanDoc \| null, revision, date}`. המסמך **כולו** במטען. מנורמל בכל קיפול, כך שמטען v1 של לקוח ישן מוסב ל‑v2 בקריאה. גם **יעד הרצף השבועי** נגזר ממנו |
| `data_merged` | סמן מיזוג — `{source: "json_import", added}`. נכתב **רק** בייבוא JSON מצטבר (כשמחוברים). אינו משנה מצב; קיים כדי שיומן ההרפתקה יסביר קפיצה ב‑XP. משיכה מהענן **אינה** כותבת אותו בכוונה — סמן לכל משיכה היה מתפנג‑פונג בין המכשירים לנצח |

**מטען סמכותי (authoritative payload):** `boss_defeated` נושא את `nextWorld`/
`nextWave` ולא רק את מזהה הבוס. כך ה‑reducer לא צריך *לגזור* מחדש את חוק
הפתיחה, ויומן ישן ימשיך להשתחזר זהה גם אם החוק ישתנה בעתיד.

**גרעיניות אירועי הקרב:** מכה בודדת **אינה** אירוע. הקרב דטרמיניסטי לפי הזרע,
ולכן די באירוע אחד לכל גל שנוצח — הוא נושא את הזרע, את המטבעות ואת האנרגיה
שנגבתה, וזה כל מה שצריך כדי לשחזר את ההתקדמות ב‑`rebuildFromEvents`.

`rebuildFromEvents(events)` בונה מחדש את המצב מהיומן בלבד (דטרמיניסטי, ממוין
לפי `(ts, id)`), כולל `state.game` דרך `rebuildGame`. האפליקציה החיה וה‑replay
מריצים **בדיוק את אותו reducer על אותם אירועים** — יש בדיקות שמוכיחות שהתוצאה
זהה.

**בטיחות מיזוג (merge-safety).** הסדר נקבע לפי `(ts, id)` ולכן הוא תכונה של
*קבוצת* האירועים ולא של סדר ההגעה: שני מכשירים שמחזיקים את אותם אירועים יקפלו
אותם לאותו מצב בדיוק. בנוסף, ה‑reducer **אידמפוטנטי לפי מפתח סמנטי** — אותה
הענקה משני מכשירים (uuid שונה, אותה משמעות) משלמת פעם אחת בלבד: `granted`
לסטים, `bonusDays` לבונוס היומי, `prKeys` לשיאים ו‑`energyGranted` לאנרגיה. כל
מכשיר גם מוטבע ב‑`device` ומחתים חותמות זמן **עולות ממש**, כך שאפילו שעון
שקופץ אחורה לא הופך את סדר האירועים של אותו מכשיר. `tests/merge.test.ts` מוכיח
את ההתכנסות, ו‑`tests/e2e.sync.test.ts` מריץ את כולה מקצה לקצה על שני מכשירים
אמיתיים מול backend בזיכרון.

**מה *לא* מתקפל מהיומן.** שלושה שדות שייכים ל**התקנה** ולא לחשבון, ולכן
`storage/merge.ts` מעביר אותם מהמצב החי אל התוצאה במקום לשחזר אותם: `ui`
(באיזה טאב אתם), `meta.createdAt` (מתי ההתקנה הזאת נוצרה) ו‑`meta.legacyImported`
(האם המכשיר הזה כבר סרק את `hyp3_data_v1`). האחרון הוא **נועל**: replay של יומן
שנמחק אינו יכול לדעת עליו, ובלעדיו מחיקה + משיכה + רענון היו מייבאים מחדש את
הנתונים הישנים — ומחזירים לחשבון בדיוק את מה שנמחק.

### מיגרציה מהאפליקציה הישנה

בטעינה הראשונה, אם קיים `hyp3_data_v1`, הוא מיובא **ללא אובדן**: כל תאריך, אות
יום, מזהה תרגיל, סט (כולל חורים), משקל, חזרות ודגל `done`. במקביל נוצר אירוע
`session_imported` לכל אימון עם כל נתוני הסטים ו‑`ts` של תאריך האימון — כך
ש‑Phase 1 יוכל להעניק XP רטרואקטיבי פשוט על ידי replay של היומן, בסדר כרונולוגי.
המפתחות הישנים נשמרים כרשת ביטחון.

### ייצוא / ייבוא JSON

הייצוא כותב:

```jsonc
{
  "format": "gym-rpg-export",
  "schemaVersion": 1,
  "exportedAt": 1700000000000,
  "state":  { /* AppState מלא, כולל game */ },
  "events": [ /* יומן האירועים */ ],
  "sessions": { /* מראה לתאימות לאחור עם האפליקציה הישנה */ }
}
```

הייבוא מקבל **את שני הפורמטים**: את הבלוב החדש, וגם קובץ ישן בצורת
`{ "sessions": { ... } }`.

### חלוקת קבוצות שריר (`bodyPart`)

לכל תרגיל נוסף שדה `bodyPart` (`chest`/`back`/`legs`/`shoulders`/`arms`/`core`),
ובחלק מהתרגילים גם `split` — פיצול XP בין שתי קבוצות (למשל מקבילים: חזה 70%,
ידיים 30%). `bodyPartWeights(exercise)` מחזיר משקלים מנורמלים שסכומם 1.

## שכבת המשחק (Phase 1)

### חוקי XP (`core/xp.ts` — פונקציות טהורות + בדיקות)

| כלל | נוסחה |
|---|---|
| סיום סט | `10 × volumeFactor` |
| `volumeFactor` | `clamp((משקל×חזרות) / השיא הקודם, 0.5, 1.5)` — 1 כשאין עם מה להשוות |
| נפח לתרגילי משקל גוף/שניות | החזרות או השניות עצמן |
| שיא אישי חדש | `×2` XP + אירוע `pr_achieved` + toast חגיגי |
| סיום כל הסטים של כל התרגילים ביום | `+50` XP **לכל** חלק גוף + `+50` אנרגיית קרב |
| עקומת רמות | `xpForLevel(n) = 100 × 1.35^(n−1)` |
| רמת הדמות | `floor(ממוצע ששת רמות חלקי הגוף)` |
| אנרגיית קרב | `+10` לכל סט, `+50` לסיום אימון (נצברת ל‑Phase 2) |

הסט הראשון אי פעם בתרגיל **קובע** את השיא ולא נחשב שיא חדש (אין עם מה להשוות).

### רצף שבועי (Sun–Sat)

`weeklyTarget` ימי אימון **שונים** בשבוע קלנדרי = "שבוע מושלם" → דרגה +1, בונוס
קבוע ומצטבר של `+10%` לכל הסטטיסטיקות. שבוע **סגור** שלא הגיע ליעד מוריד דרגה
אחת (רצפה 0). השבוע הנוכחי לעולם לא נשפט, ורמות/XP לעולם לא נלקחות.
הדרגה נגזרת מ‑`workoutDays` + התאריך של היום, ולכן שבוע שחלף מתעדכן גם בלי
פעולה של המשתמש (`refreshStreak` רץ בכל עלייה של האפליקציה).

**היעד מגיע מהתוכנית, והתוכנית מגיעה מהיומן.** בלי תוכנית היעד הוא 3 (התוכנית
המובנית); תוכנית של 4 אימונים בשבוע דורשת 4. בעורך היעד **נגזר משיבוץ ימי
השבוע** ולא מוקלד ידנית (`deriveWeeklyTarget` — ראו "היעד השבועי נגזר מהשיבוץ"). שבוע שכבר נסגר נשפט מול היעד שהיה
פעיל **באותו שבוע**: `weeklyTargetsFromEvents` מקפל את אירועי `plan_updated`
(ו‑`data_cleared`, שמחזיר ל‑3) לציר זמן של יעדים, ו‑`weeklyTargetForWeek` שואל
אותו לפי הרגע שבו השבוע נסגר. כיוון שהציר הזה נגזר מ**קבוצת** האירועים בסדר
`(ts, id)`, הרצף החי (`refreshStreak`, `commit`) והרצף שנבנה מחדש
(`rebuildGame`) תמיד מסכימים — גם אחרי מיזוג בין שני מכשירים.

### מניעת "חקלאות XP"

XP ואנרגיה מוענקים **פעם אחת לכל (תאריך, תרגיל, מספר סט)** — המפתח נשמר ב‑
`game.granted`. ביטול סימון של סט **לא** מחזיר XP, וסימון חוזר **לא** מעניק שוב.
כך כפתור ה‑✓ לא יכול לשמש כברז XP, ובלי לקנוס משתמש שתיקן טעות.
אותו רעיון לבונוס סיום האימון, שנשמר פעם אחת ליום ב‑`game.bonusDays`.

### XP רטרואקטיבי (`ensureGameState` ב‑`migrate.ts`)

בכל טעינה שבה `state.game` חסר או מגרסה לא מוכרת, ההיסטוריה הקיימת מקבלת XP:

1. ייבוא `hyp3_data_v1` שקרה עכשיו (אירועי `session_imported`);
2. משתמש שכבר ייבא ב‑Phase 0 (`legacyImported === true`, `game === null`);
3. אימונים שתועדו חי תחת Phase 0 (אירועי סטים בלי XP);
4. מצב עם אימונים אבל בלי יומן — האימונים "משוחזרים" כאירועי
   `session_imported` עם `source: "recovered"` לפני חישוב ה‑XP.

ההענקות עצמן נכתבות כאירועים ליומן (עם `ts` של תאריך האימון), כך שהמצב נשאר
פונקציה טהורה של היומן. הענקות רטרואקטיביות מסומנות `retro: true`:
הן משלמות XP ושיאים, אבל **לא** אנרגיית קרב ו**לא** ימי רצף — הרצף מתחיל מ‑0,
כפי שדורש המפרט. הפעולה אידמפוטנטית: הרצה שנייה לא מעניקה כלום.

### מסך הדמות (`דמות`)

* **SVG שכבתי** שהפרופורציות שלו נגזרות מרמות חלקי הגוף: חזה מרחיב את פלג הגוף
  העליון, גב מוסיף "כנפיים" (lats), כתפיים מרחיבות את מוטת הכתפיים והדלתות,
  ידיים מעבות את הזרועות, רגליים מעבות ירכיים ושוקיים, וליבה **מצרה** את המותן
  ומחדדת את שרירי הבטן. הגדילה חסומה (`BALANCE.character.visualMaxLevel`) כדי
  שהדמות תישאר מצוירת ומחויכת ולא מפלצתית.
* עלייה ברמה = הבהוב/פעימה קצרה על החלק שגדל (מכובד `prefers-reduced-motion`).
* לכל קבוצה יש `data-part`, ולכל מגירת ציוד יש `data-slot` (`gloves`/`belt`/
  `shoes`/`cape`) שמתמלאת מ‑`characterAnchors()` — ראו "הציוד על הדמות".
* **גוף** (`geometry`) ו**צבע** (`palette` + `decor`) מגיעים מהדמות הנבחרת
  (`data/characters.ts`) — ראו "מגוון הדמויות". שתי הגיאומטריות קוראות את אותן
  שש הרמות ומחזיקות את אותן נקודות עיגון לציוד.
* במסך: רמה ראשית, שישה פסי התקדמות (חזה, גב, רגליים, כתפיים, ידיים, ליבה),
  **רצועת הדמויות**, סטטיסטיקות לחימה נגזרות, דרגת רצף, חנות הציוד ומדף הגביעים.

### מסך האימון

`+XP חזה!` צף מעל כפתור ה‑✓ בכל סימון סט (אחד לכל חלק גוף שקיבל XP), מונה
אנרגיה שקט בפינת הכותרת, ו‑toast חגיגי לשיא אישי ולעליית רמה.

## מצב קרב (Phase 2)

### הלולאה

`core/combat.ts` הוא **טהור**: אין בו DOM, אין `Date.now()` ואין `Math.random()`.
ה‑UI מזין אותו בזמן שעבר ומצייר את מה שהוא מחזיר.

| חלק גוף | סטטיסטיקה | תפקיד בקרב |
|---|---|---|
| חזה | ATK | `damage = ATK × (1 ± 10%)` |
| ידיים | סיכוי/מכפיל קריטי | מכה קריטית |
| כתפיים | `attackIntervalMs` | תדירות ההתקפה האוטומטית |
| גב | DEF | נזק נכנס מוכפל ב‑`defK / (defK + DEF)` (רך, לעולם לא 0) |
| רגליים | Max HP | כמה מכות סופגים |
| ליבה | Regen | ריפוי לשנייה תוך כדי הקרב |

### דטרמיניזם

* PRNG מזורע (mulberry32) — הזרע נשמר באירוע של כל גל שנוצח.
* **צעד זמן קבוע** (`BALANCE.combat.tickMs = 50ms`): `advance()` צובר זמן אמיתי
  ומריץ רק טיקים שלמים, כך שקצב הפריימים לא משנה את התוצאה.
* **זרע לכל גל**: `waveSeed(seed, world, wave, attempt)` — אפשר לשחזר גל בודד
  בבדיקה, וניסיון חוזר אחרי נוק‑אאוט אינו שחזור מדויק של הקרב שהפסדתם.
* `advance()` חוסם "צבירת זמן" מלשונית שהייתה מוסתרת (תקרה של שנייה) — אין
  רווחים אופליין: הקרב רץ רק כשלשונית הקרב פתוחה וגלויה.

### כלכלת אנרגיה

* אנרגיה נצברת **רק** מאימון אמיתי: `+10` לסט, `+50` לסיום אימון.
* גל עולה `10` ⚡ ונגבה בסיום הגל — **נוק‑אאוט לא עולה אנרגיה**, רק זמן.
* אימון מלא ≈ `207` ⚡ ≈ **20 גלים** (היעד במפרט: 15–25).
* באפס אנרגיה הקרב נעצר עם הודעה בעברית: "אין מספיק אנרגיה — הדמות נחה.
  לכו להתאמן!" ומתחדש ברגע שסט חדש מסומן.

### גלים, מיני‑בוסים ושערי בוס

* `50` גלים בעולם, מיני‑בוס בכל גל עשירי (הפי `×2.2` HP, `×1.25` ATK).
* מטבעות: `(5 + 1×(גל−1)) × 1.6^(עולם−1)`, ומיני‑בוס משלם `×4`.
* HP/ATK של אויב: `32 × 1.045^(גל−1) × 1.6^(עולם−1)` ו‑`6 × 1.03^(גל−1) × 1.25^(עולם−1)`.
* אחרי הגל האחרון בעולם עומד **בוס העולם** — ראו הפרק הבא.

### הקשות ומהלך על

הקשה על האויב = מכה נוספת (`0.22 × ATK`) + טעינת מד מהלך העל (6% להקשה).
קצב ההקשות חסום ב‑`160ms` **בליבה** (לא רק ב‑UI), כדי שמאקרו לא ינצח שחקן.
מד מלא = מכה של `6 × ATK` + רעידת מסך (מבוטלת ב‑`prefers-reduced-motion`).

### מסך הקרב (`קרב`)

זירה עם הדמות (אותו בונה SVG, בקנה מידה קטן) מול ספרייט האויב, פסי חיים לשני
הצדדים, מספרי נזק צפים, פס אנרגיה, מונה גלים, מד מהלך על, שם העולם וכרטיס שער
הבוס. כל הטקסטים בעברית, RTL, יעדי מגע ≥ 40px.

### יומן הרפתקה (במסך ההיסטוריה)

`ui/feed.ts` מקרין את יומן האירועים לשורות קצרות: עליות רמה, שיאים אישיים,
סיום אימון, שינויי רצף, גלים, **בוסי עולם**, **רכישות בחנות**, הצטיידות
ו**ייבוא נתונים מקובץ** (`⬆ יובאו נתונים מקובץ (N אירועים)` — הסמן
`data_merged`, כדי שקפיצה פתאומית ב‑XP תקבל הסבר).
רצף של גלים רגילים **מתכווץ לשורה אחת** ("גלים 5–24 בחדר כושר נטוש · +180 🪙"),
ואילו מיני‑בוסים, בוסי עולם ופעולות חנות תמיד מקבלים שורה משלהם.

## בוסי עולם, ציוד וגביעים (Phase 3)

### שערי הבוסים

בסוף כל עולם (אחרי גל 50) עומד בוס עם **דרישות רמות לחלקי גוף**. אם הן לא
מולאו, הקרב פשוט לא מתחיל: המסך עובר למצב `gated` ואומר בעברית בדיוק מה חסר
(`חסר לכם: חזה רמה 3 · רגליים רמה 3`). ברגע שרמה עולה — גם באמצע סשן פתוח —
השער נפתח מעצמו והקרב מתחיל (`setGate` נקרא בכל פריים).

| עולם | בוס | דרישות |
|---|---|---|
| 1 · חדר כושר נטוש | **מאמן הצללים** | חזה 3 · ידיים 3 · רגליים 3 |
| 2 · הרחוב | **שליט הרחוב** | חזה 5 · גב 5 · ידיים 5 |
| 3 · הזירה | **אלוף האלופים** | גב 7 · ליבה 7 · רגליים 6 · כתפיים 6 |
| 4 · הר האולימפוס | **זאוס** | כל ששת חלקי הגוף ברמה 8 |

**איך המספרים נבחרו.** שתי עקומות בלתי תלויות הוצלבו בסימולציה מול המנוע האמיתי:

1. **קושי** — באיזו רמה גל 50 של עולם N ניתן לניצחון (עם הקשות): ‎3 / 5 / 7 / 9.
2. **קצב אימון** — כמה אימונים לוקח למתאמן 3×בשבוע להגיע לרמה: ‎4 / 9 / 19 / 36.

כל שער הוצב על הרמה שהשחקן צריך ממילא, כך שהוא נסגר בערך אימון אחד אחרי
שנגמרים לו הגלים — מבקש **אימון**, לא גרינד. כדי שזה יסתדר, גם מכפילי העולם של
Phase 2 כווננו מחדש (‎`4×`/`2.2×` → `1.6×`/`1.25×`): המספרים הישנים הפכו את
עולמות 3–4 לבלתי‑ניתנים להשגה בכל רמה שמתאמן אמיתי יכול להגיע אליה, מה שהיה
הופך את בוסי העולם לקישוט. הפירוט המלא בהערה בראש `core/balance.ts`.

### קרב הבוס

הבוס הוא **ספוג** עם מכות כבדות ואיטיות (`2400ms` בין מכות): גל רגיל נגמר
בשניות ספורות, בוס לוקח כ‑‎26 / 33 / 43 / 60 שניות של משחק פעיל לדמות שרק בדיוק
עומדת בשער — **בלי ציוד כלל**. יש בדיקה שמוודאת בדיוק את זה לכל ארבעת הבוסים.

* HP/ATK: עקומת הגלים בגל `51` כפול `hpMult`/`atkMult` של הבוס.
* עלות: `30` ⚡ (שלושה גלים), נגבית רק בניצחון.
* פרס: `400 × 1.7^(עולם−1)` 🪙 — ‎400 / 680 / 1156 / 1965.
* ניצחון → אירוע `boss_defeated` → העולם הבא נפתח (`wave` חוזר ל‑1) + **גביע**.

### מצב אלוף (endgame)

אחרי **זאוס** אין עולם חמישי, ולכן ההחלטה: הדמות **נשארת בעולם 4** ומונה הגלים
פשוט ממשיך מעבר ל‑50, עם אותה עקומת התחזקות. כל גל נוסף הוא שיא אישי חדש,
כרטיס הבוס הופך לבאנר "👑 מצב אלוף", והגביע הרביעי יושב במדף. זה שומר על
המשחק פתוח בלי להמציא תוכן שאי אפשר לאזן.

טכנית: `bossStanding(world, wave, defeated)` מחזיר `false` כשהבוס כבר גביע, ולכן
`spawn()` פשוט ממשיך להוציא אויבים רגילים; `isEndgame(defeated)` הוא מה שה‑UI
בודק.

### חנות הציוד

**איפה:** במסך 🦸 **דמות**, לא בזירה — קנייה משנה מיד את ציור הדמות ואת טבלת
הסטטיסטיקות שכרטיס אחד מעליה, כך שסיבה ותוצאה נשארות על אותו מסך. הזירה נשארת
מסך חד‑מטרה שאפשר להפעיל ביד אחת באמצע אימון.

ארבעה מגירות (כפפות · חגורה · נעליים · גלימה), שלוש דרגות בכל אחת:

| מגירה | דרגה 1 | דרגה 2 | דרגה 3 |
|---|---|---|---|
| 🥊 כפפות (התקפה/קריטי) | כפפות אימון · 120 🪙 | כפפות עור · 520 🪙 | כפפות האלופים · 1900 🪙 |
| 🎗 חגורה (הגנה/חיים) | חגורת בד · 120 🪙 | חגורת כוח · 560 🪙 | חגורת אלוף עולם · 2000 🪙 |
| 👟 נעליים (מהירות/חיים) | נעלי ריצה · 140 🪙 | נעלי הרמה · 620 🪙 | כנפי הרמס · 2200 🪙 |
| 🧣 גלימה (התאוששות/הכול) | מגבת אימון · 150 🪙 | גלימת הרחוב · 700 🪙 | גלימת האולימפוס · 2400 🪙 |

**תמחור:** חמישים הגלים של עולם 1 משלמים ≈`1800` 🪙 ועוד `400` מהבוס, וכל עולם
מכפיל את התשלום ב‑`1.6`. לכן דרגה 1 בהישג יד בעולם הראשון, דרגה 2 סביב הבוס
שלו, ודרגה 3 במהלך עולמות 2–3.

**איך הבונוס נכנס לסטטיסטיקות:** `deriveStats(parts, streakTier, bonus)` מחבר את
הבונוס לערך שנגזר מהרמה **ואז** מכפיל בבונוס הרצף — כך ציוד ורצף מתחברים, אבל
איבר הרמה תמיד דומיננטי. הציוד לעולם לא "נושא" דמות לא מאומנת.

**כללים (טהורים, ב‑`core/xp.ts`):** אי אפשר לקנות פעמיים, אי אפשר לקנות בלי
מטבעות (הכיס נבדק **לפני** שנכתב משהו — רכישה שנדחתה לא משאירה זכר ביומן),
ואי אפשר להצטייד בפריט שלא נקנה או במגירה הלא נכונה.

### הציוד על הדמות

כל פריט מצויר מ**אותן נקודות עיגון** של הגוף (`characterAnchors`): גב רחב מרחיב
את הגלימה, רגליים עבות מרחיבות את הנעליים, ליבה חטובה מצרה את החגורה. מהגדרת
הפריט מגיעים רק שני צבעים ודרגה. הגלימה היא השכבה היחידה שמצוירת **לפני** הגוף
(היא תלויה מאחוריו); השאר נלבשות מעליו.

הכול חייב להיקרא גם ב‑220px (מסך הדמות) וגם ב‑90px (הזירה), ולכן כל פריט הוא
צללית אחת נועזת ועוד פרט הדגשה אחד לכל היותר.

### מגוון הדמויות (Roster)

**איפה:** רצועת "דמויות" במסך 🦸 **דמות**, מתחת לדמות עצמה — הקשה על כרטיס
משנה מיד את הציור שמעליה (וגם את הדמות בזירה).

| מזהה | שם | גוף | מחיר | מה זה |
|---|---|---|---|---|
| `hero_m` | לוחם המכון | male | **0 🪙** | הדמות המקורית, ברירת המחדל |
| `hero_f` | לוחמת המכון | female | **0 🪙** | גוף בסיס שני: מוטת כתפיים צרה יותר, אגן רחב, מותן צרה, חזה עגול, שיער אסוף |
| `robot` | רובוט מתאמן | male | 400 🪙 | פלדה, קסדת ויזור זוהרת ואנטנה |
| `spartan` | לוחם עתיק | male | 900 🪙 | ברונזה, קסדה עם ציצה אדומה ומגן אף |
| `zombie` | זומבי מתאמן | male | 1400 🪙 | ירוק חולני, תפרים על המצח, עיניים צהובות |
| `ninja` | נינג׳ת צללים | female | 1800 🪙 | מסכה מלאה, סרט ראש אדום מתנפנף |

**הכלל שאין ממנו יוצא דופן: הדמויות הן קוסמטיקה בלבד.** אף דמות לא נותנת סטט,
לא בונוס ולא שער — `deriveStats` אפילו לא מקבל אותן כפרמטר, ויש בדיקה שסורקת את
כל הרוסטר ומוודאת שטבלת הסטטיסטיקות זהה לחלוטין לכל בחירה. רק אימון מחזק.

**שני גופי הבסיס חינם, תמיד.** ייצוג הוא לא רכישה: `hero_m` ו‑`hero_f` נחשבים
"בבעלות" מעצם הגדרתם (`cost: 0`), אף פעם לא נכתבים ל‑`characters.owned`,
והמעבר ביניהם לא עולה מטבע אחד ולא תלוי בשום אירוע ששרד מיזוג.

**רכישה:** כרטיס נעול נפתח בגיליון אישור (שם, מחיר, כמה מטבעות יש) — הקשה אחת
לעולם לא קונה. הכיס נבדק ב‑`buildCharacterPurchase` **לפני** שנכתב משהו, בדיוק
כמו בחנות הציוד, ולכן רכישה שנדחתה לא משאירה זכר ביומן. קנייה גם **בוחרת** מיד.

**איך זה נשמר:** `characters.owned` (סקינים בלבד) ו‑`characters.selected`
מקופלים מהיומן כמו כל השאר. `character_purchased` אידמפוטנטי לפי מזהה הדמות —
שני מכשירים שקנו את אותו סקין אופליין (שני uuid שונים) יחויבו **פעם אחת**
באיחוד; `character_selected` הוא LWW לפי `(ts, id)`, ולכן שני מכשירים מתכנסים
לאותה דמות. הבחירה מסתנכרנת בלי שורת סנכרון אחת ייעודית — היא פשוט אירוע.

### איך סקין מצויר

הגיאומטריה **לא** משוכפלת: `characterGeometry(parts, body)` היא אותה פונקציה עם
טבלת פרופורציות אחת לכל גוף (`BODIES`), והשורה של `male` היא בדיוק המספרים
המקוריים — הווריאנטים נוצרו מחילוץ הקבועים, לא מכיוונון מחדש. סקין תורם רק:

* `palette` — שמונה צבעים שנכתבים כ‑CSS custom properties על ה‑`<svg>` עצמו,
  כך ש‑`styles/character.css` נשאר המקום היחיד שבו מוגדרים הצבעים;
* `decor` — קישוט ראש (שיער/ויזור/קסדה/תפרים/מסכה) ביחידות של רדיוס הראש, כך
  שהוא נקרא גם ב‑220px וגם ב‑90px, ויכול להסתיר עיניים/פה כשהוא מכסה אותם.

לכל דמות יש `id` משלה ל‑`linearGradient` של פלג הגוף, כי רצועת הרוסטר מציירת
שש דמויות על אותו עמוד ו‑`id` כפול היה גורם לכולן לקבל את הצבע של הראשונה.

### גביעים

כל בוס שהופל משאיר **מדליה** קטנה על חזה הדמות (`<g class="ch-trophies">`) ו**גביע
SVG** במדף הגביעים במסך הדמות, עם שם הבוס ושם העולם בעברית. לצידם מוצג גם מונה
המיני‑בוסים ומונה הגלים.

## תוכנית אימונים ניתנת לעריכה

**התוכנית מגדירה את הימים של עצמה** — בין יום אחד לשבעה — ובתוך כל יום הכול
ניתן לעריכה: סטים, חזרות, מנוחה, סדר התרגילים, הסרה והוספה, וגם **תרגילים
משלכם**. גרסה 1 של המסמך הכירה בדיוק שלושה ימים קבועים (A/B/C); גרסה 2 החליפה
את זה במערך מסודר של ימים, כל אחד עם מפתח יציב, שם עברי וימי השבוע שבהם מתאמנים
אותו — כך שפיצול A/B של 4 אימונים בשבוע (א׳ בראשון ורביעי, ב׳ בשלישי וחמישי)
הוא **שני** ימים עם `weeklyTarget: 4`.

### המודל

`PlanDay` הוא `{key, label, weekdays?, exercises}`:

* `key` — **יציב**, וכל השאר מצביע עליו: `Session.day`, מטעני האירועים והטאב
  הפעיל. שינוי שם היום או הזזתו במערך לא מייתמים שום אימון מתועד. יום שהוסב
  מ‑v1 שומר על `A`/`B`/`C`, יום חדש מקבל `d_` + פרוסת uuid. ארבעת מפתחות המסך
  (`CH`, `BT`, `H`, `PL`) שמורים ואסורים כמפתחות יום.
* `label` — שם עברי חופשי ("אימון A", "חלק א׳").
* `weekdays` — `0=ראשון … 6=שבת`. השיבוץ הזה הוא גם **שורת הטאבים** (יום שמתאמנים
  בו פעמיים בשבוע מקבל שני טאבים — ראו "טאבים לפי לוח האימונים"), והטאב שנפתח
  כברירת מחדל הוא זה שמשובץ ליום בשבוע הנוכחי; אם אף יום לא תובע אותו —
  הראשון בתוכנית.
* `weeklyTarget` (ברמת המסמך) — כמה ימי אימון שונים בשבוע נחשבים "שבוע מושלם".
  מכוון בנפרד ממספר הימים: שני אימונים שמתחלפים על פני ארבעה ימים = יעד 4.
  בעורך הוא **נגזר** ולא מוקלד — ראו "היעד השבועי נגזר מהשיבוץ" למטה.

`resolveProgram(plan)` מחזיר את המבנה שהמסכים מציירים ממנו:
`{days: [{key, label, weekdays, day}], weeklyTarget}` — מסודר, כשסדר המערך הוא
סדר הטאבים, ו‑`day` הוא ה‑`Day` המלא (תרגילים + כותרת). חיפוש יום בודד נעשה עם
`dayOf(program, key)`, שמחזיר `null` למפתח שלא קיים — מפתח לא מוכר הוא **נתון**
(תוכנית ממכשיר אחר), לא שגיאה.

`PlanDoc` הוא כל התוכנית באובייקט JSON אחד. שורה ביום היא
`{id, sets, reps, rest}` בלבד: היא **מצביעה** על הגדרת תרגיל ולא מעתיקה אותה.
לכן שורה שמצביעה על תרגיל מובנה דורסת רק את המספרים — שיפור של ההסברים בגרסה
עתידית ישפר גם תוכנית ששמורה מזמן. תרגיל מותאם אישית (`cx_…`) נושא את ההגדרה
שלו, פחות ההסברים — ולכן מסך האימון פשוט לא מצייר עבורו מגירת "הסבר ודגשי
ביצוע" ריקה.

**`plan: null` = התוכנית המקורית.** `resolveProgram(null)` מחזיר את
`BUILTIN_PROGRAM` **עצמו**, וימיו הם אובייקטי `PROGRAM` עצמם — ולכן מי שלא נגע
בעורך מריץ בדיוק את אותו קוד כמו קודם. גם יום שלא נערך בתוך תוכנית אמיתית מוחזר
כאובייקט ה‑`Day` המקורי; רק יום שנערך באמת מקבל משך ומיקוד מחושבים מחדש.

### ניהול הימים בעורך

* **הוספת יום** — כפתור ＋ ליד תת‑הטאבים (עד 7 ימים). היום נולד עם מפתח `d_`
  חדש, בשם "אימון חדש", וגיליון התרגילים נפתח מיד: הוספת יום ובחירת התרגיל
  הראשון שלו הן פעולה אחת ולא שתיים. יום ריק אינו ניתן לשמירה, והשמירה אומרת
  את זה בעברית במקום להיכשל בשקט.
* **שינוי שם** — שדה טקסט בכרטיס היום. הוא נכתב ישירות לטיוטה (רינדור מחדש היה
  גונב את הסמן באמצע מילה), והטאב שמעליו מתעדכן ידנית כדי לא לפגר אחריו.
* **סידור** — ▲/▼ מזיזים את היום במערך, והמערך **הוא** סדר הטאבים.
* **הסרה** — 🗑 עם אישור, שאומר במפורש שאימונים שכבר תועדו ליום הזה **נשארים
  בהיסטוריה**; רק היום יורד מהתוכנית. את היום האחרון אי אפשר להסיר.

### שיבוץ לימי השבוע

שורה של שבעה צ׳יפים (א ב ג ד ה ו ש) לכל יום. **יום בשבוע שייך לכל היותר ליום
אימון אחד**: הדלקה כאן מכבה במקום שממנו הוא נלקח, ושורה שקטה מתחת לצ׳יפים אומרת
מאיפה ("רביעי הועבר מאימון B"). בלי הבלעדיות הזו `defaultDay` היה מטיל מטבע בין
שני ימים שתובעים את אותו יום בשבוע, והיעד השבועי הנגזר היה קטן ממספר האימונים
שהוא מתאר. יום שנשאר בלי ימי שבוע פשוט לא נפתח אוטומטית — והשדה יורד מהמסמך
לגמרי, בדיוק כפי שבנאי הימים כותב אותו, כדי שמסמך יישאר שווה לעצמו אחרי שמירה.

### היעד השבועי נגזר מהשיבוץ

`deriveWeeklyTarget(days)` ב‑`core/plan.ts` הוא **מקור האמת היחיד**, והעורך רק
מציג אותו: "יעד שבועי: N ימי אימון (משפיע על רצף השבוע המושלם)".

| מצב | היעד |
|---|---|
| יש שיבוץ | מספר ימי השבוע ה**שונים** שהתוכנית תובעת (הצ׳יפים בלעדיים, ולכן זה בדיוק "כמה פעמים בשבוע אני בחדר כושר") |
| אין שיבוץ בכלל | `min(מספר הימים, 3)` — אימון אחד לכל יום בתוכנית, בתקרה של ברירת המחדל |
| מפת A/B/C המובנית | 3 — ראו מיד למטה |

מפת ברירת המחדל (`[0,1] / [2,3] / [4,5,6]`) מכסה את כל שבעת ימי השבוע בשלושה
אימונים, כי היא מפת **ניתוב** שנועדה לפתוח טאב בכל יום — לא לוח אימונים. ספירה
שלה הייתה הופכת "לפתוח את העורך ולשמור" לקפיצה מ‑3 ל‑7, ולכן היא מזוהה במפורש
ומוחזרת ל‑3. ברגע שנוגעים בצ׳יפים, המפה היא לוח אמיתי ונספרת ככזה.

### טאבים לפי לוח האימונים

`scheduleTabs(program)` ב‑`core/plan.ts` הוא **מקור האמת היחיד** לשורת טאבי
האימון, והוא מציג את **השבוע** ולא את רשימת הימים: תוכנית A/B שמתאמנים בה
בראשון+רביעי / שלישי+חמישי מקבלת **ארבעה** טאבים — ראשון(א), שלישי(ב), רביעי(א),
חמישי(ב) — ממוינים לפי יום בשבוע, כשהכותרת היא שם היום והשורה הקטנה היא שם
האימון. יום בלי שיבוץ מקבל טאב יחיד (הכיתוב הנוכחי שלו) בסוף השורה.

היוצא מן הכלל הוא **מפת הניתוב** המובנית (`[0,1] / [2,3] / [4,5,6]`, שכל תוכנית
שעברה מ‑v1 יורשת): היא מזוהה באותו predicate שהיעד השבועי משתמש בו
(`isBuiltInWeekdayMap`) ונשארת **שלושה** טאבים — פריסה שלה הייתה מנפחת תוכנית של
שלושה ימים לשבעה טאבים, בדיוק כמו שספירה שלה הייתה מנפחת את היעד השבועי ל‑7.

* **`viewId`** — `UiState.view` שומר `dayKey` כשליום יש טאב אחד, ו‑`dayKey@יום`
  (למשל `d_a1b2@3`) כשהוא נפרס לכמה. כל ה‑view‑ים שנשמרו אי פעם (`A`, `d_…`)
  נשארים תקפים; `normalizeUi` מקבל את שתי הצורות ונופל לטאב ברירת המחדל אחרת.
* **ה‑`@` לא יורד מתחת ל‑UI.** `ui/app.ts` הוא המודול היחיד שמחזיק את הצורה
  המורכבת, ו‑`viewDayKey(view)` מקלף אותה לפני מסך האימון, הכותרת, ה‑session וכל
  אירוע. שני טאבים של אותו אימון = אותו יום, אותו session, אותם `set_*` — אין
  צורת אירוע חדשה ואין צורת session חדשה.
* **ברירת המחדל** — `defaultTabView(plan, now)` בוחר את הטאב המשובץ להיום (יום
  רביעי → טאב "רביעי" של חלק א׳), ואם אין כזה נופל בדיוק כמו `defaultDay`.
* **שורה שנגללת** — הטאבים האלה הם **שורת תת‑הטאבים** של מרכז 🏋️ אימון (ראו
  "ניווט דו‑שכבתי"), ולכן ארבעה מופעים כבר לא דוחפים כלום החוצה: דמות, קרב
  והיסטוריה עברו למרכזים שלהם. רק מעל **ארבעה** תת‑טאבים — תוכנית של 5–7 ימים —
  השורה נגללת אופקית (`.sub-row.scroll` ב‑`styles/tabs.css`) במקום לרסק אותם;
  הטאב הפעיל נגלל לתצוגה בכל render וכל טאב נשאר ≥40px. השורה הראשית לעולם לא
  נגללת, כי היא תמיד אותם שלושה מרכזים.

### תוכניות מוכנות

`📋 תוכניות מוכנות` פותח גיליון עם מסמכי `PlanDoc` **שלמים** (`data/presets.ts`)
— לא תבניות. הבחירה מבקשת אישור, מחליפה את ה**טיוטה** (שום דבר לא נשמר עד 💾),
ומשם זו שמירה רגילה לגמרי עם אירוע `plan_updated` אחד.

| תוכנית | מה יש בה |
|---|---|
| **היפרטרופיה 3 ימים** | התוכנית המובנית A/B/C — שקולה ל"איפוס לתוכנית המקורית" |
| **תוכנית A/B — 4 ימים** | שני אימונים על פני ארבעה ימים: חלק א׳ (רגליים, חזה, כתפיים ויד אחורית) בראשון וברביעי, חלק ב׳ (גב ויד קדמית) בשלישי ובחמישי · 8 תרגילים ליום · מנוחה 90 שנ׳ בתרגילים מורכבים ו‑60 שנ׳ בבידודים · יעד שבועי 4 |

מפתחות הימים **נטבעים מחדש בכל בחירה** (`d_…`): שני מכשירים שבחרו את אותה
תוכנית מוכנה לא ממזגים בטעות את ימיהם לאחד, ואימונים שתועדו תחת הימים הקודמים
ממשיכים להצביע על המפתחות הישנים במקום לקבל שם של תוכנית שלא התאמנו בה.

### ספריית התרגילים

מלבד תרגילי התוכנית המובנית יש **ספריית תרגילים** (`EXTRA_EXERCISES` ב‑
`data/program.ts`): סקוואט בסמית׳, פשיטת/כפיפת ברכיים במכשיר, הרחקה לצדדים,
פשיטת מרפקים בפולי, פולי עליון באחיזה צרה, פייס פול, הרמת שכמות ופטישים. הם
תרגילים מובנים לכל דבר — אותה כתיבה מדריכה, אותו `bodyPart`/`split` ואותו
`findExercise` — והם פשוט לא יושבים בתוכנית ברירת המחדל. הם מוצעים בגיליון
ההוספה של העורך ומשמשים את התוכנית המוכנה. הם נשמרים **מחוץ** ל‑`PROGRAM`
בכוונה, כדי ש‑`tests/program.test.ts` ימשיך להשוות את `PROGRAM` לקובץ הישן
מילה במילה.

### הסבה מ‑v1 ל‑v2

`normalizePlanDoc` מקבל את **שתי** הגרסאות: מסמך v1 (או מטען `plan_updated`
שנכתב על ידי לקוח ישן, ומסמך בלי `version` בכלל) מוסב בקריאה למערך של שלושה
ימים — מפתחות `A`/`B`/`C`, השמות המקוריים, ימי השבוע `[0,1] / [2,3] / [4,5,6]`
ו‑`weeklyTarget: 3`. אלה בדיוק הטווחים ש‑`defaultDay` השתמש בהם מאז ומתמיד
(ראשון־שני → A, שלישי־רביעי → B, חמישי־שבת → C), ושם היום נגזר מהיום **הראשון**
בטווח — כלומר ראשון/שלישי/חמישי, בדיוק כמו `DAY_NAMES`. לכן מי ששמר תוכנית לפני
השדרוג לא רואה שום שינוי: אותם טאבים, אותם שמות, אותו טאב שנפתח בכל יום בשבוע.
מסמך מגרסה **עתידית** נדחה ל‑`null` (= התוכנית המובנית), כמו קודם.

> **לקוחות מעורבים על אותו חשבון:** לקוח ישן שיקפל `plan_updated` עם מסמך v2
> יראה `version: 2`, ידחה אותו ויציג את התוכנית המובנית — לא יאבד מידע, אבל גם
> לא יראה את התוכנית החדשה. הפתרון הוא רענון של ה‑PWA בכל מכשיר; לא ניסינו
> תאימות עמוקה יותר, כי היומן עצמו נשמר ללא שינוי והשדרוג פותר הכול.

### שמירה ומיזוג

שמירה = **אירוע `plan_updated` אחד** שנושא את המסמך כולו. הכרעה בין מכשירים היא
לכן סדר הקיפול עצמו: **האחרון ב‑`(ts, id)` מנצח**, ו‑`data_cleared` מאפס את
התוכנית ל‑`null`. אין מה ליישב שדה‑שדה, ומיזוג בשני הכיוונים נותן אותה תוצאה.
`rev` נספר לצורכי תצוגה בלבד — הסמכות היא היומן.

### היסטוריה שורדת כל עריכה

XP נשמר לפי **מזהה תרגיל** ולא לפי מיקום: `best[exId]`,
`granted[date|exId|setIndex]` ו"האימון הקודם" לא יודעים באיזה יום התרגיל יושב,
או אם הוא יושב באיזשהו יום בכלל. אפשר לסדר מחדש, להסיר ולהחזיר — שום שיא לא
הולך לאיבוד. מסכי ההיסטוריה והיומן מציגים תרגילים לפי מזהה גם שנים אחרי, ולכן
הם משתמשים ב‑`makeResolver(state.plan)` ונופלים חזרה למזהה הגולמי אם התרגיל כבר
לא קיים.

**גם שם היום נפתר ככה.** אימון מתועד נושא את מפתח היום שבו הוא נרשם, והמפתח
הזה עלול להיות יום ששונה שמו, יום שהוסר מהתוכנית או יום שנוצר במכשיר אחר.
`dayLabelOf(program, key)` יורד בסולם: השם שבתוכנית → השם המובנה אם המפתח הוא
עדיין `A`/`B`/`C` (אימון מלפני שנגעתם בעורך) → "אימון" ניטרלי. כיתוב יום השבוע
ושורת המיקוד מוצגים רק כשהיום עצמו עדיין קיים — הם **לא** מושאלים מיום אחר, ואף
פעם לא מוצג מפתח `d_…` גולמי. אותו כלל חל על יומן ההרפתקה: `workout_finished`
נושא את המפתח, והמסך הוא זה שיודע לתת לו שם ("אימון הושלם במלואו · חלק א׳").

### מסך העריכה (`PL`)

`PL` הוא מסך אמיתי אבל **לא טאב**: הפעולה היומיומית בשורת האימון היא בחירת יום
אימון, ועורך שיושב שם היה גונב לה מקום. הוא שייך למרכז 🏋️ **אימון**
(`hubOf('PL') === 'TR'`) — הטאב הראשי נדלק כשהוא פתוח, אבל אף תת‑טאב לא —
והכניסה היא כפתור ⚙️ בכותרת מסך האימון (שם מגלים שרוצים לשנות את היום) וכרטיס
התוכנית במסך ⚙️ **הגדרות** (שם יושבות שאר פעולות הנתונים). היציאה מחזירה למסך
שממנו נכנסתם, כולל חזרה למסך ההגדרות.

בתוך המסך, מלמעלה למטה: תת‑טאב לכל יום שהתוכנית מגדירה (ו‑＋ להוספת יום), כרטיס
היום — שם, ▲/▼ להזזתו, 🗑 להסרתו, שבעת צ׳יפי ימי השבוע והיעד השבועי הנגזר — ואז
שורה לכל תרגיל עם ▲/▼ לסידור, 🗑 להסרה (עם אישור),
ושלושה שדות — סטים, חזרות, מנוחה. `+ הוספת תרגיל` פותח גיליון תחתון עם ספריית
התרגילים המובנים שעדיין לא ביום, התרגילים המותאמים, וטופס ✨ ליצירת תרגיל חדש:
שם בעברית (חובה), אנגלית (רשות), חלק גוף עיקרי, חלק גוף משני אופציונלי
(שמתורגם לפיצול 70/30 בדיוק כמו בתרגילים המובנים), יחידת מדידה וציוד.

**העריכה כולה בטיוטה בזיכרון** עד ל‑💾 שמירה. שמירה חיה בכל הקשה הייתה מציפה את
היומן (ואת תור הסנכרון) בעשרות מסמכים מלאים לכל סשן עריכה, ובעיקר —
הייתה הופכת יום חצי‑מסודר לתוכנית האמיתית ברגע שמישהו מתפזר באמצע.
`איפוס לתוכנית המקורית` שומר `plan: null` (עם אישור), וגם זה אירוע — מכשיר אחר
חייב ללמוד על האיפוס. `📋 תוכניות מוכנות` מחליף את הטיוטה בתוכנית מוכנה, וגם הוא
לא נוגע בדיסק עד ה‑💾.

יציאה מהעורך לא יכולה לנחות על יום מת: `setView` מתרגם כל view לטאב אמיתי
(`resolveTab`) — מפתח יום שהתוכנית כבר לא מכירה נופל לטאב ברירת המחדל שלה, ומפתח
יום שנפרס בינתיים לכמה טאבים נוחת על המופע של היום — מה שמכסה גם משיכה מהענן
שמחקה או שיבצה מחדש יום במכשיר אחר.

### ולידציה

`savePlan` מסרב לשמור (ולא כותב שום אירוע) על יום ריק, סטים מחוץ ל‑1–10, מנוחה
מחוץ ל‑15–600 שניות, שדה חזרות ריק, תרגיל כפול ביום, תרגיל מותאם בלי שם, יום
בלי שם, מפתח יום פסול או כפול, תוכנית בלי ימים או עם יותר משבעה, ויעד שבועי
מחוץ ל‑1–7. בקריאה, `normalizePlanDoc` **מתקן** במקום לדחות: מספרים נחתכים
לטווח, שורות שמצביעות לשומקום מושמטות, ימי שבוע פסולים נופלים, מפתחות כפולים
מאוחדים, יום מובנה שנשאר ריק חוזר ליום המובנה, ומסמך שלא נשאר בו אף יום חוזר
לשלושת הימים המובנים — מסך אימון ריק הוא לא תוצאה אפשרית.

## סנכרון בענן וחשבון Google (אופציונלי)

הפיצ׳ר הזה **כבוי כברירת מחדל** ואינו משנה דבר עד שממלאים את ההגדרות. בלי
הגדרה (וגם ב‑`file://` תמיד) `syncConfigured()` מחזיר `false`, שום לקוח לא נוצר,
שום מאזין לא נרשם וכרטיס החשבון פשוט לא קיים במסך. האפליקציה נשארת בדיוק
האפליקציה האופליינית שהייתה.

### הרעיון בשורה אחת

המודל כבר מוכן לסנכרון מהיסוד: כל כתיבה היא אירוע ב‑append‑only log, והמצב הוא
פונקציה טהורה של היומן. לכן:

> **סנכרון = איחוד קבוצות האירועים + `rebuildFromEvents`.**

אין פתרון קונפליקטים ואין ממשק מיזוג, כי אין קונפליקטים: סדר הקיפול `(ts, id)`
הוא תכונה של **הקבוצה**, ולכן שני מכשירים שמחזיקים את אותם אירועים מגיעים למצב
זהה בייט‑בייט — לא משנה מי ראה מה קודם (`tests/merge.test.ts`).

### מה קורה בפועל

| רכיב | תפקיד |
|---|---|
| `src/sync/config.ts` | ה‑URL וה‑anon key + `syncConfigured()` — **מתג ראשי** |
| `src/sync/backend.ts` | הממשקים `SyncBackend` + `AuthPort` — התפר שהבדיקות מזריקות לתוכו |
| `src/sync/meta.ts` | פנקס המנוע ב‑`gymrpg_sync_v1`: deviceId, cursor, outbox, userId, lastSyncAt |
| `src/sync/engine.ts` | לולאת ה‑write‑behind: outbox → push → pull → merge |
| `src/sync/supabaseBackend.ts` | **המודול היחיד** שמייבא `@supabase/supabase-js` |
| `src/sync/account.ts` | כרטיס החשבון במסך ההגדרות |
| `src/storage/merge.ts` | האיחוד עצמו: `mergeIntoStore` (משיכה) ו‑`mergeImport` (ייבוא מצטבר) |
| `supabase/schema.sql` | כל צד השרת. אין קוד שרת משלנו |

**מחזור אחד:** שטיפת ה‑buffer → דחיפת ה‑outbox במנות של 500 → משיכת עמודים של
1000 לפי `seq` → איחוד → `rebuildFromEvents` → `replaceAll` → ציור מחדש.
טריגרים: כתיבה מקומית (debounce 500ms), `online`, חזרה לטאב, כל 60 שניות בזמן
שהטאב גלוי, והתחברות. כישלון → backoff מעריכי (1, 2, 4… עד 5 דקות) שמתאפס
בהצלחה וב‑`online`.

**קיבוץ הקשות:** כל הקשה בשדה משקל היא אירוע `set_logged` מקומי — זה נשאר. אבל
ה‑payload הוא תצלום מלא (`w` **וגם** `r`), ולכן ל‑outbox נכנס רק האירוע האחרון
לכל `date|exId|setIndex`. הקלדת "42.5" = 4 אירועים מקומיים, שורה **אחת** בענן.

**למה אין לולאה אינסופית:** מיזוג נוחת דרך `replaceAll`, שבמכוון **אינו** משדר
ל‑`subscribeEvents`, והמנוע לא מוסיף שום אירוע משלו כשהוא ממזג. לכן אירוע
שנמשך מהשרת לא יכול להיחשב בטעות לכתיבה מקומית ולחזור החוצה.

### מה משתנה כשמחוברים

* **🗑 מחיקה** הופכת לפעולה על **כל החשבון**: אירוע `data_cleared` מסונכרן
  ומתקפל בכל מכשיר כמחיקה. הנוסח בדיאלוג אומר את זה במפורש.
* **⬆ ייבוא JSON** הופך ל**מצטבר** (`mergeImport`): קובץ הגיבוי מתאחד עם היומן
  המקומי ונרשם `data_merged`, במקום להחליף. ההחלפה ההרסנית נשארת רק כשמנותקים —
  שם היא באמת "שחזור גיבוי".
* **התנתקות** מוחקת רק את פנקס הסנכרון. כל האימונים נשארים במכשיר.

### הקמה (חד‑פעמית, ידנית)

ארבעה שלבים, בערך עשר דקות. **עד שהם נעשים — ואם לא עושים אותם בכלל — הכול
עובד בדיוק כמו קודם**, פשוט בלי ענן. אין כאן שום פקודה שהריפו מריץ בשבילכם:
Supabase ו‑Google הן קונסולות של מישהו אחר.

#### 1 · פרויקט Supabase והסכימה

1. [supabase.com](https://supabase.com) → **New project** (התוכנית החינמית
   מספיקה בגדול). לבחור אזור קרוב ולשמור את סיסמת מסד הנתונים.
2. **SQL Editor → New query** → להדביק את **כל** `supabase/schema.sql` →
   **Run**. הסקריפט אידמפוטנטי: הרצה חוזרת אינה עושה כלום.
3. **Table Editor** → אמורות להופיע `events` ו‑`sync_counters`, ריקות.
4. **Project Settings → API** → להעתיק את **Project URL**
   (`https://<ref>.supabase.co`) ואת מפתח ה‑**anon / publishable**.

#### 2 · פרטי OAuth ב‑Google Cloud Console

1. [console.cloud.google.com](https://console.cloud.google.com) → פרויקט חדש.
2. **APIs & Services → OAuth consent screen**: סוג **External**, שם אפליקציה,
   אימייל תמיכה ואימייל מפתח. אם האפליקציה נשארת ב‑**Testing**, להוסיף את
   כתובות הג׳ימייל שלכם תחת **Test users** — אין צורך בתהליך אימות של Google.
3. **APIs & Services → Credentials → Create credentials → OAuth client ID** →
   סוג **Web application**.
4. תחת **Authorized redirect URIs** להוסיף כתובת **אחת**, של Supabase ולא של
   האפליקציה:
   ```
   https://<ref>.supabase.co/auth/v1/callback
   ```
5. להעתיק **Client ID** ו‑**Client secret**.

#### 3 · הפעלת הספק וכתובות החזרה ב‑Supabase

1. **Authentication → Providers → Google** → Enable, להדביק Client ID + Secret
   → Save.
2. **Authentication → URL Configuration**:
   * **Site URL**: `https://<user>.github.io/gym-rpg/`
   * **Redirect URLs**: להוסיף גם `https://<user>.github.io/gym-rpg/` וגם
     `http://localhost:5173/`.

   האפליקציה מבקשת חזרה בדיוק אל `origin + pathname` של העמוד שממנו התחברתם
   (`defaultRedirect()` ב‑`sync/supabaseBackend.ts`) — בלי query ובלי hash.
   לכן כל כתובת שממנה מתחברים חייבת להופיע ברשימה, **כולל הסלאש הסופי**.
   כתובת שחסרה = חזרה ל‑`localhost` באמצע הטלפון, או שגיאת `redirect_to`.

#### 4 · חיווט הלקוח

`src/sync/config.ts`:

```ts
export const SYNC_CONFIG: SyncConfig = {
  url: 'https://<ref>.supabase.co',
  anonKey: 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…',
};
```

`npm run dev` → ⚙️ **הגדרות** → כרטיס החשבון מופיע → **התחברות עם Google**.
אחרי החזרה מהאימות: ב‑Supabase, **Table Editor → events** מתמלאת בשורות עם
`seq` עולה. `npm run verify` יזכיר מעכשיו את ה‑origin החדש כערך מותר ברשימה.

**למה מותר (ורצוי) לעשות commit ל‑anon key.** הוא מפתח *ציבורי* בהגדרתו: הוא
נארז בבנדל שכל דפדפן מוריד, והוא לא מעניק שום גישה בפני עצמו. הגבול הביטחוני
הוא RLS — `select`/`insert` מוגבלים ל‑`auth.uid() = user_id`, ואין policy ל‑
`update` או `delete` בכלל. בלי טוקן של משתמש מחובר, המפתח פותח דלת לחדר ריק.
מה ש**אסור** להיכנס לכאן לעולם הוא ה‑**service‑role key**, שעוקף RLS.

### מה מגן על היומן בצד השרת

* `primary key (user_id, id)` — דחיפה חוזרת של אירוע לא יוצרת עותק שני, ולכן
  אפשר לנסות שוב בלי חשש.
* `seq` פר‑משתמש שמוקצה ב‑trigger שנועל **שורת מונה** (`for update`). הנעילה
  מוחזקת עד ה‑commit, ולכן **סדר ההופעה לקוראים == סדר ה‑seq**. בלי זה ה‑cursor
  היה יכול לחנות אחרי שורה שעדיין לא בוצעה — ולאבד אותה לתמיד.
* RLS: `select` ו‑`insert` על שורות עצמך בלבד. **אין policy ל‑update או delete**,
  כלומר היומן append‑only גם ברמת מסד הנתונים. מחיקה מתבטאת כאירוע, לא כ‑DELETE.

### `npm run verify` וה‑allowlist

בנדל של `supabase-js` מכניס מחרוזות עם כתובות מוחלטות. `scripts/verify-dist.mjs`
לא מוותר עליהן בסיטונאות אלא מחזיק **רשימה מפורשת**, כל שורה עם הנימוק שלה:

| `http://localhost:9999` | קבוע ברירת המחדל של gotrue‑js, קוד מת: הלקוח תמיד נבנה עם URL מפורש |
| `https://github.com/orgs/supabase/discussions/<n>` | לינק ב‑`console.warn` על Node ישן |
| ה‑origin של פרויקט Supabase שהוגדר | נקרא מ‑`src/sync/config.ts` — הבקאנד של האפליקציה עצמה. כשלא מוגדר, פשוט לא קיים בבנדל |

בנוסף הסקריפט מוודא שאף אחד מהם לא באמת בשימוש רשתי (`fetch("http…"`,
`new WebSocket("…"`), ו**נכשל** על ערך ברשימה שהפסיק להתאים — היתר ששכחו ממנו הוא
חור. כל כתובת אחרת מפילה את הבנייה כמו קודם.

**עלות:** הבנדל גדל מ‑155 kB ל‑383 kB (קובץ יחיד, לא דחוס). בנייה ל‑`file://`
ממשיכה לעבוד ומציגה אפס ממשק ענן.

## אילוצים שנשמרים

* 100% אופליין — אין רשת, פונטים חיצוניים, CDN או קבצי אודיו. הצליל מסונתז
  ב‑Web Audio (ארפג׳ו 880 / 1108.7 / 1318.5 Hz).
* עברית ראשית, `dir="rtl"`, כותרות משנה באנגלית לתרגילים.
* Design tokens מקוריים: `#121824` / `#1E2638` / `#3B82F6` / `#10B981` / `#F59E0B`.
* Mobile‑first, יעדי מגע ≥ 40px, כבוד ל‑`prefers-reduced-motion`,
  ריווח תחתון לטיימר הצף.
* `strict: true` ב‑TypeScript, ללא `any` במודולי ה‑core.
* כל כתיבה עוברת דרך `DataStore` — שום מסך לא נוגע ב‑`localStorage` ישירות.
* אין `Math.random()` או `Date.now()` בלוגיקת הליבה; זמן וזרעים מוזרקים מבחוץ.

* `characters` — הרוסטר: ולידציה של הנתונים (מזהים ייחודיים, שני גופי בסיס
  ב‑0 🪙, **סריקה שמוכיחה שאף דמות לא נוגעת בסטטיסטיקות**), reducer מוגן מיזוג
  (רכישה כפולה משני מכשירים = חיוב אחד, מטבעות חסרים = שום אירוע, מזהה לא מוכר
  או שלא בבעלות מתעלמים ממנו, `data_cleared` מאפס), LWW לפי `(ts, id)`,
  ההתכנסות של הבחירה בין שני מכשירים, וקפיצת גרסת הבלוב ל‑v5.
* `characters.dom` — הרצועה על המסך: כרטיס לכל דמות, החלפה בהקשה אחת שמחליפה
  את ה‑SVG הגדול, גיליון האישור (קנייה מוצלחת מול "חסרים X 🪙" כפתור מנוטרל
  ששום דבר לא נכתב בגללו), הזירה שנלחמת בדמות הנבחרת, ותקינות ה‑SVG של **כל
  דמות** בארבע רמות, עם כל פריט ציוד ובשתי הגיאומטריות.
* `loop` — **הלולאה כולה בריצה אחת**: סטים → XP ו‑⚡ → גלים → שער חוסם → אימון
  נוסף → הבוס נופל → עולם 2 → קנייה והצטיידות → הסטטיסטיקות זזות → ייצוא →
  מחיקה → ייבוא → מצב זהה. בכל שלב נבדק ש‑`rebuildFromEvents(log)` שווה למצב החי.
* `plan` — התוכנית ללא UI: `resolveProgram(null) === PROGRAM`, דריסת מספרים,
  תרגילים מותאמים ופיצול ה‑XP שלהם (כולל הענקה רטרואקטיבית), קיפול
  last‑writer‑wins ב‑`(ts, id)` כולל שוויון חותמות, `data_cleared`, ולידציה,
  מיגרציה ל‑schema 3 וסובלנות לבלוב v2 ישן.
* `planEditor.dom` — העורך: רינדור, הוספה/הסרה/סידור מחדש, טופס התרגיל החדש,
  **אירוע `plan_updated` אחד בדיוק** לכל שמירה, איפוס, והתוכנית השמורה שמגיעה
  בפועל למסך האימון (כולל XP לחלק הגוף שנבחר).
* `sync.engine` — מנוע הסנכרון מול backend בזיכרון (`Map` + מונה `seq`), עם
  שעון וטיימרים מזויפים ו**אפס רשת**: outbox ששורד ריסטארט, קיבוץ הקשות
  (4 → 1, האחרון מנצח), מיזוג שמצייר מחדש ושומר על הטאב הנוכחי, קידום cursor
  ועימוד, התעלמות מאירועים מוכרים, שני מכשירים שמתכנסים, לוח ה‑backoff,
  התאוששות מ‑offline, `linkAccount` שמעלה את כל היומן, ו‑`stop()` שמוחק פנקס
  ולא נתונים.
* `account.dom` — כרטיס החשבון: אין כרטיס כשלא מוגדר, הנוסח בכל מצב (מחובר /
  מנותק / פג תוקף / אופליין), אישור לפני התנתקות, האזהרה על מחיקה מכל
  המכשירים, וייבוא **מצטבר** כשמחוברים מול הרסני כשמנותקים.
* `merge` — התכנסות האיחוד: שני כיוונים, סדר אקראי, כפילויות סמנטיות שמשלמות
  פעם אחת, `data_cleared` בתוך איחוד, ו**הנועל** שמונע ייבוא מחדש של הנתונים
  הישנים אחרי מחיקה + מיזוג.
* `e2e.sync` — **יום שלם, שני מכשירים, חשבון אחד**: אימון במרתף בלי קליטה →
  ריסטארט של הטאב באמצע (ה‑outbox וה‑cursor שורדים, ולא נדחף שום דבר פעמיים)
  → העלאה ומשיכה בסדר הפוך → קרבות שמוציאים אנרגיה בזמן שהמכשיר השני מתאמן →
  עריכת תוכנית פה ואחר כך שם (המאוחרת מנצחת בשני הצדדים) → ייבוא גיבוי ישן
  מצטבר → 🗑 מחיקה שמתפשטת לכל החשבון. בכל נקודת שקט נבדקים שלושה דברים:
  שני המכשירים מציגים אותו מצב, כל מכשיר שווה ל‑`rebuildFromEvents` של היומן
  שלו, וחוקי המשחק מתקיימים (אנרגיה ≥ 0 ואף מפתח הענקה לא שולם פעמיים).
* `app.dom` — השלד והניווט הדו‑שכבתי: תמיד **שלושה** טאבים ראשיים בכל מסך,
  גזירת המרכז מכל view id (כולל `PL` ומפתח יום זר), תת‑הטאבים של כל מרכז,
  זיכרון תת‑הטאב לכל מרכז, פיצול מרכז ההגדרות (כרטיסים ופעולות ב‑`ST`, יומן
  והיסטוריה ב‑`H`), התקנה ישנה שנשארה על `'H'`, ושורת תת‑טאבים שנגללת רק מעל
  ארבעה ימים.
* `*.dom` — בדיקות jsdom לשאר המסכים: טיימר, זירה (כולל עצירת הקרב במעבר
  תת‑טאב **ובמעבר מרכז**), קרב בוס, מגירות החנות, מדף הגביעים ותקינות ה‑SVG של
  כל פריט ציוד בארבעה גדלי דמות.
