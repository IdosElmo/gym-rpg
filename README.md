# Gym RPG 💪

אפליקציית אימוני היפרטרופיה (תוכנית של 1–7 ימים · ברירת מחדל A/B/C) בעברית,
RTL, **100% אופליין** —
עם שכבת משחק RPG מלאה שמתקדמת **רק** מאימונים אמיתיים.

> **סטטוס: הושלם.** כל מה שבמפרט קיים: מנוע XP ורמות לכל חלק גוף, דמות SVG
> שגדלה איתן, רצף שבועי, קרב אידל דטרמיניסטי, ארבעה עולמות עם **בוסי עולם
> ושערי אימון**, **חנות ציוד** במטבעות שמצטיירת על הדמות עם **שדרוגי פריטים
> (+1/+2/+3)**, **מגוון דמויות
> קוסמטי** (שני גופים חינם × חמישה מראים — כל מראה שנרכש נפתח בשני הגופים),
> **גביעים**, ומצב
> אלוף אינסופי אחרי זאוס — ומעליהם **תוכנית אימונים ניתנת לעריכה** ו**סנכרון
> ענן אופציונלי** עם חשבון Google.
>
> הסנכרון **כבוי כברירת מחדל**: כל עוד `src/sync/config.ts` ריק (וב‑`file://`
> תמיד) אין לקוח, אין מאזין ואין כרטיס חשבון — האפליקציה היא בדיוק האפליקציה
> האופליינית. ההפעלה היא ארבעה שלבים ידניים, ראו **"סנכרון בענן וחשבון
> Google"** למטה.

## מה יש כאן

הניווט הוא **שתי שכבות**: שורה ראשית של בדיוק **שלושה** טאבים קבועים (מרכזים),
ומתחתיה שורת תת‑טאבים של המרכז הפתוח. השורה הראשית לא נגללת ולא משנה סדר
לעולם; רק שורת תת‑הטאבים יכולה להיגלל, ורק כשתוכנית מגדירה יותר מארבעה ימי
אימון בשבוע. ראו **"ניווט דו‑שכבתי"** למטה.

| מרכז | תת‑טאבים | מה יש בו |
|---|---|---|
| 🏋️ **אימון** | טאב לכל **מופע אימון** בשבוע (`scheduleTabs`) | תיעוד סטים, ביצוע קודם, טיימר מנוחה צף עם צליל, `+XP חזה!` צף, מונה ⚡. כפתור ⚙️ בכותרת פותח את עורך התוכנית |
| 🎮 **קרב** | **קרב** · **דמות** | *קרב*: זירה מונפשת, **רצועת התקדמות בעולמות**, **כרטיס האתגר היומי** (🎲 גאונטלט אחד ליום, זהה לכולם), **כרטיס דו־קרב רפאים** (⚔️ קרב מול הדמות האמיתית של חשבון אחר — רק כשמחוברים), גלים, מיני‑בוסים, **קרבות בוסי עולם**, מד מהלך על, מטבעות, כרטיס שער הבוס. *דמות*: SVG שכבתי שגדל לפי הרמות, רמה ראשית, 6 פסי חלקי גוף, רצף, **בורר גוף** (🧔 גבר / 👩 אישה, חינם) + **רצועת מראים** קוסמטיים שמצטיירים על הגוף הנבחר, עם **תצוגה מקדימה** למראה נעול, **חנות ציוד**, **מדף גביעים** |
| ⚙️ **הגדרות** | **הגדרות** · **היסטוריה** · **📊 סטטיסטיקות** | *הגדרות*: **כרטיס החשבון** (התחברות, מצב סנכרון, ממתינים, **שם לוחם** לדו־קרב), כרטיס התוכנית + ⚙️, ייצוא/ייבוא/מחיקת JSON, **כרטיס 🛠 מצב מפתח** (רק בחשבון הבעלים — אצל כל אחד אחר הוא פשוט לא קיים), שורת מידע על האפליקציה. *היסטוריה*: **יומן הרפתקה** מיומן האירועים ו**האימונים המתועדים** — כל אחד בחלונית גלילה קבועת‑גובה משלו, והיומן כ**בועות תאריך** שנפתחות לפירוט האימון. *סטטיסטיקות*: **סה"כ הרמתם** (בפילים ובאוטובוסים), המספרים היבשים, **טונאז’ שבועי** ו**לוח אימונים** בגרפי SVG, איזון בין חלקי הגוף, שיאים לכל תרגיל, סיכום שכבת המשחק וכמה סטטיסטיקות מוזרות |
| ⚙️ **תוכנית** (`PL`) | — | ניהול ימי התוכנית (הוספה, שינוי שם, הסרה, סידור, שיבוץ לימי השבוע), ובתוך כל יום: סטים, חזרות, מנוחה, סדר, הסרה ותרגילים משלכם. גם **תוכניות מוכנות**. אינו טאב — שייך למרכז 🏋️ ונכנסים אליו מ‑⚙️ בכותרת האימון או מכרטיס התוכנית בהגדרות |

**הכלל הזהב:** אי אפשר להתקדם במשחק בלי אימון אמיתי. אנרגיה נצברת רק מסטים
מסומנים, ורמות חלקי גוף — שהן היחידות שפותחות בוסים — נצברות רק מ‑XP אמיתי.

## הרצה, בנייה ופריסה

דרישות: Node 22, npm 10.

```bash
npm install        # התקנת תלויות
npm run dev        # שרת פיתוח (Vite) — http://localhost:5173
npm run build      # בדיקת טיפוסים + בנייה ל-dist/index.html (קובץ יחיד)
npm run preview    # תצוגה מקדימה של ה-build
npm test           # Vitest
npm run typecheck  # tsc --noEmit
npm run verify     # מוודא ש-dist/index.html ללא הפניות חיצוניות
```

### קובץ יחיד (file://)

`vite-plugin-singlefile` מטמיע את כל ה‑JS וה‑CSS לתוך `dist/index.html`.
אפשר להעתיק את הקובץ הזה לטלפון/מחשב ולפתוח אותו ישירות — הכול עובד, כולל
הטיימר, הצליל וההיסטוריה. אין שום בקשת רשת, פונט חיצוני או CDN בזמן ריצה.

**`base: './'`** — מכיוון שהכול מוטמע, לא נשארות כתובות נכסים; ההפניות היחסיות
היחידות הן קבצי ה‑PWA (`manifest.webmanifest`, `sw.js`, `icon.svg`) שיושבים ליד
`index.html`. `base` יחסי עובד גם ב‑GitHub Project Pages (תחת `/gym-rpg/`) וגם
ב‑`file://`; `'/gym-rpg/'` היה שובר את `file://` ו‑`'/'` היה שובר את Pages.

### פריסה ל‑GitHub Pages

`.github/workflows/deploy.yml` רץ על כל push ל‑`main`:
typecheck → tests → build → verify → `configure-pages` → `upload-pages-artifact`
→ `deploy-pages`.

בהגדרות המאגר: **Settings → Pages → Source: GitHub Actions**.

### PWA

* `public/manifest.webmanifest` — התקנה למסך הבית (standalone, RTL, עברית).
* `public/sw.js` — Service Worker שמקדים‑מטמין (precache) את הקובץ הבנוי,
  cache‑first עם רענון ברקע ו‑fallback ל‑`index.html` בניווט.
* `public/icon.svg` — אייקון SVG (משקולת + דמות) על רקע `#121824`.
* רישום ה‑SW מוגן: הוא נרשם **רק** ב‑`http`/`https`, כך שגרסת הקובץ היחיד
  ב‑`file://` ממשיכה לעבוד.

## ניווט דו‑שכבתי

עד לגרסה הזו הייתה **שורה אחת שטוחה**: כל ימי האימון של השבוע ועוד דמות, קרב
והיסטוריה — שבעה טאבים לתוכנית A/B, וגלילה אופקית. שבעה דברים שנראים אותו דבר
בשורה אחת הם לא סרגל ניווט אלא רשימה: שום דבר לא אומר ש"רביעי" ו"היסטוריה" הם
**סוגים** שונים של יעד. לכן הסרגל התפצל לשתיים.

**שורה 1 — המרכזים (hubs).** בדיוק שלושה טאבים, רוחב שווה, ≥44px, בלי גלילה
ובלי סדר משתנה: 🏋️ אימון · 🎮 קרב · ⚙️ הגדרות. הפעיל צבוע במילוי `--accent`
המלא, המצב החזק ביותר באפליקציה, כי "באיזה חלק של האפליקציה אני" היא השאלה
שהסרגל חייב לענות עליה מיד.

**שורה 2 — תת‑הטאבים של המרכז הפתוח**, במשקל ויזואלי קל יותר בכוונה: גלולות
(`border-radius:99px`), `--card-2` במקום `--card`, ומצב פעיל **מתואר בקו** ולא
במילוי. אותם tokens, אותה שפה, דרגה אחת שקטה יותר — כדי שהעין תקרא "מרכז, ואז
בחירה בתוכו" ולא שתי שורות שמתחרות זו בזו.

| מרכז | תת‑טאבים | view ids |
|---|---|---|
| 🏋️ אימון | `scheduleTabs(program)` — מופע לכל אימון בשבוע | `A`, `d_alef`, `d_alef@3`… ובנוסף `PL` (שייך למרכז, בלי טאב) |
| 🎮 קרב | קרב · דמות | `BT`, `CH` |
| ⚙️ הגדרות | הגדרות · היסטוריה · 📊 סטטיסטיקות | `ST`, `H`, `SS` |

### המרכז נגזר מה‑view — אין שדה חדש ב‑state

אין `hub` ב‑`UiState`. `hubOf(view)` ב‑`src/ui/nav.ts` היא פונקציה **טוטלית**
מעל כל view id שהאפליקציה שמרה אי פעם: `BT`/`CH` → קרב, `ST`/`H`/`SS` → הגדרות, וכל
דבר אחר (כל מפתח יום, כולל מפתח שמכשיר אחר המציא, וגם `PL`) → אימון. זה מה
שהופך את השינוי לארגון מחדש של ה‑UI ולא למיגרציה: התקנה שנשארה על `'H'`, על
`'A'`, על `'d_alef@3'` או על `'CH'` נפתחת בדיוק על המסך ששמה — ועכשיו גם על
המרכז שהמסך הזה חי בו.

**`ST` היה ה‑view id היחיד שהניווט הדו‑שכבתי הוסיף** (הגדרות), כדי שאפשר יהיה
להבחין בין תת‑הטאבים של מרכז ההגדרות; **`SS`** (📊 סטטיסטיקות) הוא היחיד שמסך
הסטטיסטיקות הוסיף. שניהם נכנסים ל‑`RESERVED_VIEW_KEYS`, ולכן `normalizeUi`
מקבל אותם כמו את שאר המסכים השמורים, ו‑`'H'` — מה שכל גרסה קודמת שמרה — נשאר
תקף לחלוטין ומצביע על אותו מסך היסטוריה, בתוך מרכז ההגדרות. הכלל: view ids רק
**מתווספים**, אף פעם לא משנים משמעות — ולכן התקנה שנשארה על מסך ישן נפתחת אחרי
העדכון בדיוק על אותו מסך.

### זיכרון תת‑טאב לכל מרכז

`ui/app.ts` מחזיק **בזיכרון** את תת‑הטאב האחרון של כל מרכז, כך שמעבר למרכז אחר
וחזרה נוחת על מה שהיה פתוח שם ולא על ברירת המחדל. ברירות המחדל, כשעוד לא היה
כלום: אימון → הטאב של היום (`defaultTabView`), קרב → `BT` (הזירה), הגדרות →
`ST` (וגם `SS` נזכר כמו כל תת‑טאב אחר). עורך התוכנית (`PL`) **לא** נזכר: הוא מסך שנכנסים אליו מכפתור ויוצאים
ממנו ב‑←, ולכן חזרה למרכז אימון מחזירה לאימון שהיה פתוח ולא לתוך העורך.

מה ש**כן** נשמר לדיסק הוא `ui.view` כרגיל — כלומר המרכז שהייתם בו כשסגרתם את
האפליקציה, שהוא החלק שבאמת צריך לשרוד רענון.

### הקרב עוצר בכל יציאה מהזירה

`render()` קורא ל‑`stopBattle()` לפני כל מסך, ולכן הלולאה נעצרת גם במעבר
לתת‑הטאב **דמות** שלצידה וגם במעבר למרכז אחר לגמרי — שתי הדרכים החדשות לצאת
מהזירה. `visibilitychange` ממשיך לשמור על אותה הבטחה כשהטאב של הדפדפן מוסתר.

### מפתחות אחסון

| מפתח | תוכן |
|---|---|
| `gymrpg_state_v1` | תמונת מצב נוכחית (`AppState`) |
| `gymrpg_events_v1` | יומן אירועים append‑only |
| `gymrpg_device_v1` | מזהה **התקנה** (uuid) — מוטבע על כל אירוע שהמכשיר כותב |
| `gymrpg_sync_v1` | פנקס מנוע הסנכרון: `{v, deviceId, cursor, outbox: [id…], userId, lastSyncAt}`. **לא** נכנס לייצוא ו**שורד** מחיקה |

`game` הוא **מטמון**: אפשר לבנות אותו מחדש במלואו מיומן האירועים
(`rebuildGame`), ולכן בלוב לא מוכר פשוט נבנה מחדש במקום להישבר. זהו גם **נתיב
המיגרציה הרשמי** של הבלוב הזה: `normalizeGame` דוחה גרסה ישנה (v1/v2), ו‑
`ensureGameState` בונה אותה מחדש מהיומן — ללא אובדן, כי כל עובדה היא אירוע.

משקלים וחזרות נשמרים כמחרוזות, בדיוק כמו במקור. חורים במערך הסטים נשמרים
כ‑`null` כדי לשמר את המבנה הישן במדויק.

### יומן אירועים (append‑only)

כל פעולה משמעותית נרשמת כאירוע
`{ id: uuid, ts: epochMs, type, payload, device? }` ונשמרת לצד תמונת המצב. זה מה
שמאפשר את הסנכרון בין מכשירים בלי לכתוב מחדש שורה אחת של UI: **סנכרון = איחוד
קבוצות האירועים + replay**.

| סוג | נרשם מתי |
|---|---|
| `set_logged` | הוקלד משקל/חזרות |
| `set_completed` / `set_uncompleted` | סומן/בוטל סימון של סט |
| `workout_finished` | כל הסטים של כל התרגילים ביום סומנו (פעם אחת ליום) |
| `legacy_import` | סיכום ייבוא `hyp3_data_v1` |
| `session_imported` | אימון היסטורי שיובא — כולל כל הסטים, עם `ts` של תאריך האימון |
| `data_imported` / `data_cleared` | ייבוא קובץ JSON / מחיקת הכול |
| `xp_gained` | כל הענקת XP — כולל הפיצול לחלקי גוף, `volume`, `factor`, `pr`, `retro` |
| `energy_gained` | אנרגיית קרב (10 לסט, 50 לסיום אימון) — נושא `key` למניעת תשלום כפול |
| `pr_achieved` | שיא אישי חדש בתרגיל |
| `level_up` / `streak_changed` | אינפורמטיביים (הרמה והדרגה **נגזרות**, ראו למטה) |
| `wave_cleared` | גל שנוצח — `{world, wave, miniBoss, enemyId, coins, energySpent, seed, durationMs}` |
| `boss_defeated` | בוס עולם הופל — `{world, wave, bossId, coins, energySpent, seed, durationMs, nextWorld, nextWave, endgame}` |
| `coins_spent` | רכישה בחנות — `{itemId, slot, cost}` (מוריד מטבעות ומוסיף ל‑`owned`) |
| `item_equipped` | הצטיידות/הסרה — `{slot, itemId \| null}` |
| `item_upgraded` | שדרוג פריט בדרגה אחת — `{itemId, slot, toLevel, cost}`. המטען **סמכותי**: הוא נושא את הדרגה שאליה מגיעים ואת המחיר שנגבה בפועל. ה‑reducer מחיל אותו **רק** כש‑`upgrades[itemId] < toLevel`, ומחייב את `cost` **רק** כשהוא מוחל — ראו "שדרוגי ציוד" למטה |
| `daily_challenge` | ריצה אחת של האתגר היומי — `{date, seed, score, wavesCleared, tiebreak, coins, energySpent, complete, outcome, durationMs}`. **אירוע יחיד לריצה**, נכתב כשהיא נגמרת (ניצחון · נוק‑אאוט · ויתור). ה‑`date` הוא **מפתח האידמפוטנטיות**: ה‑reducer מחיל אותו רק כש‑`daily.runs[date]` ריק, ולכן שני מכשירים ששיחקו את אותו יום אופליין מתכנסים לניסיון אחד ולתשלום אחד — ראו "אתגר יומי" למטה |
| `character_purchased` | נקנה **מראה** קוסמטי — `{characterId, cost}`, כשה‑`characterId` הוא מזהה מראה (`"robot"`). מוריד מטבעות ומוסיף ל‑`characters.owned` — **בשני הגופים בבת אחת**; אידמפוטנטי לפי מזהה המראה |
| `character_selected` | הוחלף הצירוף גוף × מראה — `{characterId}` (`"robot_f"`). **האירוע היחיד** גם להחלפת מראה וגם להחלפת גוף, כי משחקים תמיד צירוף אחד בדיוק. LWW לפי הסדר `(ts, id)`; מזהה ישן (`"robot"`) מתורגם לצירוף, ומזהה לא מוכר או שלא בבעלות **מתעלמים** ממנו |
| `ghost_duel` | דו־קרב אחד — ראו "דו־קרב רפאים" למטה |
| `coins_granted` | מטבעות שלא הגיעו מקרב — היום רק **הענקת מפתח** — `{amount, key, source:'dev', dev:true}`. ה‑`key` **חובה**: בלעדיו אין אידמפוטנטיות, ולכן הענקה בלי מפתח לא משלמת כלום |
| `dev_reset` | פתיחה מחדש של יומן היום — `{date, scope:'daily'\|'duels', cycle, dev:true}`. `cycle` הוא **קו‑שיא** (האידיום של `item_upgraded`), כך ששני מכשירים שאיפסו פותחים מחזור אחד |
| `dev_purge` | ביטול **כל** הענקות המפתח שלפניו בסדר `(ts, id)` — `{date, dev:true}`. עובד בהשמטה: `liveEvents` לא מקפל אותן בכלל, ולכן התוצאה זהה ליומן שלא היו בו — ראו "מצב מפתח" למטה |
| `plan_updated` | תוכנית נשמרה — `{plan: PlanDoc \| null, revision, date}`. המסמך **כולו** במטען. מנורמל בכל קיפול, כך שמטען v1 של לקוח ישן מוסב ל‑v2 בקריאה. גם **יעד הרצף השבועי** נגזר ממנו |
| `data_merged` | סמן מיזוג — `{source: "json_import", added}`. נכתב **רק** בייבוא JSON מצטבר (כשמחוברים). אינו משנה מצב; קיים כדי שיומן ההרפתקה יסביר קפיצה ב‑XP. משיכה מהענן **אינה** כותבת אותו בכוונה — סמן לכל משיכה היה מתפנג‑פונג בין המכשירים לנצח |

**מטען סמכותי (authoritative payload):** `boss_defeated` נושא את `nextWorld`/
`nextWave` ולא רק את מזהה הבוס. כך ה‑reducer לא צריך *לגזור* מחדש את חוק
הפתיחה, ויומן ישן ימשיך להשתחזר זהה גם אם החוק ישתנה בעתיד.

**גרעיניות אירועי הקרב:** מכה בודדת **אינה** אירוע. הקרב דטרמיניסטי לפי הזרע,
ולכן די באירוע אחד לכל גל שנוצח — הוא נושא את הזרע, את המטבעות ואת האנרגיה
שנגבתה, וזה כל מה שצריך כדי לשחזר את ההתקדמות ב‑`rebuildFromEvents`.

`rebuildFromEvents(events)` בונה מחדש את המצב מהיומן בלבד (דטרמיניסטי, ממוין
לפי `(ts, id)`), כולל `state.game` דרך `rebuildGame`. האפליקציה החיה וה‑replay
מריצים **בדיוק את אותו reducer על אותם אירועים** — יש בדיקות שמוכיחות שהתוצאה
זהה.

**בטיחות מיזוג (merge-safety).** הסדר נקבע לפי `(ts, id)` ולכן הוא תכונה של
*קבוצת* האירועים ולא של סדר ההגעה: שני מכשירים שמחזיקים את אותם אירועים יקפלו
אותם לאותו מצב בדיוק. בנוסף, ה‑reducer **אידמפוטנטי לפי מפתח סמנטי** — אותה
הענקה משני מכשירים (uuid שונה, אותה משמעות) משלמת פעם אחת בלבד: `granted`
לסטים, `bonusDays` לבונוס היומי, `prKeys` לשיאים, `energyGranted` לאנרגיה
ו‑`devKeys` להענקות מצב המפתח. כל
מכשיר גם מוטבע ב‑`device` ומחתים חותמות זמן **עולות ממש**, כך שאפילו שעון
שקופץ אחורה לא הופך את סדר האירועים של אותו מכשיר. `tests/merge.test.ts` מוכיח
את ההתכנסות, ו‑`tests/e2e.sync.test.ts` מריץ את כולה מקצה לקצה על שני מכשירים
אמיתיים מול backend בזיכרון.

**מה *לא* מתקפל מהיומן.** שלושה שדות שייכים ל**התקנה** ולא לחשבון, ולכן
`storage/merge.ts` מעביר אותם מהמצב החי אל התוצאה במקום לשחזר אותם: `ui`
(באיזה טאב אתם), `meta.createdAt` (מתי ההתקנה הזאת נוצרה) ו‑`meta.legacyImported`
(האם המכשיר הזה כבר סרק את `hyp3_data_v1`). האחרון הוא **נועל**: replay של יומן
שנמחק אינו יכול לדעת עליו, ובלעדיו מחיקה + משיכה + רענון היו מייבאים מחדש את
הנתונים הישנים — ומחזירים לחשבון בדיוק את מה שנמחק.

### מיגרציה מהאפליקציה הישנה

בטעינה הראשונה, אם קיים `hyp3_data_v1`, הוא מיובא **ללא אובדן**: כל תאריך, אות
יום, מזהה תרגיל, סט (כולל חורים), משקל, חזרות ודגל `done`. במקביל נוצר אירוע
`session_imported` לכל אימון עם כל נתוני הסטים ו‑`ts` של תאריך האימון — כך
ש‑Phase 1 יוכל להעניק XP רטרואקטיבי פשוט על ידי replay של היומן, בסדר כרונולוגי.
המפתחות הישנים נשמרים כרשת ביטחון.

### ייצוא / ייבוא JSON

לכל תרגיל נוסף שדה `bodyPart` (`chest`/`back`/`legs`/`shoulders`/`arms`/`core`),

## שכבת המשחק (Phase 1)

### חוקי XP (`core/xp.ts` — פונקציות טהורות + בדיקות)

| כלל | נוסחה |
|---|---|
| סיום סט | `10 × volumeFactor` |
| `volumeFactor` | `clamp((משקל×חזרות) / השיא הקודם, 0.5, 1.5)` — 1 כשאין עם מה להשוות |
| נפח לתרגילי משקל גוף/שניות | החזרות או השניות עצמן |
| שיא אישי חדש | `×2` XP + אירוע `pr_achieved` + toast חגיגי |
| סיום כל הסטים של כל התרגילים ביום | `+50` XP **לכל** חלק גוף + `+50` אנרגיית קרב |
| עקומת רמות | `xpForLevel(n) = 100 × 1.35^(n−1)` |
| רמת הדמות | `floor(ממוצע ששת רמות חלקי הגוף)` |
| אנרגיית קרב | `+10` לכל סט, `+50` לסיום אימון (נצברת ל‑Phase 2) |

הסט הראשון אי פעם בתרגיל **קובע** את השיא ולא נחשב שיא חדש (אין עם מה להשוות).

### רצף שבועי (Sun–Sat)

`weeklyTarget` ימי אימון **שונים** בשבוע קלנדרי = "שבוע מושלם" → דרגה +1, בונוס
קבוע ומצטבר של `+10%` לכל הסטטיסטיקות. שבוע **סגור** שלא הגיע ליעד מוריד דרגה
אחת (רצפה 0). השבוע הנוכחי לעולם לא נשפט, ורמות/XP לעולם לא נלקחות.
הדרגה נגזרת מ‑`workoutDays` + התאריך של היום, ולכן שבוע שחלף מתעדכן גם בלי
פעולה של המשתמש (`refreshStreak` רץ בכל עלייה של האפליקציה).

**היעד מגיע מהתוכנית, והתוכנית מגיעה מהיומן.** בלי תוכנית היעד הוא 3 (התוכנית
המובנית); תוכנית של 4 אימונים בשבוע דורשת 4. בעורך היעד **נגזר משיבוץ ימי
השבוע** ולא מוקלד ידנית (`deriveWeeklyTarget` — ראו "היעד השבועי נגזר מהשיבוץ"). שבוע שכבר נסגר נשפט מול היעד שהיה
פעיל **באותו שבוע**: `weeklyTargetsFromEvents` מקפל את אירועי `plan_updated`
(ו‑`data_cleared`, שמחזיר ל‑3) לציר זמן של יעדים, ו‑`weeklyTargetForWeek` שואל
אותו לפי הרגע שבו השבוע נסגר. כיוון שהציר הזה נגזר מ**קבוצת** האירועים בסדר
`(ts, id)`, הרצף החי (`refreshStreak`, `commit`) והרצף שנבנה מחדש
(`rebuildGame`) תמיד מסכימים — גם אחרי מיזוג בין שני מכשירים.

### מניעת "חקלאות XP"

XP ואנרגיה מוענקים **פעם אחת לכל (תאריך, תרגיל, מספר סט)** — המפתח נשמר ב‑
`game.granted`. ביטול סימון של סט **לא** מחזיר XP, וסימון חוזר **לא** מעניק שוב.
כך כפתור ה‑✓ לא יכול לשמש כברז XP, ובלי לקנוס משתמש שתיקן טעות.
אותו רעיון לבונוס סיום האימון, שנשמר פעם אחת ליום ב‑`game.bonusDays`.

### XP רטרואקטיבי (`ensureGameState` ב‑`migrate.ts`)

בכל טעינה שבה `state.game` חסר או מגרסה לא מוכרת, ההיסטוריה הקיימת מקבלת XP:

1. ייבוא `hyp3_data_v1` שקרה עכשיו (אירועי `session_imported`);
2. משתמש שכבר ייבא ב‑Phase 0 (`legacyImported === true`, `game === null`);
3. אימונים שתועדו חי תחת Phase 0 (אירועי סטים בלי XP);
4. מצב עם אימונים אבל בלי יומן — האימונים "משוחזרים" כאירועי
   `session_imported` עם `source: "recovered"` לפני חישוב ה‑XP.

ההענקות עצמן נכתבות כאירועים ליומן (עם `ts` של תאריך האימון), כך שהמצב נשאר
פונקציה טהורה של היומן. הענקות רטרואקטיביות מסומנות `retro: true`:
הן משלמות XP ושיאים, אבל **לא** אנרגיית קרב ו**לא** ימי רצף — הרצף מתחיל מ‑0,
כפי שדורש המפרט. הפעולה אידמפוטנטית: הרצה שנייה לא מעניקה כלום.

### מסך הדמות (`דמות`)

* **SVG שכבתי** שהפרופורציות שלו נגזרות מרמות חלקי הגוף: חזה מרחיב את פלג הגוף
  העליון, גב מוסיף "כנפיים" (lats), כתפיים מרחיבות את מוטת הכתפיים והדלתות,
  ידיים מעבות את הזרועות, רגליים מעבות ירכיים ושוקיים, וליבה **מצרה** את המותן
  ומחדדת את שרירי הבטן. הגדילה חסומה (`BALANCE.character.visualMaxLevel`) כדי
  שהדמות תישאר מצוירת ומחויכת ולא מפלצתית.
* עלייה ברמה = הבהוב/פעימה קצרה על החלק שגדל (מכובד `prefers-reduced-motion`).
* לכל קבוצה יש `data-part`, ולכל מגירת ציוד יש `data-slot` (`gloves`/`belt`/
  `shoes`/`cape`) שמתמלאת מ‑`characterAnchors()` — ראו "הציוד על הדמות".
* **גוף** (`geometry`) ו**מראה** (`palette` + `decor` + `hair`) מגיעים מהצירוף
  הנבחר (`data/characters.ts`) — ראו "מגוון הדמויות". שתי הגיאומטריות קוראות את
  אותן שש הרמות ומחזיקות את אותן נקודות עיגון לציוד, ולכן כל מראה וכל פריט ציוד
  מתאימים לשניהם.
* במסך: רמה ראשית, שישה פסי התקדמות (חזה, גב, רגליים, כתפיים, ידיים, ליבה),
  **בורר הגוף + רצועת המראים**, סטטיסטיקות לחימה נגזרות, דרגת רצף, חנות הציוד
  ומדף הגביעים.

### מסך האימון

`+XP חזה!` צף מעל כפתור ה‑✓ בכל סימון סט (אחד לכל חלק גוף שקיבל XP), מונה
אנרגיה שקט בפינת הכותרת, ו‑toast חגיגי לשיא אישי ולעליית רמה.

## מצב קרב (Phase 2)

### הלולאה

`core/combat.ts` הוא **טהור**: אין בו DOM, אין `Date.now()` ואין `Math.random()`.
ה‑UI מזין אותו בזמן שעבר ומצייר את מה שהוא מחזיר.

| חלק גוף | סטטיסטיקה | תפקיד בקרב |
|---|---|---|
| חזה | ATK | `damage = ATK × (1 ± 10%)` |
| ידיים | סיכוי/מכפיל קריטי | מכה קריטית |
| כתפיים | `attackIntervalMs` | תדירות ההתקפה האוטומטית |
| גב | DEF | נזק נכנס מוכפל ב‑`defK / (defK + DEF)` (רך, לעולם לא 0) |
| רגליים | Max HP | כמה מכות סופגים |
| ליבה | Regen | ריפוי לשנייה תוך כדי הקרב |

### דטרמיניזם

* PRNG מזורע (mulberry32) — הזרע נשמר באירוע של כל גל שנוצח.
* **צעד זמן קבוע** (`BALANCE.combat.tickMs = 50ms`): `advance()` צובר זמן אמיתי
  ומריץ רק טיקים שלמים, כך שקצב הפריימים לא משנה את התוצאה.
* **זרע לכל גל**: `waveSeed(seed, world, wave, attempt)` — אפשר לשחזר גל בודד
  בבדיקה, וניסיון חוזר אחרי נוק‑אאוט אינו שחזור מדויק של הקרב שהפסדתם.
* `advance()` חוסם "צבירת זמן" מלשונית שהייתה מוסתרת (תקרה של שנייה) — אין
  רווחים אופליין: הקרב רץ רק כשלשונית הקרב פתוחה וגלויה.

### כלכלת אנרגיה

* אנרגיה נצברת **רק** מאימון אמיתי: `+10` לסט, `+50` לסיום אימון.
* גל עולה `10` ⚡ ונגבה בסיום הגל — **נוק‑אאוט לא עולה אנרגיה**, רק זמן.
* אימון מלא ≈ `207` ⚡ ≈ **20 גלים** (היעד במפרט: 15–25).
* באפס אנרגיה הקרב נעצר עם הודעה בעברית: "אין מספיק אנרגיה — הדמות נחה.
  לכו להתאמן!" ומתחדש ברגע שסט חדש מסומן.

### גלים, מיני‑בוסים ושערי בוס

* `50` גלים בעולם, מיני‑בוס בכל גל עשירי (הפי `×2.2` HP, `×1.25` ATK).
* מטבעות: `(5 + 1×(גל−1)) × 1.6^(עולם−1)`, ומיני‑בוס משלם `×4`.
* HP/ATK של אויב: `32 × 1.045^(גל−1) × 1.6^(עולם−1)` ו‑`6 × 1.03^(גל−1) × 1.25^(עולם−1)`.
* אחרי הגל האחרון בעולם עומד **בוס העולם** — ראו הפרק הבא.

### רוסטר האויבים — שישה בכל עולם

לכל עולם **שישה אויבים רגילים** (היו שלושה) ועוד המיני‑בוס שלו, כולם ספרייטים
מוטמעים (`viewBox 0 0 120 120`, ללא קובץ וללא רשת) בתמת העולם:

| עולם | האויבים הרגילים |
|---|---|
| 🏚 חדר כושר נטוש | משקולת חלודה · חולדת מחסן · מגבת רפאים · **הליכון משתולל** · **שק חול קרוע** · **קטלבל נוקם** |
| 🌆 הרחוב | כלב רחוב · פח מתגלגל · רוכב סקייטבורד · **חתול סמטאות** · **הידרנט מתפוצץ** · **סדרן מועדון** |
| 🏟 הזירה | גלדיאטור מתחיל · אריה הזירה · לוחם מגן · **לוחם הרשת** · **שור הזירה** · **קשתית הזירה** |
| ⛰ הר האולימפוס | הרפייה · גולם שיש · קיקלופ · **סירנה** · **הידרה** · **מינוטאורוס** |

**טעם, לא איזון.** לאויב יש בדיוק שני כפתורים — `hpMult` ו‑`atkMult` — והם
יושבים *מעל* עקומת הגלים ב‑`balance.ts`, שנשארת הסמכות. שלושה ארכיטיפים חוזרים
בכל עולם כדי שהאוצר מילים יהיה נלמד: **זריז** (מעט HP, מכה חזק), **עמיד** (הרבה
HP, מכה חלש) ו**מוחץ** (באמצע). הממוצע של שישה האויבים בכל עולם הוא ≈1.0 בשני
הכפתורים, כך שלאורך סבב אחד הטעמים מתקזזים; `tests/enemies.test.ts` מוודא שסך
ה‑HP של עולם שלם לא זז ביותר מ‑5% מהעקומה הטהורה, ושדמות ברמה 6 עדיין מנקה 24
גלים בלי תבוסה אחת.

#### למה הגדלת הרוסטר לא שוברת replay

הבחירה היא `roster[(גל − 1) mod אורך הרוסטר]`, ולכן היא **כן** משתנה כשהרוסטר
גדל: גל 4 פעם חזר לאויב הראשון והיום פוגש את הרביעי (שלושת הראשונים נשארו
בראש הרשימה, אז גלים 1–3 לא זזו). זה בטוח, ובכוונה:

* שום דבר במצב השמור לא נגזר מחדש מהפונקציה הזאת. ה‑payload של `wave_cleared`
  נושא `enemyId` כ**נתון**, וה‑reducer ב‑`core/xp.ts` קורא רק
  `world`/`wave`/`miniBoss`/`coins`/`energySpent`. קרבות גלים **לא מסומלצים
  מחדש** ב‑replay, ולכן `rebuildFromEvents` על יומן ישן מחזיר בדיוק את אותו מצב
  לפני ואחרי (יש על זה בדיקה ייעודית עם יומן שנכתב בגרסת שלושת האויבים).
* המטבעות מעולם לא היו תלויים באויב (גל, עולם ודגל המיני‑בוס קובעים אותם).
* `waveSeed()` מערבב זרע/עולם/גל/ניסיון בלבד — לא את הרוסטר — כך שזרע שנרשם
  עדיין משחזר את אותו זרם RNG.

מה שכן משתנה הוא **הקרב שלפנינו**: מגל 4 והלאה ספרייט אחר עם כפל טעם אחר. זה
תוכן, לא היסטוריה.

### הקשות ומהלך על

הקשה על האויב = מכה נוספת (`0.22 × ATK`) + טעינת מד מהלך העל (6% להקשה).
קצב ההקשות חסום ב‑`160ms` **בליבה** (לא רק ב‑UI), כדי שמאקרו לא ינצח שחקן.
מד מלא = מכה של `6 × ATK` + רעידת מסך (מבוטלת ב‑`prefers-reduced-motion`).

### מסך הקרב (`קרב`)

זירה עם הדמות (אותו בונה SVG, בקנה מידה קטן) מול ספרייט האויב, פסי חיים לשני
הצדדים, מספרי נזק צפים, פס אנרגיה, מונה גלים, מד מהלך על, שם העולם, **רצועת
העולמות** וכרטיס שער הבוס. כל הטקסטים בעברית, RTL, יעדי מגע ≥ 40px.

### רצועת ההתקדמות בעולמות

שורה אחת מתחת לשורת העולם, מעל הזירה: ארבעה צמתים — אייקון, שם עברי, ומצב.
היא עונה על שלוש שאלות שקודם דרשו גלילה: איפה אני במסע, כמה נשאר בעולם הזה,
והאם הבוס בסופו כבר פתוח.

| סמל | מצב |
|---|---|
| 🏆 | הבוס של העולם הזה כבר גביע |
| ✓ | העולם הנוכחי — שער הבוס מולא, הקרב יתחיל מעצמו |
| 🔒 | נעול: עולם עתידי, או שער שעדיין מבקש אימון |
| 👑 | מצב אלוף — זאוס נפל והגלים ממשיכים בלי סוף |

הצומת הנוכחי נושא גם `גל 23/50` ופס התקדמות דק (במצב אלוף פשוט `גל 73`, בלי
מכנה). **הקשה** על כל צומת מסבירה אותו בעברית ב‑toast; הקשה על הצומת הנוכחי
גם גוללת אל **כרטיס שער הבוס** הקיים, שכבר מפרט מה מולא ומה חסר — הרצועה לא
משכפלת את הרשימה הזאת, היא מפנה אליה. `grid` של ארבע עמודות ב‑RTL מציב את עולם
1 בימין, כך שהמסלול נקרא לכיוון שהעברית נקראת בו.

### יומן הרפתקה (במסך ההיסטוריה)

`ui/feed.ts` מקרין את יומן האירועים לשורות קצרות: עליות רמה, שיאים אישיים,
סיום אימון, שינויי רצף, גלים, **בוסי עולם**, **רכישות בחנות**, **שדרוגי ציוד**, הצטיידות
ו**ייבוא נתונים מקובץ** (`⬆ יובאו נתונים מקובץ (N אירועים)` — הסמן
`data_merged`, כדי שקפיצה פתאומית ב‑XP תקבל הסבר).
רצף של גלים רגילים **מתכווץ לשורה אחת** ("גלים 5–24 בחדר כושר נטוש · +180 🪙"),
ואילו מיני‑בוסים, בוסי עולם ופעולות חנות תמיד מקבלים שורה משלהם.

### שתי חלוניות, לא עמוד אחד ארוך

שני הרישומים שבמסך ההיסטוריה היו רשימות באורך מלא, ואחרי שלושה חודשי אימון
העמוד נמתח למטרים: יומן ההרפתקה דחף את יומן האימונים מטה, ו"מה הרמתי ב‑4
בחודש" דרש גלילה מעל כל מה שחדש יותר. עכשיו לכל רישום **חלונית גלילה משלו**
(`.scroll-pane`, `styles/history.css`) בגובה `min(40vh,320px)` ליומן ההרפתקה
ו‑`min(44vh,360px)` ליומן האימונים — הכותרות נשארות על המסך, והעמוד עצמו כמעט
לא זז. הרמז לקצוות הוא **מסכה** (`mask-image`) ולא גרדיאנט צבוע, כך שאותה
חלונית עובדת גם מעל `--card` (בתוך כרטיס) וגם מעל `--bg`, בלי לקבע צבע.

ויומן האימונים כבר אינו רשימה: הוא **שורת בועות תאריך** נגללת, החדשה ביותר
ראשונה (ב‑RTL — הפינה הימנית העליונה). כל בועה היא כפתור ≥44px עם התאריך
(`12.8`) ותווית היום המקוצרת (`אימון A` → `A`); ליום שהושלם במלואו יש ✓ ירוק
בפינה. **הקשה פותחת** מתחת לשורה בדיוק את כרטיס ה‑`.hist-day` שהמסך תמיד צייר —
שם האימון, וכל תרגיל עם הסטים שתועדו. הקשה נוספת סוגרת, הקשה על בועה אחרת
מחליפה, ופתוחה תמיד **אחת בלבד**: זה מסך של *חיפוש* ("ה‑4 בחודש"), לא של סיפור.
איזו בועה פתוחה הוא משתנה בזיכרון בלבד (`openDate` ב‑`ui/history.ts`) — לא
נשמר, אינו אירוע, ורנדור מלא של המסך מתחיל סגור; הקשה מעדכנת את הבועות ואת
הפאנל **במקום**, כך שהחלונית שומרת על מיקום הגלילה שלה.

## בוסי עולם, ציוד וגביעים (Phase 3)

### שערי הבוסים

בסוף כל עולם (אחרי גל 50) עומד בוס עם **דרישות רמות לחלקי גוף**. אם הן לא
מולאו, הקרב פשוט לא מתחיל: המסך עובר למצב `gated` ואומר בעברית בדיוק מה חסר
(`חסר לכם: חזה רמה 3 · רגליים רמה 3`). ברגע שרמה עולה — גם באמצע סשן פתוח —
השער נפתח מעצמו והקרב מתחיל (`setGate` נקרא בכל פריים).

| עולם | בוס | דרישות |
|---|---|---|
| 1 · חדר כושר נטוש | **מאמן הצללים** | חזה 3 · ידיים 3 · רגליים 3 |
| 2 · הרחוב | **שליט הרחוב** | חזה 5 · גב 5 · ידיים 5 |
| 3 · הזירה | **אלוף האלופים** | גב 7 · ליבה 7 · רגליים 6 · כתפיים 6 |
| 4 · הר האולימפוס | **זאוס** | כל ששת חלקי הגוף ברמה 8 |

**איך המספרים נבחרו.** שתי עקומות בלתי תלויות הוצלבו בסימולציה מול המנוע האמיתי:

1. **קושי** — באיזו רמה גל 50 של עולם N ניתן לניצחון (עם הקשות): ‎3 / 5 / 7 / 9.
2. **קצב אימון** — כמה אימונים לוקח למתאמן 3×בשבוע להגיע לרמה: ‎4 / 9 / 19 / 36.

כל שער הוצב על הרמה שהשחקן צריך ממילא, כך שהוא נסגר בערך אימון אחד אחרי
שנגמרים לו הגלים — מבקש **אימון**, לא גרינד. כדי שזה יסתדר, גם מכפילי העולם של
Phase 2 כווננו מחדש (‎`4×`/`2.2×` → `1.6×`/`1.25×`): המספרים הישנים הפכו את
עולמות 3–4 לבלתי‑ניתנים להשגה בכל רמה שמתאמן אמיתי יכול להגיע אליה, מה שהיה
הופך את בוסי העולם לקישוט. הפירוט המלא בהערה בראש `core/balance.ts`.

### קרב הבוס

הבוס הוא **ספוג** עם מכות כבדות ואיטיות (`2400ms` בין מכות): גל רגיל נגמר
בשניות ספורות, בוס לוקח כ‑‎26 / 33 / 43 / 60 שניות של משחק פעיל לדמות שרק בדיוק
עומדת בשער — **בלי ציוד כלל**. יש בדיקה שמוודאת בדיוק את זה לכל ארבעת הבוסים.

* HP/ATK: עקומת הגלים בגל `51` כפול `hpMult`/`atkMult` של הבוס.
* עלות: `30` ⚡ (שלושה גלים), נגבית רק בניצחון.
* פרס: `400 × 1.7^(עולם−1)` 🪙 — ‎400 / 680 / 1156 / 1965.
* ניצחון → אירוע `boss_defeated` → העולם הבא נפתח (`wave` חוזר ל‑1) + **גביע**.

### מצב אלוף (endgame)

אחרי **זאוס** אין עולם חמישי, ולכן ההחלטה: הדמות **נשארת בעולם 4** ומונה הגלים
פשוט ממשיך מעבר ל‑50, עם אותה עקומת התחזקות. כל גל נוסף הוא שיא אישי חדש,
כרטיס הבוס הופך לבאנר "👑 מצב אלוף", והגביע הרביעי יושב במדף. זה שומר על
המשחק פתוח בלי להמציא תוכן שאי אפשר לאזן.

טכנית: `bossStanding(world, wave, defeated)` מחזיר `false` כשהבוס כבר גביע, ולכן
`spawn()` פשוט ממשיך להוציא אויבים רגילים; `isEndgame(defeated)` הוא מה שה‑UI
בודק.

### חנות הציוד

**איפה:** במסך 🦸 **דמות**, לא בזירה — קנייה משנה מיד את ציור הדמות ואת טבלת
הסטטיסטיקות שכרטיס אחד מעליה, כך שסיבה ותוצאה נשארות על אותו מסך. הזירה נשארת
מסך חד‑מטרה שאפשר להפעיל ביד אחת באמצע אימון.

ארבעה מגירות (כפפות · חגורה · נעליים · גלימה), שלוש דרגות בכל אחת:

| מגירה | דרגה 1 | דרגה 2 | דרגה 3 |
|---|---|---|---|
| 🥊 כפפות (התקפה/קריטי) | כפפות אימון · 120 🪙 | כפפות עור · 520 🪙 | כפפות האלופים · 1900 🪙 |
| 🎗 חגורה (הגנה/חיים) | חגורת בד · 120 🪙 | חגורת כוח · 560 🪙 | חגורת אלוף עולם · 2000 🪙 |
| 👟 נעליים (מהירות/חיים) | נעלי ריצה · 140 🪙 | נעלי הרמה · 620 🪙 | כנפי הרמס · 2200 🪙 |
| 🧣 גלימה (התאוששות/הכול) | מגבת אימון · 150 🪙 | גלימת הרחוב · 700 🪙 | גלימת האולימפוס · 2400 🪙 |

**תמחור:** חמישים הגלים של עולם 1 משלמים ≈`1800` 🪙 ועוד `400` מהבוס, וכל עולם
מכפיל את התשלום ב‑`1.6`. לכן דרגה 1 בהישג יד בעולם הראשון, דרגה 2 סביב הבוס
שלו, ודרגה 3 במהלך עולמות 2–3.

**איך הבונוס נכנס לסטטיסטיקות:** `deriveStats(parts, streakTier, bonus)` מחבר את
הבונוס לערך שנגזר מהרמה **ואז** מכפיל בבונוס הרצף — כך ציוד ורצף מתחברים, אבל
איבר הרמה תמיד דומיננטי. הציוד לעולם לא "נושא" דמות לא מאומנת.

**כללים (טהורים, ב‑`core/xp.ts`):** אי אפשר לקנות פעמיים, אי אפשר לקנות בלי
מטבעות (הכיס נבדק **לפני** שנכתב משהו — רכישה שנדחתה לא משאירה זכר ביומן),
ואי אפשר להצטייד בפריט שלא נקנה או במגירה הלא נכונה.

### שדרוגי ציוד (+1 · +2 · +3)

**מה זה:** ציר שני של כוח, **מעל** הפריטים שכבר בבעלותכם. כל פריט (בכל דרגה)
ניתן לשדרוג עד `+3`; כל דרגת שדרוג מכפילה את **הבונוס של הפריט עצמו** ומוסיפה
לו נצנוץ, זוהר וכוכב על הדמות. השדרוג נקנה במטבעות, בכפתור `⬆ שדרוג` שנמצא
בשורת הפריט בחנות (רק לפריטים שבבעלותכם).

**שני עקומים, שניהם יחסיים לפריט** (`BALANCE.upgrades`, ו‑`core/upgrades.ts`
הוא כל החשבון):

| דרגה | עלות מצטברת (מתוך מחיר הפריט) | מחיר הצעד | מכפיל הבונוס |
|---|---|---|---|
| +1 | 60% | 60% | ×1.25 |
| +2 | 120% | 60% | ×1.5 |
| +3 | 200% | 80% | ×1.8 |

מפני שהעקום יחסי, כלל אחד מתמחר ומחזק את כל שנים־עשר הפריטים, ופריט שלוש־עשרה
לא ידרוש אף מספר חדש. דוגמאות: `כפפות אימון` (120 🪙) עולות 72/72/96 🪙 לשדרוג —
240 🪙 לכל הדרך, ו‑`+4 התקפה` הופך ל‑`+7.2`; `גלימת האולימפוס` (2400 🪙) דורשת
4800 🪙 נוספים ל‑`+3` — בור מטבעות אמיתי לסוף המשחק.

**האיזון — למה שני המסלולים מעניינים.** קניית הדרגה (tier) הבאה היא **קפיצה
אחת גדולה**: פי ≈2.5–3 בבונוס תמורת פי ≈4 במחיר. שדרוג הוא **אותו ערך למטבע,
בצעדים קטנים** על ציוד שכבר יש לכם. לכן פריט דרגה 1 ב‑`+3` נוחת **בין** דרגה 1
לדרגה 2 בכוח, ועולה בסך הכול **פחות** מדרגה 2 — יחס שנעול בבדיקה
(`tests/upgrades.test.ts`, "makes a +3 tier-1 rival a +0 tier-2"), כך ששינוי
כיוונון שמפר אותו נופל מיד. סולם הדרגות לא מתייתר, וההתחלה כן זזה.

**הסטטיסטיקות:** השדרוג נכנס דרך נקודה **אחת** — `equippedBonus` מכפיל את
הבונוס של כל פריט לבוש בדרגת השדרוג שלו, ומשם הכול זורם ל‑`deriveStats`. לכן
הקרב, ששת כישורי הגוף וכל מסך שמציג סטטיסטיקה יורשים את זה בלי שורת קוד אחת.
פריט **שלא לבוש** לא תורם כלום גם אם הוא ב‑`+3` — הדרגה נשמרת ומחכה לו.

**התכנסות (הכלל, במדויק).** הדרגה השמורה היא **קו־שיא** (high‑water mark), לא
מונה, והאירוע נושא את הדרגה שאליה **מגיעים**:

> `item_upgraded` מוחל רק כאשר `upgrades[itemId] < toLevel`, ומחייב את ה‑`cost`
> שלו **רק** כשהוא מוחל.

שלוש התוצאות, כולן בבדיקות (`tests/upgrades.test.ts`, `tests/merge.test.ts`,
`tests/e2e.sync.test.ts`):

* **כפילות** של צעד שכבר נלקח היא no‑op — בדיוק החוזה של `coins_spent` ושל
  `character_purchased`, כשהמפתח הסמנטי כאן הוא `(itemId, toLevel)`;
* **שני מכשירים אופליין** שקנו `+1` על אותו פריט כותבים שני אירועים עם uuid
  שונה ואותו `toLevel: 1`. איחוד היומנים — בכל כיוון ובכל סדר הגעה — נוחת על
  `+1` ומחייב **פעם אחת**;
* מכשיר שהגיע ל‑`+2` בזמן שהשני הגיע ל‑`+1` מתכנס ל‑`+2` ומשלם על **כל צעד**
  בדיוק פעם אחת — בדיוק מה שמכשיר יחיד היה משלם.

המחיר רוכב במטען (ולא נגזר מחדש בקיפול), בדיוק כמו `nextWorld` ב‑`boss_defeated`:
יומן ישן ימשיך להתקפל לאותו כיס גם אם `BALANCE.upgrades` יכוון מחדש.

**גרסת בלוב v6 → v7.** נוסף השדה `equipment.upgrades`. בלוב v6 פשוט לא מכיר
אותו, ולהמציא לו `{}` היה **מוחק** דרגות ששמורות ביומן — לכן הבלוב נדחה
(`normalizeGame`) והמצב נבנה מחדש מהיומן, שהוא נתיב המיגרציה הרשמי כאן. בקריאת
בלוב נזרקות דרגות של מזהים שהרוסטר איבד, וכל ערך נחתך ל‑`0…3`. `data_cleared`
מאפס גם את השדרוגים.

**הממשק:** שורת פריט שבבעלותכם מציגה תג `+N` (עם כוכבים), את הבונוס **בדרגה
הנוכחית**, וכפתור `⬆ שדרוג · 🪙 <מחיר>`. אין מספיק מטבעות — הכפתור מנוטרל ואומר
`חסרים 🪙 X` (ושום אירוע לא נכתב); ב‑`+3` הוא מוחלף ב‑`⭐ מקסימלי`. הכותרת של
המגירה מציגה את הדרגה של הפריט הלבוש, וטבלת הסטטיסטיקות כרטיס אחד מעל זזה
באותו רינדור. ביומן ההרפתקה נרשמת שורה `⬆ שודרג: <פריט> +N · −X 🪙`.

### הציוד על הדמות

כל פריט מצויר מ**אותן נקודות עיגון** של הגוף (`characterAnchors`): גב רחב מרחיב
את הגלימה, רגליים עבות מרחיבות את הנעליים, ליבה חטובה מצרה את החגורה. מהגדרת
הפריט מגיעים רק שני צבעים ודרגה. הגלימה היא השכבה היחידה שמצוירת **לפני** הגוף
(היא תלויה מאחוריו); השאר נלבשות מעליו.

הכול חייב להיקרא גם ב‑220px (מסך הדמות) וגם ב‑90px (הזירה), ולכן כל פריט הוא
צללית אחת נועזת ועוד פרט הדגשה אחד לכל היותר, ושום דבר לא נשען על קו דק מ‑2
יחידות משתמש (≈0.9px בקנה המידה של הזירה).

**הנעליים — שתי נעליים, אחת לכל רגל.** הן צוירו מחדש: הציור הישן היה שני טריזים
שטוחים שהוצמדו לחלק מרוחב האגן ש**אינו** זה שהרגליים עצמן עומדות עליו, ולכן הם
הצביעו הצידה ו"ריחפו" מתחת לדמות ככל שהרגליים התעבו. עכשיו יש **צורה אחת
שמצוירת פעמיים במראה**, כל אחת מנקודת הקרסול של הרגל שלה — בדיוק הביטוי
ש‑`legGroup` מסיים בו את קו השוק (`hipHalf · 0.58 · legSpread`), כך שנעל לא
יכולה להתנתק מהרגל שהיא נועלת: רגליים עבות עומדות רחב יותר והנעל נוסעת איתן,
בשני הגופים ובכל רמה 1–99. כל נקודה בצורה היא היסט **החוצה** מהקרסול, ולכן
הבהונות פונות החוצה־קדימה כמו אדם שעומד, והזוג סימטרי סביב קו האמצע מעצם
הבנייה. ארבעה חלקים: **צווארון** מעוגל שרחב מהשוק ומתחיל מעליו (הרגל נכנסת אל
תוך הנעל במקום לרחף מעליה), **גוף** עם עקב גבוה שיורד לקופסת בהונות עגולה,
**סוליה** בגוון כהה יותר שמעורבב מצבע הפריט עצמו (`darken()` — אין צבע שלישי
בהגדרת הפריט), ו**רמז שרוכים** אחד; הדרגה השלישית מוסיפה כנף קטנה שמושרשת
בצווארון ופונה החוצה. נקודות הברק של שדרוג (`flairSpots`) יושבות על קופסאות
הבהונות.

**ובזירה זה אותו ציור בדיוק.** הדמות בקרב מצוירת מ‑`game.equipment` — אותו
`EquipmentView` שמסך הדמות מצייר ממנו — על אותו משטח 200×320, והזירה רק מקטינה
אותו ב‑CSS. הזירה מציירת את הלוחם **פעם אחת**, בעליית המסך, וכל מצב אחר (גל
רגיל, מיני‑בוס, בוס עולם, מצב אלוף, האתגר היומי, דו־קרב) מחליף את **הקשר** הקרב
ולא את הדמות — ולכן הציוד והברק של השדרוג נמצאים שם בכל מצב, בלי חזרה על הקוד.
בדו־קרב **שני** הצדדים לבושים: הרוח מציירת את הציוד שבתצלום *שלה*
(`ghostFigure`), אחרי `normalizeGhost`, כך שפריט שהומצא בשורה עוינת לא מלביש
איש.

**הברק של השדרוג — טיפול שיטתי, לא ציור לכל פריט.** אותו כלל אחד רץ על כל
שנים־עשר הפריטים ועל כל עשרת צירופי הגוף × מראה, והוא נשען על אותן נקודות עיגון
בדיוק (`flairSpots`), כך שאין קבוצה שנייה של קואורדינטות שאפשר לשכוח לעדכן:

| דרגה | מה נוסף |
|---|---|
| `+1` | **נצנוץ** אחד (כוכב ארבע־קצוות) בנקודה הראשית של הפריט — עדין, שום דבר אחר לא משתנה |
| `+2` | נצנוץ על **כל** נקודות הפריט, ועוד **זוהר** צבעוני (`<feDropShadow>` ב‑SVG) |
| `+3` | אותם נצנוצים, זוהר מעט חזק יותר, ו**תג כוכב** קטן שננעץ ליד הפריט |

הקבוצה של הפריט מקבלת `class="ch-equip upgraded up-N"` ו‑`data-upgrade="N"`,
ומ‑`+2` ומעלה גם `filter="url(#chUp-<פריט>-<דרגה>)"` שמצביע על הגדרה בתוך ה‑`<defs>`
היחיד של הציור. פריט ב‑`+0` מייצר בדיוק את אותו markup שהיה קודם, בלי תו אחד נוסף.

**למה הזוהר עבר מ‑CSS ל‑SVG.** הוא היה
`filter:drop-shadow(0 0 Npx var(--up-glow))` ב‑`styles/character.css`, והצבע
הועבר כמשתנה CSS. על גלקסי S24 (Samsung/Chrome אנדרואיד) זה נראה כמו **כתם כהה
ענק** מתחת לנעליים: `var()` בתוך פונקציית `filter` על אלמנט SVG לא נפתר שם
באמינות, וצבע שלא נפתר נופל ל**שחור** — ובנוסף `+3` ערם **שני** `drop-shadow`,
ושניים כאלה מצטברים לזרקור ולא לנצנוץ. היום זה `<feDropShadow>` אחד לפריט, עם
`flood-color` **מפורש** (האקסנט של הפריט, ידוע בזמן הציור — אין מה לפתור),
`stdDeviation` קטן ו‑`flood-opacity` חסום. הרדיוס ביחידות ה‑viewBox, ולכן הזוהר
הוא אותו שבר מהציור ב‑220px (מסך הדמות), ב‑90px (הזירה) וב‑62px (כרטיס ברוסטר).
שני פריטים משודרגים = שתי קבוצות עם שני פילטרים נפרדים, כך ששום דבר לא מצטבר.

### מגוון הדמויות (Roster) — מטריצת גוף × מראה

**איפה:** במסך 🦸 **דמות**, מתחת לדמות עצמה: **בורר גוף** (שני כפתורים, ≥44px:
🧔 גבר / 👩 אישה) ומעליו רצועת **מראים**. הקשה משנה מיד את הציור שמעליה (וגם את
הדמות בזירה).

הרוסטר הוא **מטריצה**: כל אחד מחמשת המראים קיים על **שני** הגופים, כלומר עשרה
צירופים. מזהה צירוף הוא `<מראה>_<m|f>` — `hero_m`, `hero_f`, `robot_f`…

**גופים (חינם, תמיד):**

| גוף | סילואט |
|---|---|
| `male` | הגוף המקורי, ספרה בספרה |
| `female` | מוטת כתפיים צרה יותר, אגן רחב (הנקודה הרחבה ביותר במנוחה), מותן צרה, חזה עגול ונמוך מעט, גפיים קלות יותר |

**מראים (מחיר אחד, שני הגופים):**

| מזהה | שם הכרטיס | מחיר | קישוט ראש (זהה בשני הגופים) | שיער — גבר / אישה |
|---|---|---|---|---|
| `hero` | הבסיס | **0 🪙** | אין | ללא / **תלתלים ארוכים** |
| `robot` | רובוט | 400 🪙 | ויזור זוהר + אנטנה | ללא / ללא (שלדה, אין שיער) |
| `spartan` | לוחם עתיק | 900 🪙 | קסדה עם ציצה אדומה ומגן אף | ללא / קוקו קלוע שמבצבץ מאחורי הקסדה |
| `zombie` | זומבי | 1400 🪙 | תפרים על המצח + ציצת שיער | ללא / **תלתלים קרועים** (אותו ענן, שליש ממנו חסר) |
| `ninja` | נינג׳ה | 1800 🪙 | מסכה מלאה + סרט ראש אדום מתנפנף | שיער אסוף / שיער אסוף |

**למה השיער נבחר כך:** הקישוט הוא של ה**מראה** וזהה בשני הגופים (הוא נכתב
ביחידות של רדיוס הראש, ולכן מסכת הנינג׳ה יושבת גם על ראש גברי וקסדת הספרטני גם
על ראש נשי); ה**שיער** נבחר לכל גוף בנפרד, כי הוא מה שנותן לצירוף אישיות. תלתלים
ארוכים שורדים מתחת לתפרים של הזומבי אבל לא מתחת לקסדה או למסכה — קסדה הייתה
מסתירה אותם לגמרי, ומסכה הייתה נדחפת החוצה מהם ומאבדת את הצללית שלה. לכן שם יש
קוקו/שיער אסוף, ולרובוט אין שיער כלל.

**הכלל שאין ממנו יוצא דופן: הדמויות הן קוסמטיקה בלבד.** אף צירוף לא נותן סטט,
לא בונוס ולא שער — `deriveStats` אפילו לא מקבל אותם כפרמטר, ויש בדיקה שסורקת את
**כל עשרת הצירופים** ומוודאת שטבלת הסטטיסטיקות זהה לחלוטין לכל בחירה. רק אימון
מחזק.

**שני הגופים חינם, תמיד.** ייצוג הוא לא רכישה: המראה `hero` נחשב "בבעלות" מעצם
הגדרתו (`cost: 0`) על שני הגופים, אף פעם לא נכתב ל‑`characters.owned`, והמעבר
בין הגופים לא עולה מטבע אחד ולא תלוי בשום אירוע ששרד מיזוג.

**רכישה אחת = שני הגופים.** מה שנכנס ל‑`characters.owned` הוא מזהה ה**מראה**,
לעולם לא צירוף, ולכן `robot` פותח גם את `robot_m` וגם את `robot_f` באותו מחיר.
כרטיס נעול נפתח בגיליון אישור (שם, מחיר, כמה מטבעות יש) — הקשה אחת לעולם לא
קונה. הכיס נבדק ב‑`buildCharacterPurchase` **לפני** שנכתב משהו, בדיוק כמו בחנות
הציוד, ולכן רכישה שנדחתה לא משאירה זכר ביומן. קנייה גם **בוחרת** מיד — על הגוף
שכבר משחקים בו.

**👁 תצוגה מקדימה:** מהגיליון אפשר "למדוד" מראה נעול — הדמות הגדולה במסך נצבעת
אליו **על הגוף, הרמות והציוד האמיתיים שלכם**, בתוך מסגרת מקווקוות עם השבב
"תצוגה מקדימה — לא נרכש" וכפתור "↩ חזרה לדמות שלי". החלפת גוף בזמן מדידה מלבישה
את אותו מראה נעול על הגוף השני. זה **מצב תצוגה בזיכרון בלבד**: אף אירוע לא נכתב,
`game.characters` לא נוגעים, הגיליון נשאר פתוח מתחת (קנייה היא הקשה אחת), והמצב
מת ביציאה מהמסך — ולכן **הזירה לעולם לא נלחמת כדמות שרק נמדדה**
(`ui/battle.ts` קורא רק את `characters.selected`).

**איך זה נשמר:** `characters.owned` (מזהי מראה) ו‑`characters.selected` (מזהה
צירוף) מקופלים מהיומן כמו כל השאר. `character_purchased` אידמפוטנטי לפי מזהה
המראה — שני מכשירים שקנו את אותו מראה אופליין (שני uuid שונים) יחויבו **פעם
אחת** באיחוד; `character_selected` הוא LWW לפי `(ts, id)`, ולכן שני מכשירים
מתכנסים לאותו צירוף.

**למה אין אירוע `body_selected`.** גוף ומראה נבחרים תמיד ביחד — משחקים צירוף
אחד בדיוק — ולכן שני אירועים שמתארים חצי מהצירוף כל אחד היו יכולים רק **לסתור
זה את זה אחרי מיזוג** (מכשיר א׳ החליף גוף, מכשיר ב׳ החליף מראה, ואיזה חצי
מנצח?). שדה אחד + אירוע אחד = LWW טריוויאלי, ואין reducer שני לשמור בסנכרון.

**תאימות לאחור (v5 → v6).** מזהים שנכתבו ביומן לפני המטריצה ממופים בקיפול
(`resolveCharacterId`), ולכן שום יומן לא נכתב מחדש:

| מה שביומן | סוג | לאן זה מתקפל | למה |
|---|---|---|---|
| `character_purchased "ninja"` | מראה | מראה `ninja` — פתוח בשני הגופים | זה כבר היה מזהה מראה |
| `character_selected "hero_m"` | צירוף | `hero_m` | היה כבר מזהה צירוף |
| `character_selected "hero_f"` | צירוף | `hero_f` (גוף נשי + מראה הבסיס) | היה כבר מזהה צירוף |
| `character_selected "robot"` | ישן | `robot_m` | הרובוט היה זכר‑בלבד — זה בדיוק הציור שהיה על המסך |
| `character_selected "spartan"` | ישן | `spartan_m` | כנ״ל |
| `character_selected "zombie"` | ישן | `zombie_m` | כנ״ל |
| `character_selected "ninja"` | ישן | `ninja_f` | הנינג׳ה הייתה נקבה‑בלבד |

הכלל הוא שדה אחד ב‑`SkinDef`: `nativeBody` — הגוף שהמראה נמכר עליו לפני
המטריצה. **המיגרציה עצמה היא בנייה מחדש מהיומן:** `GAME_STATE_VERSION` עלה
5→6, `normalizeGame` דוחה בלוב v5 (אותם שמות שדות, מזהים במשמעות אחרת — בדיוק
המקרה שמספר גרסה קיים בשבילו), ו‑`ensureGameState` מקפל את היומן מחדש. לשם
ביטחון, גם `normalizeCharacters` סובלנית לשתי צורות המזהה בקריאה.

### איך מראה מצויר

הגיאומטריה **לא** משוכפלת: `characterGeometry(parts, body)` היא אותה פונקציה עם
טבלת פרופורציות אחת לכל גוף (`BODIES`), והשורה של `male` היא בדיוק המספרים
המקוריים — הווריאנטים נוצרו מחילוץ הקבועים, לא מכיוונון מחדש. מראה תורם רק:

* `palette` — שמונה צבעים שנכתבים כ‑CSS custom properties על ה‑`<svg>` עצמו,
  כך ש‑`styles/character.css` נשאר המקום היחיד שבו מוגדרים הצבעים. הפלטה זהה
  בשני הגופים: מראה הוא סכמת צבע, לא סילואט;
* `decor` — קישוט ראש (ויזור/קסדה/תפרים/מסכה) ביחידות של רדיוס הראש, כך שהוא
  נקרא גם ב‑220px וגם ב‑90px ומתאים לשני גדלי הראש בלי מספר מכויל ביד. יכול
  להסתיר עיניים/פה כשהוא מכסה אותם;
* `hair` — שכבה **נפרדת** (`none`/`curls`/`ragged`/`tied`) שנבחרת לכל גוף. השיער
  מצויר ראשון והקישוט מעליו, ולכן השניים **מתחברים**: קסדת ספרטני על קוקו,
  תפרי זומבי על תלתלים קרועים.

לכל צירוף יש `id` משלו ל‑`linearGradient` של פלג הגוף, כי רצועת הרוסטר מציירת
כמה דמויות על אותו עמוד ו‑`id` כפול היה גורם לכולן לקבל את הצבע של הראשונה.

### תלתלים ארוכים (הגוף הנשי)

השיער הנשי הוא **ענן עיגולים חופפים** — אותו סגנון של הגרסה הקצרה, אבל באורך
מלא, עד גובה החזה. הוא בנוי משלוש שכבות, כי שיער ארוך יותר מהראש:

1. **הכתר** (`.ch-decor.back`, בתוך קבוצת הראש, מאחורי הגולגולת) — אליפסת מסה
   ועליה טבעת של תשעה תלתלים שנוגסים מעבר לקו הגולגולת, ועוד שני "פוחים" בגובה
   האוזניים שנותנים לענן את רוחבו;
2. **המפל** (`.ch-hair back`, **לפני הגוף**) — שני טורים חיצוניים שנופלים עד
   גובה החזה ועוד זוג צר מאחורי הצוואר, בתוספת שני תלתלי הדגשה בגוון הבהיר.
   השכבה הזו מצוירת אחרי הגלימה ולפני פלג הגוף: **שיער נח על גלימה**, לא נעלם
   מתחתיה, ובכל זאת הגוף נקרא ראשון;
3. **הקדמה** (`.ch-decor.front`, אחרונה בציור) — קו השיער שממסגר את הפנים, שני
   תלתלי ההדגשה, ו**גדיל אחד לכל צד שנופל על הכתף**. הגדילים האלה הם מה שמבטיח
   שהשיער נקרא בכל רמה: גב רחב מאוד יכול לבלוע את המפל, הוא לא יכול לבלוע אותם.

**שני אזורי אסור, ולמה הם קיימים.** בצילום מסך מ‑S24 ברמה גבוהה השיער *בלע* את
הדמות: הגדילים הקדמיים נפלו עד גובה 118 בקו קבוע, כלומר **בתוך** פלג הגוף מרמה 5
ומעלה — סינר כהה על שני שרירי החזה — וקו השיער ישב על הלחיים. שניהם תוקנו
כגאומטריה, ונבדקים כגאומטריה:

* **הפנים** — אף תלתל בשכבה הקדמית לא נוגע במעגל סביב תווי הפנים (‎0.62·r סביב
  מרכז שמעט מתחת למרכז הראש). קו השיער ממסגר את הפנים **מבחוץ**. הכתר מותר
  לחפוף כרצונו: הוא מצויר מתחת לגולגולת ולכן אינו מכסה כלום;
* **החזה** — הגדילים הקדמיים **נעצרים על קו הכתפיים** (‎y=88, וקצה החזה מתחיל
  ב‑‎y≈100 גם ברמה המקסימלית). ה**אורך** הוא תפקידו של המפל, והמפל מצויר **לפני
  הגוף** — ולכן שום אורך לא יכול לנחות על החזה, בשום רמה.

הכול נכתב ביחידות של רדיוס הראש. **מספר אחד** בענן כן קורא את הגאומטריה: קצה
הגדיל הקדמי עוקב אחרי נקודת הכתף (`shoulderHalf − 0.45·deltoidR`), כדי שהגדילים
**יחבקו** את הצללית במקום לחצות אותה — קצה קבוע מפסיק לחבק ברגע שהכתפיים גדלות
מעבר לו. הוא **חסום** לטווח ‎[1.05·r, 2.2·r], וזה מה שמשמר את התכונה הישנה: אין
רמת חזה או כתפיים שדוחפת תלתל אל מחוץ ל‑viewBox של 200×320 — הנקודה הרחבה היא
‎≈2.4·r מקו האמצע והנמוכה ‎≈5.0·r מתחת למרכז הראש, בכל רמה. הבדיקות סורקות בדיוק
את זה (מספר התלתלים, כמה מהם מתחת לקו הכתפיים, שני אזורי האסור ברמות
‎1/5/10/25/99, סדר הציור גלימה → מפל → פלג גוף → ראש → גדילים, וגבולות הבמה).
המחלקה `.ch-curl` נשמרה — היא החוזה שהבדיקות נאחזות בו.

הזומבית מקבלת את אותו ענן ב‑`ragged`: כל תלתל שלישי חסר והרדיוסים קטנים ב‑14%.

### גביעים

כל בוס שהופל משאיר **מדליה** קטנה על חזה הדמות (`<g class="ch-trophies">`) ו**גביע
SVG** במדף הגביעים במסך הדמות, עם שם הבוס ושם העולם בעברית. לצידם מוצג גם מונה
המיני‑בוסים ומונה הגלים.

## מיומנויות גוף (Phase 4)

לכל אחת משש קבוצות השרירים יש **מיומנות אקטיבית** אחת, שנפתחת כשאותו חלק גוף מגיע
לרמה 5 ומתחזקת עם כל רמה נוספת מעליה. זו לא מטבע חדש ולא מסך חדש: זו שורת כפתורים
בזירה, מעל מהלך העל.

### שש המיומנויות

| חלק גוף | מיומנות | נפתחת | מה היא עושה | טעינה |
|---|---|---|---|---|
| חזה | 🔨 **מכת מחץ** | חזה רמה 5 | מכה בודדת בנזק ×4 מההתקפה | 20 שנ׳ |
| גב | 🛡️ **עמידת ברזל** | גב רמה 5 | 6 שניות שבהן הנזק הנכנס יורד ב‑55% (מעל ההגנה הרגילה) | 30 שנ׳ |
| רגליים | 🌋 **רעידת אדמה** | רגליים רמה 5 | נזק ×1.2 ועצירת האויב ל‑1.5 שניות (הטיימר שלו נדחף אחורה) | 25 שנ׳ |
| כתפיים | 🌀 **סערת מהלומות** | כתפיים רמה 5 | 5 שניות שבהן מרווח ההתקפה נחתך לחצי | 30 שנ׳ |
| ידיים | 🎯 **מכה מדויקת** | ידיים רמה 5 | ההתקפה האוטומטית הבאה קריטית מובטחת, עם ‎+50%‎ נזק קריטי | 15 שנ׳ |
| ליבה | 🌬️ **נשימה עמוקה** | ליבה רמה 5 | ריפוי מיידי של 25% מהחיים ועוד 4 שניות של התאוששות ×5 | 35 שנ׳ |

### מה מחזק אותן

**רמת אותו חלק גוף, ורק היא.** העוצמה היא

```
power = 1 + min(0.6, 0.03 × (רמת החלק − 5))
```

כלומר ‎+3%‎ לכל רמה מעל הפתיחה, עד תקרה של ‎+60%‎ (רמה 25). ה‑power מוכפל בעוצמה
של המיומנות — נזק, אחוז הריפוי, אורך הסטאן, משך סערת המהלומות, בונוס הקריטי —
אבל **לא בזמן הטעינה**, כדי שקצב הקרב יישאר קריא. אימון חזה מחזק את מכת המחץ בלבד;
אימון ידיים לא נוגע בה. כל המספרים יושבים ב‑`BALANCE.skills` ב‑`core/balance.ts`.

### למה זה לא נוגע ביומן האירועים

* **הפתיחה נגזרת.** אין דגל "נפתח" בשום מקום — מיומנות פתוחה כי `parts[part].level ≥ 5`,
  והרמה עצמה כבר נבנית מהיומן. אין מה למגרייט, ואי אפשר שהמצב יסתור את היומן.
* **הפעלה היא טקטיקה, לא היסטוריה.** בדיוק כמו הקשה על האויב, הפעלת מיומנות לא
  כותבת אירוע. `wave_cleared` (ו‑`boss_defeated`) נשארים האירועים היחידים בקרב.
* **ה‑state של הקרב הוא בזיכרון בלבד.** ה‑cooldowns וחלונות ה‑buff חיים ב‑`BattleState.skills`,
  ו‑`BattleState` לא נשמר לעולם — לא ב‑localStorage ולא בענן.

### דטרמיניזם

`useSkill(state, id, stats, levels)` הוא חלק ממכונת המצבים של `core/combat.ts`:
הוא מזיז את אותו state, ה‑cooldowns וחלונות ה‑buff יורדים על אותו tick קבוע
(`BALANCE.combat.tickMs`), וכל הגרלה ממשיכה לצאת מאותו זרם RNG מזורע. לכן **אותו
seed + אותם טיקים של הפעלה = ריצה זהה בייט‑בייט**, ולוח הפעלות אחר נותן ריצה אחרת
— אבל משוחזרת בדיוק גם היא. שתי החלטות עיצוב שומרות על זה:

* **העוצמה נפתרת בזמן ההפעלה** ונשמרת ב‑state (למשל `guardTaken`), כך שלולאת
  ה‑tick לא צריכה להכיר רמות, ועליית רמה באמצע חלון לא משנה חלון שכבר רץ.
* **הגרלת הקריטי תמיד קורית**, גם כשמכה מדויקת כבר מבטיחה קריטי — כך רצף ה‑RNG
  לא זז בגלל מיומנות.

מיומנות נעולה היא **no‑op מוחלט**: לא נפתח cooldown, לא מוגרל מספר, שום שדה ב‑state
לא זז (יש על זה בדיקה שמשווה snapshot מלא).

### איזון

בסימולציה של 20 גלים רצופים, דמות עם כל החלקים ברמה 5–6 שמפעילה את כל שש
המיומנויות **ברגע שהן מוכנות** מנקה גלים ב‑**26%–36% מהר יותר** מריצה סבילה לגמרי
(נמדד בגלים 10/20/30, מוצמד ב‑`tests/skills.test.ts` לטווח 20%–45%). זה משמעותי,
אבל הלולאה הסבילה נשארת שלמה: אותה דמות מנקה 12 גלים ברצף בלי אף נוק‑אאוט גם בלי
לגעת בשורה. ובכיוון השני — דמות ברמה 3 עם מיומנויות (כלומר נעולות) עדיין מפסידה
לדמות ברמה 8 שרק עומדת שם. **אימון מנצח טכניקה.**

### הממשק

שורה של שישה כפתורים מעל מהלך העל, בסדר חלקי הגוף:

* **נעול** — 🔒 ושורת רמז עם האימון החסר ("חזה רמה 5"). הכפתור נשאר לחיץ בכוונה:
  הקשה עליו מסבירה בעברית מה פותח אותו, כי 🔒 לבד לא מלמד כלום.
* **מוכן** — האייקון בצבע `--warn`, כיתוב "מוכן".
* **בטעינה** — מטאטא רדיאלי (`conic-gradient` שקורא `--cd`, מספר אחד בין 0 ל‑1
  שנכתב מהליבה) וספירה לאחור בשניות.
* **פעיל** — מסגרת ירוקה, ו**צ׳יפ קטן מעל הדמות** עם הזמן שנשאר לחלון.

כל משבצת ≥44px, הכול RTL ובעברית, והצבעים מגיעים מה‑tokens בלבד. הפידבק על המסך
(`.anim-skill` על הגיבור, `sk-<part>` שמנפח את השריר שהתאמן, `fx-<skill>` על שכבת
האפקטים) בנוי בדיוק כמו שאר האנימציות — מחלקות קצרות‑חיים ש‑`prefers-reduced-motion`
מכבה בלי לשבור כלום.

## אתגר יומי (Phase 7)

**גאונטלט אחד ליום — אותו גאונטלט לכל חשבון, נבנה מהתאריך עצמו.** ניסיון אחד
ליום, דמי כניסה באנרגיה, ובלי החייאות: זה מבחן של הסטטיסטיקות ושל הידיים, לא
המשך של הקמפיין.

### הזרע: התאריך, ורק הוא

```
seed = FNV-1a("daily|2025-05-04")
```

הזרע הוא hash של **מחרוזת התאריך** בלבד — לא של השעון, לא של ההתקדמות, לא של
המכשיר. לכן שני חשבונות שפותחים את האפליקציה באותו יום קלנדרי פוגשים גלים זהים
בייט‑בייט (ואפשר לחשב את של מחר כבר היום). כל מה שנגזר מזה — איזה אויב מגיע בכל
גל, וכל הגרלת נזק בקרב דרך `waveSeed(seed, …)` — יוצא מאותו מספר.
`core/daily.ts` הוא הבעלים, והוא טהור כמו כל `core/`: התאריך תמיד פרמטר, אף
פעם לא `Date.now()`.

### הפורמט

| | |
|---|---|
| גלים | **10**, גל 10 הוא **מיני‑בוס** |
| עולמות | סיור מעולם 1 לעולם 4 — 1,1,2,2,2,3,3,4,4,4 — **בלי קשר לאן הגעתם** |
| אויבים | הגרלה מזורעת מהרוסטר של אותו עולם, הגרלה אחת לכל גל |
| עקום | `BALANCE.daily.enemy` — עקום **משלו**, נפרד מ‑`combat.enemy` |
| חיים | ריצה אחת. אין ניסיון חוזר; ב‑0 חיים הריצה נגמרת |
| ריפוי | 18% מהחיים בין גל לגל, ועוד ההתאוששות של הליבה |
| כניסה | **30 ⚡** — פעם אחת לניסיון, לא לכל גל |
| פרס | 20 🪙 בגל הראשון, ‎+5 לכל גל אחריו, ו‑**250 🪙 בונוס** על ניקוי מלא (675 🪙 לריצה מושלמת) |

העקום נפרד מהקמפיין בכוונה: כוונון מחדש של העולמות לא יכול לכוונן בשקט את
האתגר, ולהיפך.

### הניקוד

**ניקוד = גלים שנוקו (0–10).** שובר השוויון הוא **אחוז החיים שנשאר בסוף** — 0
אחרי נוק‑אאוט — כך שתי ריצות ש"עשו 8" מסתדרות לפי כמה בנוח הן עשו את זה. אין
"שיא אישי לתאריך", כי יש בדיוק ניסיון אחד לכל תאריך; מה שנשמר לכל החיים הוא
מספר הניצחונות המלאים, השיא הגבוה ביותר, והרצף — ימים קלנדריים רצופים שבהם
ניגשתם.

### אירוע אחד לריצה, אידמפוטנטי לפי תאריך

הקרב עצמו **לא כותב כלום**: אין `wave_cleared` בזמן אתגר, אין מטבעות בארנק, אין
אנרגיה שיורדת. כל הריצה נרשמת באירוע **אחד** ברגע שהיא נגמרת:

```ts
daily_challenge {
  date,          // התאריך של הגאונטלט — וגם מפתח האידמפוטנטיות
  seed, score, wavesCleared, tiebreak,
  coins, energySpent, complete, outcome, durationMs
}
```

המטען **סמכותי** (כמו `boss_defeated` ו‑`item_upgraded`): המחיר והפרס נוסעים
בתוכו, ולכן replay אף פעם לא מדמה מחדש את הקרב ולא גוזר מחדש את טבלת הפרסים —
יומן ישן ימשיך להתקפל לאותו ארנק גם אחרי כוונון של `BALANCE.daily`.

ה‑reducer מחיל את האירוע **רק** כש‑`daily.runs[date]` ריק, ומחייב/משלם רק כשהוא
מוחל. מכאן שלושת הכללים:

* **כפילות = no‑op.** אותו אירוע פעמיים (או עותק עם uuid אחר) לא משלם פעמיים.
* **שני מכשירים, אותו יום, שניהם אופליין.** שניהם כותבים אירוע עם אותו `date`
  ו‑uuid שונה. איחוד היומנים בכל אחד משני הכיוונים משאיר את **הראשון בסדר
  `(ts, id)`** — סדר שהוא תכונה של *קבוצת* האירועים ולא של סדר ההגעה — ולכן שני
  המכשירים מגיעים לאותה רשומה, לאותם מטבעות ולאותה אנרגיה. הריצה ה"מפסידה"
  נשארת ביומן לנצח, פשוט לא נספרת.
* **כל שאר המספרים נגזרים.** `attempts`, `completed`, השיא, הרצף והרצף הטוב
  ביותר מחושבים ב‑`finalizeGame` מתוך `daily.runs` — בדיוק כמו שרמות נגזרות
  מ‑XP. שדה נגזר לא יכול לסתור את היומן אחרי מיזוג.

### מה קורה כשעוזבים באמצע

הכלל, במשפט אחד: **ריצה נרשמת פעם אחת, כשהיא נגמרת — בניצחון, בנוק‑אאוט, או
בוויתור.** יציאה מהזירה (החלפת טאב, החלפת מרכז) היא **ויתור**: `stopBattle()`
רושם את הריצה עם הגלים שנוקו בפועל, בלי בונוס הסיום, והניסיון של היום נוצל.

* **מזעור הטאב** רק **משהה** — בדיוק כמו בקרב רגיל. אין רווחים אופליין ואין
  ויתור.
* **רענון או קריסה של הדפדפן** באמצע ריצה לא כותבים כלום: הניסיון לא נוצל,
  המטבעות לא שולמו, הריצה פשוט אבדה. זה הכיוון הבטוח — **שום מטבע חלקי לא
  דולף**, כי מטבעות משולמים אך ורק על גלים שהיומן מעיד שנוקו.

### למה זה לא דורש מנוע שני

האתגר רץ בתוך **אותה** מכונת מצבים (`core/combat.ts`), בהקשר נפרד:
`BattleState.challenge` מחזיק את הגאונטלט ומחליף בדיוק שלושה חוקים —

1. הגלים מגיעים מהסקריפט ולא מ‑`waveSpec(world, wave)`;
2. ניקוי גל פולט `challenge_wave` במקום `wave_cleared`;
3. נוק‑אאוט **מסיים** את הריצה במקום להחיות אותה.

הקשות, מהלך על, שש המיומנויות, הסטטיסטיקות, ה‑tick הקבוע וה‑RNG המזורע —
זהים לחלוטין. גם ה‑UI לא מכפיל כלום: לחיצה על ⚔️ מחליפה את ה‑state של הזירה
ומדליקה מסגרת ענבר, ואותה לולאה ממשיכה לרוץ.

### הממשק

כרטיס אחד מתחת לרצועת העולמות, עם ארבעה מצבים (מסומנים ב‑`data-state`, כך
שהעיצוב והבדיקות קוראים את אותה מילה):

* **`available`** — התאריך, 🎲, חמישה ספרייטים אמיתיים מהגאונטלט של היום,
  ו‑`⚔️ התחילו את האתגר · 30 ⚡`.
* **`locked`** — אין מספיק אנרגיה. הכפתור נשאר לחיץ ומסביר בעברית כמה ⚡ יש
  וכמה שווה סט.
* **`live`** — `גל 3/10`, פס התקדמות, ואזהרה שיציאה עכשיו היא ויתור. הזירה
  מוקפת בענבר, מונה הגלים בכותרת הופך ל‑`3/10`, ושורת המצב מדברת אתגר.
* **`done`** — `8/10 · +300 🪙` ו"מחר יש אתגר חדש". שורת היומן:
  `🎲 אתגר יומי: 8/10 · +300 🪙` (🏅 על ניקוי מלא).

הכול RTL ובעברית, כל יעד מגע ≥44px, הצבעים מה‑tokens, ו‑`prefers-reduced-motion`
מכבה את התנועה כמו בכל שאר המסך.

### איזון

נמדד מול המנוע האמיתי, עם אותו טייס אוטומטי של המיומנויות שמשמש את בדיקות
Phase 4 ו**בלי הקשות** — כלומר הרצפה השמרנית, כי שחקן אמיתי מקיש:

| רמת חלקי גוף | גלים שנוקו |
|---|---|
| 3–4 | 3–5 |
| **5–6** | **5–8** |
| 7–8 | 9 |
| **9+** | **10 — גאונטלט מלא** |

ריצה שלמה נמשכת דקה וחצי עד שתי דקות. `tests/daily.test.ts` מצמיד את שני
הטווחים המודגשים על שלושה תאריכים שונים, כדי שכוונון עתידי לא יזיז אותם בשקט.

### v7 → v8

`GAME_STATE_VERSION` עלה ל‑8 ונוסף `game.daily`. בלוב v7 פשוט לא מכיר את השדה,
ולהמציא לו ערך ריק היה גרוע מלטעות: זה היה אומר "מעולם לא שיחקתם" ומחזיר ניסיון
שהיומן כבר רשם כמנוצל. לכן `normalizeGame` דוחה אותו, ו‑`ensureGameState` בונה
את הבלוב מחדש מהיומן — ללא אובדן, כי כל עובדה היא אירוע. `data_cleared` מאפס גם
את האתגרים, כמו כל השאר.

## דו־קרב רפאים (Phase 8)

**קרב אחד מול הדמות האמיתית של חשבון אחר.** שני אנשים בבית אחד (ובעתיד גם
חברים) מפרסמים "רוח" — תצלום של הדמות שלהם — והשני נלחם בה: הרמות שלה, הרצף
שלה, הציוד והשדרוגים שלה, הגוף והמראה שלה — עם פרס אמיתי בסוף (150 🪙 בניצחון,
30 🪙 בהפסד), שהפנקס של "דו־קרב אחד ליום מול כל יריב" הוא מה שמגביל אותו.

### מה זו רוח

תצלום **מינימלי ומגורסת** של דמות, ותו לא:

```ts
{ v: 1, name, body, skin, parts: {six levels}, streakTier, equipped, upgrades, characterLevel }
```

אין בו היסטוריית אימונים, אין תאריכים, אין אימייל, אין מזהה משתמש ואין מטבעות.
זה בדיוק מה ש‑`deriveStats` צריך — ולכן **היריב נבנה באותו צינור שהשחקן נבנה
בו**: אין מודל סטטיסטיקות שני, אין "עקום אויב", ואי אפשר ששני הצדדים יסטו זה
מזה. `core/ghost.ts` הוא הבעלים, והוא טהור כמו כל `core/`.

### הזרע: שני השמות, ממוינים, ועוד התאריך

```
seed = FNV-1a("duel|<שני השמות ממוינים>|2025-05-04")
```

המיון הוא מה שהופך את הקרב **סימטרי**: "א׳ נגד ב׳" ו"ב׳ נגד א׳" הם אותו מספר
באותו יום, כך שאפשר לדבר על הקרב ("ניצחתי אותך שלוש פעמים") במקום לגלגל אותו
מחדש עד שיֵצא טוב. התאריך הוא מה שמונע ממנו להיות אותו קרב לנצח.

### מה הרוח עושה בקרב (v1)

היא תוקפת בקצב האמיתי שלה, **מקטינה נזק לפי ההגנה שלה**, מכה קריטית לפי הידיים
שלה ומתאוששת לפי הליבה שלה. מה שהיא **לא** עושה: מיומנויות והקשות — כי אף אחד
לא מחזיק אותה. זו א‑סימטריה מכוונת ומתועדת: לשחקן החי יש שש יכולות, מד מהלך על
וידיים; לרוח יש רק מה שהבעלים שלה אימן. זה מה ששומר על הקרב דטרמיניסטי (תסריט,
לא בינה מלאכותית שנייה) ומאפשר לנצח יריב חזק יותר — וזה כל העניין בכבוד.

טכנית זה גל גאונטלט אחד שנושא גם את **החצי המגן** של דמות
(`def`/`critChance`/`critMultiplier`/`regen`). כל השדות האלה **אופציונליים**,
ו‑`mitigation(0) === 1`, ולכן אויב רגיל מתנהג בייט‑בייט כמו תמיד — כולל סדר
הגרלות ה‑RNG, כי הגרלת הקריטי של האויב קורית רק כשיש לו סיכוי קריטי בכלל.

### הכלכלה: 20 ⚡ פנימה, 150 / 30 🪙 החוצה

| | |
|---|---|
| כניסה | **20 ⚡** — פעם אחת לדו־קרב, כשהתוצאה נרשמת |
| פרס | **150 🪙 בניצחון · 30 🪙 בהפסד** (גם ויתור הוא הפסד, ומשולם ככזה) |
| תדירות | **דו־קרב אחד ליום מול כל יריב** (יריב אחר באותו יום — בבקשה) |
| ניקוד | 1 או 0 — יש גל אחד, אז "ניקוי" הוא בדיוק "ניצחון" |

**מה מגביל את זה הוא הפנקס, לא המחיר.** דו־קרב אחד נספר לכל (תאריך, יריב), וזה
נאכף ב‑reducer ולא בממשק — ולכן שני חשבונות בבית אחד יכולים לסחור בדו־קרב אחד
ביום, 20 ⚡ כל אחד, אנרגיה שרק אימון אמיתי מייצר. בפרספקטיבה:

| | תשלום | לכל ⚡ |
|---|---|---|
| גאונטלט יומי מושלם | 675 🪙 ל‑30 ⚡ | 22.5 |
| ניצחון בדו־קרב | 150 🪙 ל‑20 ⚡ | 7.5 |
| הפסד בדו־קרב | 30 🪙 ל‑20 ⚡ | 1.5 |

הפרס **רוכב על האירוע** (`coins` במטען, בדיוק כמו `daily_challenge`), ולכן כיוונון
מחדש של `BALANCE.duel` לא משכתב מה שילם דו־קרב אתמול; ה‑reducer **חותך** אותו
ל‑`max(winCoins, lossCoins)` ומשלם אותו **רק בענף שתופס את משבצת הפנקס**, ולכן
אירוע מזויף לא יכול לשלם יותר ממקסימום של דו־קרב אחד, וכפילות לא משלמת בכלל.
אירוע ישן מהתקופה שבה דו־קרב לא שילם כלום מגיע בלי `coins` ומתקפל כאפס — אין
מיגרציה, כי צורת ה‑`GameState` לא זזה: המטבעות נכנסים לארנק הקיים.

### אירוע אחד לדו־קרב, אידמפוטנטי לפי (תאריך, יריב)

```ts
ghost_duel {
  date, opponentHandle,      // המפתח הסמנטי — נגזר מהמטען, לא נישא בו
  opponentName, won, score, tiebreak, coins,
  seed, energySpent, snapshotHash, outcome, durationMs
}
```

אותו אידיום של האתגר היומי, בשדה אחד רחב יותר. ה‑reducer מחיל את האירוע רק
כש‑`duels.runs["<date>|<handle>"]` ריק, ולכן:

* **כפילות = no‑op** — אין חיוב כפול, אין תשלום כפול ואין רשומה שנייה;
* **שני מכשירים, אותו יריב, אותו יום, שניהם אופליין** — איחוד בכל אחד משני
  הכיוונים משאיר את הראשון בסדר `(ts, id)`, וזו תכונה של *קבוצת* האירועים
  (`tests/ghost.test.ts`, `tests/e2e.duel.test.ts` מצמידים את שני הכיוונים);
* **המטען סמכותי** — `won`/`score`/`tiebreak`/`coins` נשמרים כפי שהיו (המטבעות
  עד לתקרה). replay **לא**
  מדמה מחדש את הקרב, ולכן העובדה שהיריב התאמן מאז ופרסם רוח חזקה יותר לא
  משכתבת היסטוריה. `snapshotHash` מציין באיזו גרסה של הדמות שלו נלחמתם — לצורך
  תיעוד בלבד.

**מאזן ניצחונות/הפסדים — כללי ולכל יריב — נגזר** ב‑`finalizeGame` מתוך
`duels.runs`, בדיוק כמו רמות מ‑XP: שדה נגזר לא יכול לסתור את היומן אחרי מיזוג.

### לעולם לא לסמוך על השורה שהתקבלה

`ghosts` קריא לכל משתמש מחובר (זה **מנגנון השיתוף**), ולכן כל לקוח יכול לכתוב
בשורה שלו מה שבא לו ולהגיש לנו אותה. `normalizeGhost` הוא גבול קשיח, לא נימוס:

* `v` שאינו 1 — **נדחה**, לא מנוחש;
* כל רמה נחתכת ל‑1..99, הרצף ל‑0..200;
* מזהה פריט חייב להתקיים **ולהתאים למשבצת** שהוא טוען לה (אחרת אפשר ללבוש
  ארבע גלימות);
* רמת שדרוג נחתכת ל‑+0..+3, `skin`/`body` חייבים להיות ערכי רוסטר אמיתיים;
* `characterLevel` **נגזר** מהרמות החתוכות ולא מאומן — שורה לא יכולה להצהיר על
  רמה שהסטטיסטיקות שלה לא מכסות;
* שם שלא ניתן היה לבחור (ריק, קצר מדי, תווים אסורים) פוסל את כל השורה.

`tests/ghost.test.ts` מצמיד גם את התוצאה של כל זה: מטען עוין לא יכול לייצר שום
סטטיסטיקה שגבוהה מדמות אמיתית מקסימלית — והוא ממילא לא משלם כלום.

### פרסום: ערוץ צדדי, לא היומן

הפרסום קורה **אחרי** מחזור סנכרון מוצלח, ורק אם ה‑fingerprint של התצלום
(`ghostHash`) שונה מזה שפורסם לאחרונה (נשמר ב‑`sync/meta.ts`). דמות שלא התאמנה,
לא החליפה ציוד ולא שינתה שם לא מייצרת ולו בקשה אחת.

> **רוח היא נוכחות, לא היסטוריה.** היא נדרסת במקום בכל פרסום, ומה שהיה בה לפני
> כן לא אומר כלום. היומן נשאר **מקור האמת היחיד** למצב של החשבון עצמו: שום דבר
> מהרוח לא מתקפל חזרה לתוכו, לא כאן ולא במכשיר אחר. לכן גם **שם הלוחם נשמר
> מקומית** (בפנקס הסנכרון) ולא כאירוע: שם קוסמטי, ניתן לשינוי וייחודי‑חיצונית
> לא צריך להיות עובדה היסטורית שכל מכשיר חייב לשחזר ולהסכים עליה. פנקס שאבד =
> פרסום אחד מחדש, וזהו.

כישלון בפרסום נבלע בשקט: הגיבוי כבר עלה, והרוח תנסה שוב במחזור הבא.

### שם לוחם

השם הוא **כל משטח הגילוי**: אין רשימה, אין חיפוש חלקי ואין דרך למנות חשבונות.
3–20 תווים, אותיות בעברית/אנגלית, ספרות ו‑`_ . -`. הצורה הקנונית (trim, רווחים
מכווצים, אנגלית ב‑lowercase) עוברת דרך **אותה פונקציה** בפרסום, בחיפוש, במפתח
היומן ובזרע — ולכן חיפוש מדויק עובד גם כשמישהו הקליד "Yossi ". ברירת המחדל
נגזרת מהחלק שלפני ה‑`@` באימייל (או `לוחם-<id קצר>`), וניתנת לעריכה בכרטיס
החשבון במסך ההגדרות.

### על המסך

בלשונית 🎮 קרב, מתחת לכרטיס האתגר היומי: שדה שם + 🔍 חיפוש → תצוגה מקדימה (הדמות
שלהם, הרמה, המאזן מולם) → כפתור עם המחיר. המצבים נקראים ב‑`data-state`:
`idle` · `searching` · `missing` · `ready` · `locked` · `done` · `live`. בזמן
הדו־קרב הזירה ממוסגרת ב**סגול** (במקום הענבר של האתגר היומי), הדמות של היריב
משתקפת מולכם, ושני פסי החיים **נקראים בשם** — כשמשני הצדדים עומדים אנשים, צריך
לדעת מי מפסיד. **בלי חשבון הכרטיס פשוט לא קיים** (לא מושבת — נעדר), בדיוק כמו
כרטיס החשבון.

### v8 → v9

`GAME_STATE_VERSION` עלה ל‑9 ונוסף `game.duels`. אותו נימוק בפעם השלישית: בלוב
v8 לא מכיר את השדה, ולהמציא לו ערך ריק היה אומר "לא נלחמתם באף אחד היום"
ולהחזיר דו־קרב שהיומן כבר רשם כמנוצל. לכן הוא נדחה ונבנה מחדש מהיומן.
`data_cleared` מאפס גם את המאזן.

## מצב מפתח (Phase 9)

**לוח בקרה לבעלים בלבד, שמאפשר לבדוק יכולות בלי להתאמן — ומשאיר סימן.** אפשר
להעניק אנרגיה, מטבעות, XP ורמות, להשלים את האימון של היום, לפתוח מחדש את האתגר
היומי ואת הדו־קרבות, לאפס זמני קירור — ולבטל את הכל בלחיצה אחת.

### מי רואה את זה: כתובת האימייל, בתור hash

הריפו הזה **ציבורי**, ולכן הכתובת עצמה לא כתובה בו. מה שכתוב הוא **SHA‑256** שלה
ב‑hex (`src/dev/ownerHashes.ts`), והאפליקציה מגבבת בזמן ריצה את הכתובת של מי
שמחובר (`crypto.subtle.digest`, אחרי `trim` + `lowercase`) ומשווה.

```
                       ┌──────────────┐
 סשן Google ──email──▶ │ normalize    │──▶ SHA‑256 ──▶ ∈ OWNER_EMAIL_HASHES ?
                       │ trim+lower   │                        │
                       └──────────────┘                   כן ──┴── לא
                                                           │       │
                                              כרטיס 🛠 + window.gymDev   כלום
```

שלוש תשובות הן "לא", וכולן אותה תשובה: **מנותקים**, **חשבון אחר**, או
**`file://`** — ואז הכרטיס **לא קיים בכלל**: אין DOM, אין `window.gymDev`, אין
רמז. לא "מושבת", **נעדר** — בדיוק הכלל של כרטיס החשבון ושל כרטיס הדו־קרב.

> ה‑hash **אינו סוד ולא מתיימר להיות**. מי שכבר מכיר את הכתובת יכול לאמת שזו
> היא; מה שהוא באמת קונה זה שהכתובת לא **מפורסמת** — לא נגרפת מריפו ציבורי ולא
> יושבת בקובץ יחיד שמסתובב בין אנשים. גם השער עצמו אינו גבול אבטחה: כל מה
> שהכרטיס עושה הוא אירוע רגיל **בשמירה של המשתמש עצמו**, כך שגרוע מכל, מישהו
> יעניק לעצמו מטבעות במשחק של עצמו. ההרשאות האמיתיות יושבות ב‑`supabase/schema.sql`,
> שם כל policy מוגבל ל‑`auth.uid()` ואף אחד מהם לא שמע על הקובץ הזה מימיו.
> `crypto.subtle` קיים רק ב‑secure context — וזה בדיוק צורת התשובה הרצויה: איפה
> שאין hasher, אין שער.

### כל הענקה היא אירוע אמיתי, מסומן 🛠

אין "מצב מפתח" שמשנה איך המשחק מתנהג, ואין נתיב כתיבה שני. כל לחיצה עוברת
ב‑`commit` של `core/game.ts` — אותו אחד שכל הענקה אמיתית עוברת בו — ולכן הכל
נשמר: `live state === rebuildFromEvents(log)`, המיזוג מתכנס, וכפילות משלמת פעם
אחת. מה שמסמן אותן זה שדה אחד, `dev: true`, שקונה שלושה דברים:

* **היומן** מציג שורות 🛠 ("🛠 אנרגיה: +100 ⚡ (מצב מפתח)") — דמות מחוזקת לעולם
  לא תהיה תעלומה;
* **הרוח שמתפרסמת** נושאת דגל `dev` כל עוד יש הענקה בתוקף, והיריב רואה 🛠 קטן
  ליד השם בכרטיס הדו־קרב;
* אפשר **לבטל אותן בבת אחת** (`dev_purge`).

| כפתור | אירוע | למה דווקא הוא |
|---|---|---|
| ⚡ +100 | `energy_gained` `{source:'dev', key:'dev\|<uuid>'}` | לאירוע כבר יש שמירת `key` מ‑v4 — אין סיבה להמציא שני |
| 🪙 +500 | `coins_granted` `{key}` **(חדש)** | כל משלם המטבעות הקיים נושא גם **קרב**; להעמיד פנים שהענקה ניקתה גל היה שקר ביומן ובפיד |
| ⬆ +1 רמה לכל החלקים | `xp_gained` `{source:'dev'}` + `level_up` | רמות **נגזרות** מ‑XP בכל האפליקציה; אירוע שקובע רמה ישירות היה העובדה היחידה ש‑replay לא יכול לגזור |
| ✨ +250 XP לחלק | `xp_gained` `{source:'dev', parts:{chest:250}}` | אותו אירוע שסט אמיתי כותב |
| 💪 השלמת אימון היום | `xp_gained` + `energy_gained` של בונוס הסיום | **אותו** בונוס, רק מתויג: אותו שומר לפי תאריך, אותו `bonus\|<date>` |
| 🎲 / ⚔️ איפוס | `dev_reset {date, scope, cycle}` **(חדש)** | ראו "מחזורי איפוס" |
| ⏳ זמני קירור | *(אין אירוע)* | קירורים חיים בזיכרון של הזירה בלבד — אירוע עליהם היה עובדה על מסך |
| 🧹 ניקוי | `dev_purge {date}` **(חדש)** | ראו "הביטול" |

### אידמפוטנטיות: לכל הענקה מפתח משלה

להענקת מפתח אין משבצת טבעית (אין תאריך+תרגיל+סט, אין גל, אין רכישה), ולכן היא
נושאת `key: "dev|<uuid>"` וה‑reducer מקפל אותה דרך פנקס: `energyGranted` לאנרגיה
(השומר שכבר היה שם) ו‑`devKeys` ל‑XP ולמטבעות. שני מכשירים שמאחדים יומנים משלמים
כל הענקה **בדיוק פעם אחת**, בשני הכיוונים. `coins_granted` בלי `key` לא משלם
**כלום**: בלי מפתח אין אידמפוטנטיות, ועדיף לא לשלם מאשר לשלם פעמיים.

**הענקת מפתח אף פעם לא סופרת יום אימון.** הרצף הוא המספר האחד שלוח בקרה לא יכול
לזייף, ולכן `xp_gained` עם `dev: true` מדלג על `workoutDays` — בדיוק כמו XP
רטרואקטיבי, ומאותו טעם.

### מחזורי איפוס

"פעם ביום" הופך ל**"פעם במחזור איפוס"**. `dev_reset` נושא את המחזור שהוא **פותח**
(הנוכחי + 1), וה‑reducer מחיל אותו רק כל עוד `devCycles["<scope>|<date>"]` נמוך
ממנו — בדיוק האידיום של `item_upgraded`. לכן:

* שני מכשירים שלחצו "אפס" אופליין כתבו שניהם `cycle: 1`; איחוד בכל אחד משני
  הכיוונים פותח **מחזור אחד** — ניסיון נוסף אחד, לא שניים;
* אחרי איפוס, הריצה הבאה תופסת את המשבצת הריקה, ועד האיפוס הבא הכלל שוב חוסם;
* איפוס לא מחזיר אנרגיה ולא מוחק היסטוריה: הוא מנקה בדיוק את הרשומות שכלל
  "פעם ביום" קורא (`daily.runs[date]`, וכל `"<date>|…"` בדו־קרבות).

### הביטול: 🧹 ניקוי שיפורי מפתח

הכפתור מחזיר את הדמות למצב שהיה אילו אף הענקה לא קרתה. הוא לא הענקה נגדית — הוא
עובד **בהשמטה**:

```
liveEvents(log):  ממיינים ב‑(ts, id) → מוצאים את ה‑dev_purge האחרון
                  → כל אירוע dev שלפניו פשוט לא מקופל
```

ולכן התוצאה **זהה בייט‑בייט** ליומן שמעולם לא היו בו הענקות (זו בדיוק ההצמדה
ב‑`tests/dev.test.ts`: שוויון עמוק מול rebuild ביקורת). מכאן גם השאר בחינם:
הפעולה **אידמפוטנטית** (ניקוי שני מכסה את אותו כלום), **מתכנסת במיזוג** ("לפני"
היא תכונה של *קבוצת* האירועים), ו**הענקה שנכתבה אחרי** הניקוי עובדת כרגיל —
לנקות, ולהמשיך לבדוק.

**מה הוא לא מבטל:** אירועים אמיתיים שקרו בזמן שההענקות היו בתוקף. מטבעות שנוצחו
בקרב שרק אנרגיית מפתח מימנה — **נשארים**. הביטול מסיר **הענקות, לא היסטוריה**;
היומן נשאר היומן.

בנתיב החי הכתיבה עוברת ב‑`commitRebuild`: הקיפול הרגיל רק **מוסיף** את ההשפעה של
אירוע, וזה בדיוק לא מה שצריך כשאירוע אומר "אירועים שכבר קופלו מפסיקים להיחשב".
לבטל אותם אחד‑אחד היה מחייב reducer הפוך שני שיישאר מסונכרן לנצח; לשחזר מהיומן
משתמש ב‑reducer היחיד שכבר סומכים עליו ונוחת בדיוק איפה שמכשיר חדש היה נוחת —
בדיוק המהלך של `ensureGameState`. המחיר הוא קיפול מלא של היומן, על כפתור שנלחץ
ביד וממילא מצייר מחדש את המסך.

### `window.gymDev`

אותו אובייקט בדיוק שהכרטיס מפעיל (אין מימוש שני):

```js
gymDev.addEnergy(100)   gymDev.addCoins(500)     gymDev.addXp('chest', 250)
gymDev.levelAllParts(1) gymDev.completeToday()   gymDev.resetDaily()
gymDev.resetDuels()     gymDev.resetCooldowns()  gymDev.purge()
gymDev.state()          gymDev.help()            // עברית + English
```

`state()` מחזיר **עותק קפוא** ולא את האובייקט החי — "בוא נציץ במצב" לא אמור להיות
דרך להשחית אותו. `resetCooldowns()` הוא היחיד שלא כותב כלום, והוא שימושי בעיקר
בקונסולה **בזמן קרב**: יציאה מהזירה מאפסת קירורים ממילא.

### רוח עם 🛠

`GhostPayload` קיבל שדה אופציונלי `dev`, שמוצהר **רק כשהוא true** — כך שמי שלא
נגע במצב מפתח מפרסם בדיוק את המטען שתמיד פרסם. הוא נכנס גם ל‑`ghostHash`, ולכן
הדלקת הדגל (הענקה ראשונה) וכיבויו (ניקוי) **מפרסמים מחדש** במקום להשאיר תווית של
אתמול. בכרטיס היריב זו 🛠 קטנה ליד השם, עם ההסבר על ה‑tooltip. זו **תווית ותו
לא**: היא לא משנה סטטיסטיקה, לא זרע ולא פרס (הפרס תלוי ב**תוצאה** וב‑`BALANCE.duel`
בלבד, לא במי שנלחמתם בו).

### תאימות לאחור: לקוח ישן

הכלל המוכר — ה‑reducer מתעלם מסוגי אירועים שאינו מכיר (`default: break`) — עדיין
מגן, אבל צריך לומר בקול מה המשמעות כאן: לקוח שנבנה **לפני** Phase 9 יתעלם
מ‑`coins_granted`, מ‑`dev_reset` ומ‑`dev_purge`. כלומר הענקת מטבעות לא תופיע שם,
איפוס שנעשה במכשיר חדש לא ייפתח שם, וניקוי לא ינקה שם (הענקות אנרגיה ו‑XP דווקא
כן יגיעו — הן אירועים ותיקים עם שדה נוסף). היומן עצמו לא ניזוק בשום מקרה: האירועים
נשמרים, מסתנכרנים, ומתקפלים נכון ברגע שהלקוח מתעדכן. ההנחה המקובלת היא שכל
המכשירים של אותו חשבון על הבילד הנוכחי.

### v9 → v10

`GAME_STATE_VERSION` עלה ל‑10 ונוספו `devUsed`, `devKeys` ו‑`devCycles`. אותו

## סטטיסטיקות (📊 `SS`)

תת‑הטאב השלישי של מרכז ⚙️ הגדרות — **הגדרות · היסטוריה · 📊 סטטיסטיקות**.
היסטוריה היא הרישום ("מה עשיתי ב‑4 בחודש"), וזה מה שהרישום **מסתכם** אליו.

`src/core/stats.ts` הוא **פונקציות טהורות בלבד**: אין DOM, אין `Date.now()` ואין
store — `today` מוזרק תמיד מבחוץ, בדיוק כמו בשאר הליבה. `src/ui/stats.ts` רק
מצייר, ו‑`styles/stats.css` נותן לו צבעים מה‑tokens הקיימים.

### שני מקורות, וכלל אחד ל‑🛠 מצב מפתח

| מקור | מה נגזר ממנו | מה עם הענקות מפתח |
|---|---|---|
| **הסשנים** (`state.sessions`) | טונאז׳, אימונים, סטים, חזרות, שניות פלאנק, הגרף השבועי, לוח האימונים, איזון חלקי הגוף, שיאים לכל תרגיל, ורוב המוזרויות | **לא רלוונטי בעיקרון**: פאנל המפתח כותב אירועי XP/אנרגיה/מטבעות ו**לעולם לא סט**. אין דרך שהענקה תנפח מספר אימון |
| **יומן האירועים** | שיאים אישיים (`pr_achieved`), דרגת רצף, גלים, בוסים, אתגרים יומיים, דו־קרבות, מטבעות ואנרגיה לכל החיים, סה״כ XP | **שני מסננים**, שניהם ב‑`trainingEvents`: `liveEvents` (מוריד כל הענקה ש‑`dev_purge` ביטל — בדיוק כמו שמצב המשחק מקפל) ואז דחייה של כל אירוע שעדיין נושא `dev: true`, כולל `coins_granted` כולו |

מה ש**כן** נספר: מטבעות שנצברו בקרב ששולם באנרגיית מפתח. הקרב הזה קרה —
הביטול מבטל **הענקות**, לא היסטוריה. זה בדיוק מה ש‑`liveEvents` מבטיח גם
לשכבת המשחק, ולכן שני המסכים לא יכולים לחלוק זה על זה.

**רק סטים מסומנים ✓.** משקל שהוקלד בשורה שלא סומנה הוא כוונה, לא הרמה — וזה גם
הכלל שמנוע ה‑XP משלם לפיו, ולכן "סה״כ הרמתם" לא יכול לסתור את מה שהדמות קיבלה
עליו XP. משקלים הם **מחרוזות** (`"42.5"`, `"42,5"`, `""`, `"abc"`) ומפורסרים
דרך `toNumber`; תרגילי משקל גוף ותרגילי זמן (`שניות`) תורמים **חזרות ושניות**,
אף פעם לא קילוגרמים.

### מה יש על המסך

1. **💪 סה״כ הרמתם** — Σ משקל×חזרות, מספר ענק, ומתחתיו סולם השוואות: 🦍 גורילה
   (160), 🐄 פרה (750), 🚗 מכונית (1,400), 🐘 פיל אפריקאי (6,000), 🚌 אוטובוס
   (12,000), 🐋 לווייתן כחול (150,000), 🗼 מגדל אייפל (10,100,000). הכותרת מציגה
   את **השלב הכבד ביותר שכבר עברתם** (אף פעם לא עיגול כלפי מעלה של שלב שלא
   הושג), ולצידה "עוד X ק״ג ל…". הסולם מתחיל קטן בכוונה: אימון ראשון הוא כמה
   מאות ק״ג, וסולם שמתחיל בפיל היה מציג "0.0 פילים" חודש שלם.
2. **📋 המספרים היבשים** — אימונים, סטים, חזרות, שניות פלאנק, שיאים אישיים,
   אימונים לשבוע (מאז הראשון ועד **היום**, לא עד האימון האחרון), דרגת רצף
   נוכחית ושיא, והיום הכי חזק בשבוע.
3. **📈 טונאז׳ שבועי** — 12 שבועות (ראשון–שבת), SVG מוטבע, סדרה אחת ולכן בלי
   מקרא; שיא/נמוך/השבוע החי ככיתוב HTML מתחת לגרף, בלי צירים בכלל.
4. **🗓 לוח האימונים** — 16 שבועות בסגנון GitHub, עוצמה לפי מספר הסטים ביום
   (0 · 1–5 · 6–10 · 11–15 · 16+).
5. **⚖️ איזון בין חלקי הגוף** — שישה פסים אופקיים לפי `bodyPartWeights`, אותה
   חלוקה שמנוע ה‑XP משלם לפיה, עם תגיות "הכי חזק" / "הכי מוזנח".
6. **🥇 השיאים שלכם** — שמונת התרגילים עם הכי הרבה עומס: הסט הכי טוב, הסט

7. **🎮 שכבת המשחק** — גלים, מיני‑בוסים, בוסי עולם, אתגרים, W‑L בדו־קרבות,
   מטבעות ואנרגיה — ועוד המרה אחת מטופשת: **250 ⚡ = טעינת טלפון אחת**.
8. **🎲 סטטיסטיקות מוזרות** — הזמן מתחת לטיימר המנוחה (הערכה: כל סט מסומן ×
   זמן המנוחה של התרגיל שלו), הסט הכבד ביותר אי פעם, XP לכל טונה, התרגיל הכי

### למה הפסים נמדדים ב"נקודות עומס" ולא בק״ג

ליבה מתאמנת כמעט רק במשקל גוף ובפלאנקים. סרגל בקילוגרמים היה מצייר אותה כאפס
קבוע — כלומר אומר משהו **לא נכון** על האימון. לכן הפסים משתמשים ביחידת ה‑volume
שכבר קיימת באפליקציה (`core/xp.ts#setVolume`: ק״ג×חזרות כשיש משקל, ואחרת חזרות
או שניות) — אותה יחידה שהשיאים וה‑XP נמדדים בה — וכל שורה מדפיסה **גם** את
הקילוגרמים שלה לצד הפס, ששם הטונאז׳ כן כנה.

### מוסכמות התרשימים (נקבעו כאן, לא היו קודם)

* **SVG מוטבע, בלי שום ספריית גרפים.** הבנייה היא קובץ יחיד עצמאי
  (`npm run verify`) — ספריית גרפים הייתה התלות הראשונה בזמן ריצה.
* **גוון אחד לכל תרשים.** עוצמה = `--accent` שמתחזק (חמישה שלבים של אותו כחול
  בלוח), אף פעם לא קשת צבעים; `--ok` / `--warn` שומרים על המשמעות שכבר יש להם
  (טוב / דורש תשומת לב) ולא הופכים ל"סדרה 2".
* **הזמן זורם ימינה→שמאלה.** זו אפליקציה בעברית: הקריאה מתחילה מימין, ולכן גם
  הזמן. בגרף השבועי השבוע הישן ביותר בקצה **הימני** והשבוע החי בקצה השמאלי;
  בלוח האימונים העמודה השמאלית ביותר היא **השבוע הזה**, בדיוק במקום שבו העין
  נוחתת אחרונה — ואותיות הימים (א–ש) יושבות מימין לרשת, כי שם שורה עברית
  מתחילה. ל‑SVG אין `direction`, ולכן שני התרשימים מחשבים את קואורדינטת ה‑x
  בסדר הזה במפורש.
* **סימנים דקים, כרום נסוג.** קו 2px, שטח במילוי 12%, נקודת קצה ≥8px עם טבעת
  בצבע הכרטיס, קו בסיס דק ואחיד, ואפס צירים. הכיתובים הם **HTML סביב ה‑SVG**
  ולא `<text>` בתוכו: הכיתובים בעברית, ל‑SVG אין פריסת bidi ששווה לסמוך עליה,
  וכיתוב HTML נשאר ניתן לבחירה וגדל עם גודל הגופן של המשתמש.
* **שום דבר לא אינטראקטיבי.** את הכרטיסים קוראים, לא לוחצים — ולכן אין יעד מגע
  שאפשר לפספס בטלפון. לכל תא ולכל נקודה יש `<title>` מובנה, שהוא ה‑tooltip
  במחשב והשם הנגיש בכל מקום.
* **`prefers-reduced-motion`** — האנימציה היחידה היא הופעת שטח הגרף, והיא כבויה
  שם (גם גלובלית ב‑`responsive.css` וגם מפורשות ב‑`stats.css`).

### מצב ריק

בלי אף סט מסומן המסך מציג כרטיס אחד ידידותי ("עוד אין מה לספור") ואת כרטיס
המשחק, אם יש בו בכלל סיפור. כל כרטיס בנפרד גם מחזיק מעמד עם נתונים דלילים:
שבוע בלי אימון הוא **אפס אמיתי** ולא חור בגרף, תרגיל עם סט אחד מציג "—" במקום
"צמיחה: +0%", ותרגיל שהתוכנית כבר לא מכירה נספר בסך הכול אבל לא משויך לחלק גוף
— אין יותר מי שיודע לאיזה.

## אנימציות (CSS בלבד)

כל התנועה בזירה ובמסך הדמות היא **keyframes של CSS על קבוצות ה‑SVG**
(`styles/anim.css`). ה‑JS לא מזיז שום דבר: לולאת הקרב רק מדליקה ומכבה מחלקה
קצרת‑חיים על ספרייט. אין אירוע חדש, אין שעון שני, ו‑`core/combat.ts` הדטרמיניסטי
לא יודע שכל זה קיים.

### מה זז

| מתי | מה |
|---|---|
| תמיד | **נשימה** — הטורסו של הדמות (מסך דמות + הזירה) עולה ויורד ב‑1.5%, והחזה ב‑3.5% |
| תמיד | **ריחוף האויב** — כל ספרייט מרחף בקצב משלו |
| הדמות תוקפת | `.anim-attack` — זינוק לכיוון האויב ורתיעה |
| האויב נפגע | `.anim-hit` — הדיפה + הבזק (`filter: brightness`) |
| האויב תוקף | `.anim-attack` על האויב + `.anim-hurt` על הדמות (רתיעה והבזק) |
| האויב מת | `.anim-die` — קריסה, סיבוב ודעיכה, לפני שהגל הבא נולד |
| מהלך על | `.anim-super` — כיווץ (טעינה) ואז קפיצת קנה מידה עם זוהר, מעל רעידת המסך שכבר הייתה |
| בוס עולם נפל | `.anim-victory` — הדמות קופצת וקבוצת `data-part="arms"` מתרוממת (פוזת ניצחון) |
| מיומנות הופעלה | `.anim-skill` — פוזה קצרה, ‎`sk-<part>`‎ מנפח את השריר שפתח אותה, ו‑`fx-<skill>` צובע את שכבת האפקטים |
| עליית רמה | `.leveled` על ה‑SVG — זוהר זהב קצר, **מעל** ה‑pulse הקיים של החלק שגדל |

### הכללים שהאנימציות מצייתות להם

* **`prefers-reduced-motion` — כלל אחד, לא שניים.** הכלל הגלובלי
  `*{animation:none!important}` ב‑`responsive.css` מכבה את הכול. לכן כל אנימציה
  כאן **מתחילה ונגמרת** ב‑transform ניטרלי ובאטימות מלאה: כשמכבים אותה האיבר
  פשוט יושב בפוזת המנוחה שלו, והמחלקות שהלולאה מדליקה הן תוויות חסרות משמעות.
  רעידת המסך היא היחידה שגם נחסמת ב‑JS — היא מזיזה את הכרטיס כולו ולא ספרייט
  בודד.
* **בלי צבעים קשיחים.** רק `transform`, `opacity` ו‑`filter` (`drop-shadow` /
  `brightness`). ה‑palette של הדמות חיה ב‑custom properties
  (`--ch-body`, `--ch-skin`…), ואילו נגענו בהן — סקין היה קופץ בחזרה לכחול של
  הגיבור המקורי לשנייה. הזוהר הזהוב של עליית רמה הוא `drop-shadow`, לא צבע.
* **`transform-origin` מפורש.** לקבוצת SVG יש ברירת מחדל של ראשית ה‑viewBox, לא
  של הצורה, ולכן כל קבוצה מונפשת מצהירה `transform-box:fill-box` ומקור מפורש —
  בלי זה קנה מידה של 3% נראה כמו קפיצה לרוחב הזירה.
* **כיוון מודע ל‑RTL.** transform לא מושפע מ‑`direction`, אז "לכיוון האויב" הוא
  מספר: `--to-foe` / `--to-hero` על `.bt-arena` (‎-1/1 ב‑RTL, הפוך תחת
  `[dir="ltr"]`).
* **תזמונים מסונכרנים עם הסימולציה.** `ANIM` ב‑`ui/battle.ts` גוזר אותם
  מ‑`BALANCE` ומפרסם אותם ל‑CSS כ‑custom properties: אנימציית המוות חייבת
  להסתיים בתוך `spawnDelayMs` (אחרת גופה עוד קורסת כשהיורש נולד), והזינוק בתוך
  `attackIntervalMinMs` (אחרת זינוקים של דמות מהירה נערמים). הזינוק מופעל **לכל
  אירוע התקפה**, ולכן הוא עוקב מאליו אחרי מהירות ההתקפה שהכתפיים מכתיבות.
* **לא מסובבים את הלולאה מחדש.** `consume()` כבר מקבל כל
  `hit`/`enemy_hit`/`wave_cleared`/`boss_defeated` — שם, ורק שם, נדלקות המחלקות.

## תוכנית אימונים ניתנת לעריכה

**התוכנית מגדירה את הימים של עצמה** — בין יום אחד לשבעה — ובתוך כל יום הכול
ניתן לעריכה: סטים, חזרות, מנוחה, סדר התרגילים, הסרה והוספה, וגם **תרגילים
משלכם**. גרסה 1 של המסמך הכירה בדיוק שלושה ימים קבועים (A/B/C); גרסה 2 החליפה
את זה במערך מסודר של ימים, כל אחד עם מפתח יציב, שם עברי וימי השבוע שבהם מתאמנים
אותו — כך שפיצול A/B של 4 אימונים בשבוע (א׳ בראשון ורביעי, ב׳ בשלישי וחמישי)
הוא **שני** ימים עם `weeklyTarget: 4`.

### המודל

`PlanDay` הוא `{key, label, weekdays?, exercises}`:

* `key` — **יציב**, וכל השאר מצביע עליו: `Session.day`, מטעני האירועים והטאב
  הפעיל. שינוי שם היום או הזזתו במערך לא מייתמים שום אימון מתועד. יום שהוסב
  מ‑v1 שומר על `A`/`B`/`C`, יום חדש מקבל `d_` + פרוסת uuid. ארבעת מפתחות המסך
  (`CH`, `BT`, `H`, `PL`) שמורים ואסורים כמפתחות יום.
* `label` — שם עברי חופשי ("אימון A", "חלק א׳").
* `weekdays` — `0=ראשון … 6=שבת`. השיבוץ הזה הוא גם **שורת הטאבים** (יום שמתאמנים
  בו פעמיים בשבוע מקבל שני טאבים — ראו "טאבים לפי לוח האימונים"), והטאב שנפתח
  כברירת מחדל הוא זה שמשובץ ליום בשבוע הנוכחי; אם אף יום לא תובע אותו —
  הראשון בתוכנית.
* `weeklyTarget` (ברמת המסמך) — כמה ימי אימון שונים בשבוע נחשבים "שבוע מושלם".
  מכוון בנפרד ממספר הימים: שני אימונים שמתחלפים על פני ארבעה ימים = יעד 4.
  בעורך הוא **נגזר** ולא מוקלד — ראו "היעד השבועי נגזר מהשיבוץ" למטה.

`resolveProgram(plan)` מחזיר את המבנה שהמסכים מציירים ממנו:
`{days: [{key, label, weekdays, day}], weeklyTarget}` — מסודר, כשסדר המערך הוא
סדר הטאבים, ו‑`day` הוא ה‑`Day` המלא (תרגילים + כותרת). חיפוש יום בודד נעשה עם
`dayOf(program, key)`, שמחזיר `null` למפתח שלא קיים — מפתח לא מוכר הוא **נתון**
(תוכנית ממכשיר אחר), לא שגיאה.

`PlanDoc` הוא כל התוכנית באובייקט JSON אחד. שורה ביום היא
`{id, sets, reps, rest}` בלבד: היא **מצביעה** על הגדרת תרגיל ולא מעתיקה אותה.
לכן שורה שמצביעה על תרגיל מובנה דורסת רק את המספרים — שיפור של ההסברים בגרסה
עתידית ישפר גם תוכנית ששמורה מזמן. תרגיל מותאם אישית (`cx_…`) נושא את ההגדרה
שלו, פחות ההסברים — ולכן מסך האימון פשוט לא מצייר עבורו מגירת "הסבר ודגשי
ביצוע" ריקה.

**`plan: null` = התוכנית המקורית.** `resolveProgram(null)` מחזיר את
`BUILTIN_PROGRAM` **עצמו**, וימיו הם אובייקטי `PROGRAM` עצמם — ולכן מי שלא נגע
בעורך מריץ בדיוק את אותו קוד כמו קודם. גם יום שלא נערך בתוך תוכנית אמיתית מוחזר
כאובייקט ה‑`Day` המקורי; רק יום שנערך באמת מקבל משך ומיקוד מחושבים מחדש.

### ניהול הימים בעורך

* **הוספת יום** — כפתור ＋ ליד תת‑הטאבים (עד 7 ימים). היום נולד עם מפתח `d_`
  חדש, בשם "אימון חדש", וגיליון התרגילים נפתח מיד: הוספת יום ובחירת התרגיל
  הראשון שלו הן פעולה אחת ולא שתיים. יום ריק אינו ניתן לשמירה, והשמירה אומרת
  את זה בעברית במקום להיכשל בשקט.
* **שינוי שם** — שדה טקסט בכרטיס היום. הוא נכתב ישירות לטיוטה (רינדור מחדש היה
  גונב את הסמן באמצע מילה), והטאב שמעליו מתעדכן ידנית כדי לא לפגר אחריו.
* **סידור** — ▲/▼ מזיזים את היום במערך, והמערך **הוא** סדר הטאבים.
* **הסרה** — 🗑 עם אישור, שאומר במפורש שאימונים שכבר תועדו ליום הזה **נשארים
  בהיסטוריה**; רק היום יורד מהתוכנית. את היום האחרון אי אפשר להסיר.

### שיבוץ לימי השבוע

שורה של שבעה צ׳יפים (א ב ג ד ה ו ש) לכל יום. **יום בשבוע שייך לכל היותר ליום
אימון אחד**: הדלקה כאן מכבה במקום שממנו הוא נלקח, ושורה שקטה מתחת לצ׳יפים אומרת
מאיפה ("רביעי הועבר מאימון B"). בלי הבלעדיות הזו `defaultDay` היה מטיל מטבע בין
שני ימים שתובעים את אותו יום בשבוע, והיעד השבועי הנגזר היה קטן ממספר האימונים
שהוא מתאר. יום שנשאר בלי ימי שבוע פשוט לא נפתח אוטומטית — והשדה יורד מהמסמך
לגמרי, בדיוק כפי שבנאי הימים כותב אותו, כדי שמסמך יישאר שווה לעצמו אחרי שמירה.

### היעד השבועי נגזר מהשיבוץ

`deriveWeeklyTarget(days)` ב‑`core/plan.ts` הוא **מקור האמת היחיד**, והעורך רק
מציג אותו: "יעד שבועי: N ימי אימון (משפיע על רצף השבוע המושלם)".

| מצב | היעד |
|---|---|
| יש שיבוץ | מספר ימי השבוע ה**שונים** שהתוכנית תובעת (הצ׳יפים בלעדיים, ולכן זה בדיוק "כמה פעמים בשבוע אני בחדר כושר") |
| אין שיבוץ בכלל | `min(מספר הימים, 3)` — אימון אחד לכל יום בתוכנית, בתקרה של ברירת המחדל |
| מפת A/B/C המובנית | 3 — ראו מיד למטה |

מפת ברירת המחדל (`[0,1] / [2,3] / [4,5,6]`) מכסה את כל שבעת ימי השבוע בשלושה
אימונים, כי היא מפת **ניתוב** שנועדה לפתוח טאב בכל יום — לא לוח אימונים. ספירה
שלה הייתה הופכת "לפתוח את העורך ולשמור" לקפיצה מ‑3 ל‑7, ולכן היא מזוהה במפורש
ומוחזרת ל‑3. ברגע שנוגעים בצ׳יפים, המפה היא לוח אמיתי ונספרת ככזה.

### טאבים לפי לוח האימונים

`scheduleTabs(program)` ב‑`core/plan.ts` הוא **מקור האמת היחיד** לשורת טאבי
האימון, והוא מציג את **השבוע** ולא את רשימת הימים: תוכנית A/B שמתאמנים בה
בראשון+רביעי / שלישי+חמישי מקבלת **ארבעה** טאבים — ראשון(א), שלישי(ב), רביעי(א),
חמישי(ב) — ממוינים לפי יום בשבוע, כשהכותרת היא שם היום והשורה הקטנה היא שם
האימון. יום בלי שיבוץ מקבל טאב יחיד (הכיתוב הנוכחי שלו) בסוף השורה.

היוצא מן הכלל הוא **מפת הניתוב** המובנית (`[0,1] / [2,3] / [4,5,6]`, שכל תוכנית
שעברה מ‑v1 יורשת): היא מזוהה באותו predicate שהיעד השבועי משתמש בו
(`isBuiltInWeekdayMap`) ונשארת **שלושה** טאבים — פריסה שלה הייתה מנפחת תוכנית של
שלושה ימים לשבעה טאבים, בדיוק כמו שספירה שלה הייתה מנפחת את היעד השבועי ל‑7.

* **`viewId`** — `UiState.view` שומר `dayKey` כשליום יש טאב אחד, ו‑`dayKey@יום`
  (למשל `d_a1b2@3`) כשהוא נפרס לכמה. כל ה‑view‑ים שנשמרו אי פעם (`A`, `d_…`)
  נשארים תקפים; `normalizeUi` מקבל את שתי הצורות ונופל לטאב ברירת המחדל אחרת.
* **ה‑`@` לא יורד מתחת ל‑UI.** `ui/app.ts` הוא המודול היחיד שמחזיק את הצורה
  המורכבת, ו‑`viewDayKey(view)` מקלף אותה לפני מסך האימון, הכותרת, ה‑session וכל
  אירוע. שני טאבים של אותו אימון = אותו יום, אותו session, אותם `set_*` — אין
  צורת אירוע חדשה ואין צורת session חדשה.
* **ברירת המחדל** — `defaultTabView(plan, now)` בוחר את הטאב המשובץ להיום (יום
  רביעי → טאב "רביעי" של חלק א׳), ואם אין כזה נופל בדיוק כמו `defaultDay`.
* **שורה שנגללת** — הטאבים האלה הם **שורת תת‑הטאבים** של מרכז 🏋️ אימון (ראו
  "ניווט דו‑שכבתי"), ולכן ארבעה מופעים כבר לא דוחפים כלום החוצה: דמות, קרב
  והיסטוריה עברו למרכזים שלהם. רק מעל **ארבעה** תת‑טאבים — תוכנית של 5–7 ימים —
  השורה נגללת אופקית (`.sub-row.scroll` ב‑`styles/tabs.css`) במקום לרסק אותם;
  הטאב הפעיל נגלל לתצוגה בכל render וכל טאב נשאר ≥40px. השורה הראשית לעולם לא
  נגללת, כי היא תמיד אותם שלושה מרכזים.

### תוכניות מוכנות

`📋 תוכניות מוכנות` פותח גיליון עם מסמכי `PlanDoc` **שלמים** (`data/presets.ts`)
— לא תבניות. הבחירה מבקשת אישור, מחליפה את ה**טיוטה** (שום דבר לא נשמר עד 💾),
ומשם זו שמירה רגילה לגמרי עם אירוע `plan_updated` אחד.

| תוכנית | מה יש בה |
|---|---|
| **היפרטרופיה 3 ימים** | התוכנית המובנית A/B/C — שקולה ל"איפוס לתוכנית המקורית" |
| **תוכנית A/B — 4 ימים** | שני אימונים על פני ארבעה ימים: חלק א׳ (רגליים, חזה, כתפיים ויד אחורית) בראשון וברביעי, חלק ב׳ (גב ויד קדמית) בשלישי ובחמישי · 8 תרגילים ליום · מנוחה 90 שנ׳ בתרגילים מורכבים ו‑60 שנ׳ בבידודים · יעד שבועי 4 |

מפתחות הימים **נטבעים מחדש בכל בחירה** (`d_…`): שני מכשירים שבחרו את אותה
תוכנית מוכנה לא ממזגים בטעות את ימיהם לאחד, ואימונים שתועדו תחת הימים הקודמים
ממשיכים להצביע על המפתחות הישנים במקום לקבל שם של תוכנית שלא התאמנו בה.

### ספריית התרגילים

מלבד תרגילי התוכנית המובנית יש **ספריית תרגילים** (`EXTRA_EXERCISES` ב‑
`data/program.ts`): סקוואט בסמית׳, פשיטת/כפיפת ברכיים במכשיר, הרחקה לצדדים,
פשיטת מרפקים בפולי, פולי עליון באחיזה צרה, פייס פול, הרמת שכמות ופטישים. הם
תרגילים מובנים לכל דבר — אותה כתיבה מדריכה, אותו `bodyPart`/`split` ואותו
`findExercise` — והם פשוט לא יושבים בתוכנית ברירת המחדל. הם מוצעים בגיליון
ההוספה של העורך ומשמשים את התוכנית המוכנה. הם נשמרים **מחוץ** ל‑`PROGRAM`
בכוונה, כדי ש‑`tests/program.test.ts` ימשיך להשוות את `PROGRAM` לקובץ הישן
מילה במילה.

### הסבה מ‑v1 ל‑v2

`normalizePlanDoc` מקבל את **שתי** הגרסאות: מסמך v1 (או מטען `plan_updated`
שנכתב על ידי לקוח ישן, ומסמך בלי `version` בכלל) מוסב בקריאה למערך של שלושה
ימים — מפתחות `A`/`B`/`C`, השמות המקוריים, ימי השבוע `[0,1] / [2,3] / [4,5,6]`
ו‑`weeklyTarget: 3`. אלה בדיוק הטווחים ש‑`defaultDay` השתמש בהם מאז ומתמיד
(ראשון־שני → A, שלישי־רביעי → B, חמישי־שבת → C), ושם היום נגזר מהיום **הראשון**
בטווח — כלומר ראשון/שלישי/חמישי, בדיוק כמו `DAY_NAMES`. לכן מי ששמר תוכנית לפני
השדרוג לא רואה שום שינוי: אותם טאבים, אותם שמות, אותו טאב שנפתח בכל יום בשבוע.
מסמך מגרסה **עתידית** נדחה ל‑`null` (= התוכנית המובנית), כמו קודם.

> **לקוחות מעורבים על אותו חשבון:** לקוח ישן שיקפל `plan_updated` עם מסמך v2
> יראה `version: 2`, ידחה אותו ויציג את התוכנית המובנית — לא יאבד מידע, אבל גם
> לא יראה את התוכנית החדשה. הפתרון הוא רענון של ה‑PWA בכל מכשיר; לא ניסינו
> תאימות עמוקה יותר, כי היומן עצמו נשמר ללא שינוי והשדרוג פותר הכול.

### שמירה ומיזוג

שמירה = **אירוע `plan_updated` אחד** שנושא את המסמך כולו. הכרעה בין מכשירים היא
לכן סדר הקיפול עצמו: **האחרון ב‑`(ts, id)` מנצח**, ו‑`data_cleared` מאפס את
התוכנית ל‑`null`. אין מה ליישב שדה‑שדה, ומיזוג בשני הכיוונים נותן אותה תוצאה.
`rev` נספר לצורכי תצוגה בלבד — הסמכות היא היומן.

### היסטוריה שורדת כל עריכה

XP נשמר לפי **מזהה תרגיל** ולא לפי מיקום: `best[exId]`,
`granted[date|exId|setIndex]` ו"האימון הקודם" לא יודעים באיזה יום התרגיל יושב,
או אם הוא יושב באיזשהו יום בכלל. אפשר לסדר מחדש, להסיר ולהחזיר — שום שיא לא
הולך לאיבוד. מסכי ההיסטוריה והיומן מציגים תרגילים לפי מזהה גם שנים אחרי, ולכן
הם משתמשים ב‑`makeResolver(state.plan)` ונופלים חזרה למזהה הגולמי אם התרגיל כבר
לא קיים.

**גם שם היום נפתר ככה.** אימון מתועד נושא את מפתח היום שבו הוא נרשם, והמפתח
הזה עלול להיות יום ששונה שמו, יום שהוסר מהתוכנית או יום שנוצר במכשיר אחר.
`dayLabelOf(program, key)` יורד בסולם: השם שבתוכנית → השם המובנה אם המפתח הוא
עדיין `A`/`B`/`C` (אימון מלפני שנגעתם בעורך) → "אימון" ניטרלי. כיתוב יום השבוע
ושורת המיקוד מוצגים רק כשהיום עצמו עדיין קיים — הם **לא** מושאלים מיום אחר, ואף
פעם לא מוצג מפתח `d_…` גולמי. אותו כלל חל על יומן ההרפתקה: `workout_finished`
נושא את המפתח, והמסך הוא זה שיודע לתת לו שם ("אימון הושלם במלואו · חלק א׳").

### מסך העריכה (`PL`)

`PL` הוא מסך אמיתי אבל **לא טאב**: הפעולה היומיומית בשורת האימון היא בחירת יום
אימון, ועורך שיושב שם היה גונב לה מקום. הוא שייך למרכז 🏋️ **אימון**
(`hubOf('PL') === 'TR'`) — הטאב הראשי נדלק כשהוא פתוח, אבל אף תת‑טאב לא —
והכניסה היא כפתור ⚙️ בכותרת מסך האימון (שם מגלים שרוצים לשנות את היום) וכרטיס
התוכנית במסך ⚙️ **הגדרות** (שם יושבות שאר פעולות הנתונים). היציאה מחזירה למסך
שממנו נכנסתם, כולל חזרה למסך ההגדרות.

בתוך המסך, מלמעלה למטה: תת‑טאב לכל יום שהתוכנית מגדירה (ו‑＋ להוספת יום), כרטיס
היום — שם, ▲/▼ להזזתו, 🗑 להסרתו, שבעת צ׳יפי ימי השבוע והיעד השבועי הנגזר — ואז
שורה לכל תרגיל עם ▲/▼ לסידור, 🗑 להסרה (עם אישור),
ושלושה שדות — סטים, חזרות, מנוחה. `+ הוספת תרגיל` פותח גיליון תחתון עם ספריית
התרגילים המובנים שעדיין לא ביום, התרגילים המותאמים, וטופס ✨ ליצירת תרגיל חדש:
שם בעברית (חובה), אנגלית (רשות), חלק גוף עיקרי, חלק גוף משני אופציונלי
(שמתורגם לפיצול 70/30 בדיוק כמו בתרגילים המובנים), יחידת מדידה וציוד.

**העריכה כולה בטיוטה בזיכרון** עד ל‑💾 שמירה. שמירה חיה בכל הקשה הייתה מציפה את
היומן (ואת תור הסנכרון) בעשרות מסמכים מלאים לכל סשן עריכה, ובעיקר —
הייתה הופכת יום חצי‑מסודר לתוכנית האמיתית ברגע שמישהו מתפזר באמצע.
`איפוס לתוכנית המקורית` שומר `plan: null` (עם אישור), וגם זה אירוע — מכשיר אחר
חייב ללמוד על האיפוס. `📋 תוכניות מוכנות` מחליף את הטיוטה בתוכנית מוכנה, וגם הוא
לא נוגע בדיסק עד ה‑💾.

יציאה מהעורך לא יכולה לנחות על יום מת: `setView` מתרגם כל view לטאב אמיתי
(`resolveTab`) — מפתח יום שהתוכנית כבר לא מכירה נופל לטאב ברירת המחדל שלה, ומפתח
יום שנפרס בינתיים לכמה טאבים נוחת על המופע של היום — מה שמכסה גם משיכה מהענן
שמחקה או שיבצה מחדש יום במכשיר אחר.

### ולידציה

`savePlan` מסרב לשמור (ולא כותב שום אירוע) על יום ריק, סטים מחוץ ל‑1–10, מנוחה
מחוץ ל‑15–600 שניות, שדה חזרות ריק, תרגיל כפול ביום, תרגיל מותאם בלי שם, יום
בלי שם, מפתח יום פסול או כפול, תוכנית בלי ימים או עם יותר משבעה, ויעד שבועי
מחוץ ל‑1–7. בקריאה, `normalizePlanDoc` **מתקן** במקום לדחות: מספרים נחתכים
לטווח, שורות שמצביעות לשומקום מושמטות, ימי שבוע פסולים נופלים, מפתחות כפולים
מאוחדים, יום מובנה שנשאר ריק חוזר ליום המובנה, ומסמך שלא נשאר בו אף יום חוזר
לשלושת הימים המובנים — מסך אימון ריק הוא לא תוצאה אפשרית.

## סנכרון בענן וחשבון Google (אופציונלי)

הפיצ׳ר הזה **כבוי כברירת מחדל** ואינו משנה דבר עד שממלאים את ההגדרות. בלי
הגדרה (וגם ב‑`file://` תמיד) `syncConfigured()` מחזיר `false`, שום לקוח לא נוצר,
שום מאזין לא נרשם וכרטיס החשבון פשוט לא קיים במסך. האפליקציה נשארת בדיוק
האפליקציה האופליינית שהייתה.

### הרעיון בשורה אחת

המודל כבר מוכן לסנכרון מהיסוד: כל כתיבה היא אירוע ב‑append‑only log, והמצב הוא
פונקציה טהורה של היומן. לכן:

> **סנכרון = איחוד קבוצות האירועים + `rebuildFromEvents`.**

אין פתרון קונפליקטים ואין ממשק מיזוג, כי אין קונפליקטים: סדר הקיפול `(ts, id)`
הוא תכונה של **הקבוצה**, ולכן שני מכשירים שמחזיקים את אותם אירועים מגיעים למצב
זהה בייט‑בייט — לא משנה מי ראה מה קודם (`tests/merge.test.ts`).

### מה קורה בפועל

| רכיב | תפקיד |
|---|---|
| `src/sync/config.ts` | ה‑URL וה‑anon key + `syncConfigured()` — **מתג ראשי** |
| `src/sync/backend.ts` | הממשקים `SyncBackend` + `AuthPort` — התפר שהבדיקות מזריקות לתוכו |
| `src/sync/meta.ts` | פנקס המנוע ב‑`gymrpg_sync_v1`: deviceId, cursor, outbox, userId, lastSyncAt, ושם הלוחם + fingerprint הרוח |
| `src/core/ghost.ts` | תצלום הדמות לדו־קרב רפאים, והנרמול העוין שלו |
| `src/core/handle.ts` | שם הלוחם: צורה קנונית, ולידציה ומפתח היומן |
| `src/sync/engine.ts` | לולאת ה‑write‑behind: outbox → push → pull → merge |
| `src/sync/supabaseBackend.ts` | **המודול היחיד** שמייבא `@supabase/supabase-js` |
| `src/sync/account.ts` | כרטיס החשבון במסך ההגדרות |
| `src/storage/merge.ts` | האיחוד עצמו: `mergeIntoStore` (משיכה) ו‑`mergeImport` (ייבוא מצטבר) |
| `supabase/schema.sql` | כל צד השרת. אין קוד שרת משלנו |

**מחזור אחד:** שטיפת ה‑buffer → דחיפת ה‑outbox במנות של 500 → משיכת עמודים של
1000 לפי `seq` → איחוד → `rebuildFromEvents` → `replaceAll` → ציור מחדש.
טריגרים: כתיבה מקומית (debounce 500ms), `online`, חזרה לטאב, כל 60 שניות בזמן
שהטאב גלוי, והתחברות. כישלון → backoff מעריכי (1, 2, 4… עד 5 דקות) שמתאפס
בהצלחה וב‑`online`.

**קיבוץ הקשות:** כל הקשה בשדה משקל היא אירוע `set_logged` מקומי — זה נשאר. אבל
ה‑payload הוא תצלום מלא (`w` **וגם** `r`), ולכן ל‑outbox נכנס רק האירוע האחרון
לכל `date|exId|setIndex`. הקלדת "42.5" = 4 אירועים מקומיים, שורה **אחת** בענן.

**למה אין לולאה אינסופית:** מיזוג נוחת דרך `replaceAll`, שבמכוון **אינו** משדר
ל‑`subscribeEvents`, והמנוע לא מוסיף שום אירוע משלו כשהוא ממזג. לכן אירוע
שנמשך מהשרת לא יכול להיחשב בטעות לכתיבה מקומית ולחזור החוצה.

### מה משתנה כשמחוברים

* **🗑 מחיקה** הופכת לפעולה על **כל החשבון**: אירוע `data_cleared` מסונכרן
  ומתקפל בכל מכשיר כמחיקה. הנוסח בדיאלוג אומר את זה במפורש.
* **⬆ ייבוא JSON** הופך ל**מצטבר** (`mergeImport`): קובץ הגיבוי מתאחד עם היומן
  המקומי ונרשם `data_merged`, במקום להחליף. ההחלפה ההרסנית נשארת רק כשמנותקים —
  שם היא באמת "שחזור גיבוי".
* **התנתקות** מוחקת רק את פנקס הסנכרון. כל האימונים נשארים במכשיר.

### הקמה (חד‑פעמית, ידנית)

ארבעה שלבים, בערך עשר דקות. **עד שהם נעשים — ואם לא עושים אותם בכלל — הכול
עובד בדיוק כמו קודם**, פשוט בלי ענן. אין כאן שום פקודה שהריפו מריץ בשבילכם:
Supabase ו‑Google הן קונסולות של מישהו אחר.

#### 1 · פרויקט Supabase והסכימה

1. [supabase.com](https://supabase.com) → **New project** (התוכנית החינמית
   מספיקה בגדול). לבחור אזור קרוב ולשמור את סיסמת מסד הנתונים.
2. **SQL Editor → New query** → להדביק את **כל** `supabase/schema.sql` →
   **Run**. הסקריפט אידמפוטנטי: הרצה חוזרת אינה עושה כלום.
3. **Table Editor** → אמורות להופיע `events`, `sync_counters` ו‑`ghosts`, ריקות.
4. **Project Settings → API** → להעתיק את **Project URL**
   (`https://<ref>.supabase.co`) ואת מפתח ה‑**anon / publishable**.

> ### ⬆️ שדרוג פרויקט קיים — דו־קרב רפאים
>
> אם הפרויקט שלכם כבר רץ מלפני Phase 8, **אין צורך להריץ את כל הקובץ מחדש**
> (אם כי זה בטוח — הכול אידמפוטנטי). מספיק להדביק את הבלוק שבסוף
> `supabase/schema.sql` שמסומן:
>
> ```sql
> -- =====================================================================
> --  GHOST DUEL (run this block if upgrading)
> -- =====================================================================
> ```
>
> הוא יוצר את הטבלה `public.ghosts` (שורה אחת למשתמש, `handle` ייחודי,
> `payload` מסוג jsonb), מפעיל RLS ומגדיר שלוש מדיניויות: **קריאה לכל משתמש
> מחובר** (זה מנגנון השיתוף — ראו את ההערה בקובץ על מה נחשף בדיוק), וכתיבה/עדכון
> **רק לשורה שלך**. בלי הבלוק הזה הכול ממשיך לעבוד — פשוט כל חיפוש יריב ייכשל.

#### 2 · פרטי OAuth ב‑Google Cloud Console

1. [console.cloud.google.com](https://console.cloud.google.com) → פרויקט חדש.
2. **APIs & Services → OAuth consent screen**: סוג **External**, שם אפליקציה,
   אימייל תמיכה ואימייל מפתח. אם האפליקציה נשארת ב‑**Testing**, להוסיף את
   כתובות הג׳ימייל שלכם תחת **Test users** — אין צורך בתהליך אימות של Google.
3. **APIs & Services → Credentials → Create credentials → OAuth client ID** →
   סוג **Web application**.
4. תחת **Authorized redirect URIs** להוסיף כתובת **אחת**, של Supabase ולא של
   האפליקציה:
   ```
   https://<ref>.supabase.co/auth/v1/callback
   ```
5. להעתיק **Client ID** ו‑**Client secret**.

#### 3 · הפעלת הספק וכתובות החזרה ב‑Supabase

1. **Authentication → Providers → Google** → Enable, להדביק Client ID + Secret
   → Save.
2. **Authentication → URL Configuration**:
   * **Site URL**: `https://<user>.github.io/gym-rpg/`
   * **Redirect URLs**: להוסיף גם `https://<user>.github.io/gym-rpg/` וגם
     `http://localhost:5173/`.

   האפליקציה מבקשת חזרה בדיוק אל `origin + pathname` של העמוד שממנו התחברתם
   (`defaultRedirect()` ב‑`sync/supabaseBackend.ts`) — בלי query ובלי hash.
   לכן כל כתובת שממנה מתחברים חייבת להופיע ברשימה, **כולל הסלאש הסופי**.
   כתובת שחסרה = חזרה ל‑`localhost` באמצע הטלפון, או שגיאת `redirect_to`.

#### 4 · חיווט הלקוח

`src/sync/config.ts`:

```ts
export const SYNC_CONFIG: SyncConfig = {
  url: 'https://<ref>.supabase.co',
  anonKey: 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…',
};
```

`npm run dev` → ⚙️ **הגדרות** → כרטיס החשבון מופיע → **התחברות עם Google**.
אחרי החזרה מהאימות: ב‑Supabase, **Table Editor → events** מתמלאת בשורות עם
`seq` עולה. `npm run verify` יזכיר מעכשיו את ה‑origin החדש כערך מותר ברשימה.

**למה מותר (ורצוי) לעשות commit ל‑anon key.** הוא מפתח *ציבורי* בהגדרתו: הוא
נארז בבנדל שכל דפדפן מוריד, והוא לא מעניק שום גישה בפני עצמו. הגבול הביטחוני
הוא RLS — `select`/`insert` מוגבלים ל‑`auth.uid() = user_id`, ואין policy ל‑
`update` או `delete` בכלל. בלי טוקן של משתמש מחובר, המפתח פותח דלת לחדר ריק.
מה ש**אסור** להיכנס לכאן לעולם הוא ה‑**service‑role key**, שעוקף RLS.

### מה מגן על היומן בצד השרת

* `primary key (user_id, id)` — דחיפה חוזרת של אירוע לא יוצרת עותק שני, ולכן
  אפשר לנסות שוב בלי חשש.
* `seq` פר‑משתמש שמוקצה ב‑trigger שנועל **שורת מונה** (`for update`). הנעילה
  מוחזקת עד ה‑commit, ולכן **סדר ההופעה לקוראים == סדר ה‑seq**. בלי זה ה‑cursor
  היה יכול לחנות אחרי שורה שעדיין לא בוצעה — ולאבד אותה לתמיד.
* RLS: `select` ו‑`insert` על שורות עצמך בלבד. **אין policy ל‑update או delete**,
  כלומר היומן append‑only גם ברמת מסד הנתונים. מחיקה מתבטאת כאירוע, לא כ‑DELETE.

### `npm run verify` וה‑allowlist

בנדל של `supabase-js` מכניס מחרוזות עם כתובות מוחלטות. `scripts/verify-dist.mjs`
לא מוותר עליהן בסיטונאות אלא מחזיק **רשימה מפורשת**, כל שורה עם הנימוק שלה:

| `https://github.com/supabase/supabase-js/blob/**.md` | טקסט בתוך `new Error(...)` של realtime — אנחנו לא פותחים ערוץ realtime בכלל |
| `http://localhost:9999` | קבוע ברירת המחדל של gotrue‑js, קוד מת: הלקוח תמיד נבנה עם URL מפורש |
| `https://github.com/orgs/supabase/discussions/<n>` | לינק ב‑`console.warn` על Node ישן |
| ה‑origin של פרויקט Supabase שהוגדר | נקרא מ‑`src/sync/config.ts` — הבקאנד של האפליקציה עצמה. כשלא מוגדר, פשוט לא קיים בבנדל |

בנוסף הסקריפט מוודא שאף אחד מהם לא באמת בשימוש רשתי (`fetch("http…"`,
`new WebSocket("…"`), ו**נכשל** על ערך ברשימה שהפסיק להתאים — היתר ששכחו ממנו הוא
חור. כל כתובת אחרת מפילה את הבנייה כמו קודם.

**עלות:** הבנדל גדל מ‑155 kB ל‑383 kB (קובץ יחיד, לא דחוס). בנייה ל‑`file://`
ממשיכה לעבוד ומציגה אפס ממשק ענן.

## אילוצים שנשמרים

* 100% אופליין — אין רשת, פונטים חיצוניים, CDN או קבצי אודיו. הצליל מסונתז
  ב‑Web Audio (ארפג׳ו 880 / 1108.7 / 1318.5 Hz).
* עברית ראשית, `dir="rtl"`, כותרות משנה באנגלית לתרגילים.
* Design tokens מקוריים: `#121824` / `#1E2638` / `#3B82F6` / `#10B981` / `#F59E0B`.
* Mobile‑first, יעדי מגע ≥ 40px, כבוד ל‑`prefers-reduced-motion`,
  ריווח תחתון לטיימר הצף (`body.timer-open`, נדלק ונכבה על ידי הטיימר עצמו).
* `text-size-adjust:100%` בשורש — אנדרואיד לא מנפח את הטיפוגרפיה של האפליקציה.
  כל `font-size` בגיליונות הוא הגודל שבאמת מוצג.
* `color-scheme:dark` בשורש (וב‑`<meta>`) — האפליקציה כהה בעצמה, ומנגנוני
  ה"מצב הכהה" של הדפדפנים לא ממחזרים לה את הצבעים.
* `strict: true` ב‑TypeScript, ללא `any` במודולי ה‑core.
* כל כתיבה עוברת דרך `DataStore` — שום מסך לא נוגע ב‑`localStorage` ישירות.
* אין `Math.random()` או `Date.now()` בלוגיקת הליבה; זמן וזרעים מוזרקים מבחוץ.

  אחת** מול כפילויות ובשני כיווני מיזוג, שלא סופרות יום אימון, ורמה שנוחתת
  בדיוק מכל נקודת פתיחה; **מחזורי איפוס** (שני מכשירים = מחזור אחד, בשני
  הכיוונים); ו**הביטול** — שוויון עמוק מול rebuild ביקורת של יומן בלי הענקות,
  אירועים אמיתיים ששורדים אותו, אידמפוטנטיות, מיזוג ענן אמיתי בשני הכיוונים,
  והדגל 🛠 שנכבה איתו. וגם קפיצת הבלוב ל‑v10.
* `dev.dom` — הכרטיס על המסך: **היעדר מוחלט** בלי השער (אין DOM, אין
  `window.gymDev`), כל כפתור שכותב אירוע מסומן אחד ומצייר מחדש, ה‑confirm של
  הניקוי (סירוב = שום דבר לא קרה), חיבור וניתוק של הקונסולה, ו‑🛠 על כרטיס
  היריב בדו־קרב.
* `mobile.dom` — **רינדור חוצה‑מכשירים**, כל מקרה מצילום מסך אמיתי של S24 מול
  פיקסל: הביטול של הגדלת הטקסט האוטומטית של אנדרואיד (שתי הכתיבות, בשורש,
  בגיליון שהבנייה מטמיעה), תקרת הגודל של שתי שורות הכותרת, והאלידה של תוויות
  הניווט; **סרגל הטיימר שלא בורח מהמסך** (‏`max-width` + `overflow`, שבירת שורת
  הכפתורים מתחת ל‑420px, ה‑`min-width:0` שבלעדיו ה‑ellipsis של התווית לא נדלק
  בכלל, והמבנה ב‑`index.html` שה‑CSS נשען עליו); ו**מחזור החיים** בשעון מזויף —
  `body.timer-open` שנדלק ונכבה, `המשך` שנעלם ב‑0:00, סגירה עצמית אחרי 20 שניות,
  ביטולה בנגיעה, ושסגירה ממתינה לא נועלת את הסט הבא; ו**ההגנה מפני מצב כהה
  כפוי** — `color-scheme:dark` ב‑`<meta>` ובשורש הגיליון, וצבע רקע כהה אחד
  שמשותף ל‑`--bg`, ל‑`theme-color` ול‑manifest.
* `loop` — **הלולאה כולה בריצה אחת**: סטים → XP ו‑⚡ → גלים → שער חוסם → אימון
  נוסף → הבוס נופל → עולם 2 → קנייה והצטיידות → הסטטיסטיקות זזות → ייצוא →
  מחיקה → ייבוא → מצב זהה. בכל שלב נבדק ש‑`rebuildFromEvents(log)` שווה למצב החי.
* `plan` — התוכנית ללא UI: `resolveProgram(null) === PROGRAM`, דריסת מספרים,
  תרגילים מותאמים ופיצול ה‑XP שלהם (כולל הענקה רטרואקטיבית), קיפול
  last‑writer‑wins ב‑`(ts, id)` כולל שוויון חותמות, `data_cleared`, ולידציה,
  מיגרציה ל‑schema 3 וסובלנות לבלוב v2 ישן.
* `planEditor.dom` — העורך: רינדור, הוספה/הסרה/סידור מחדש, טופס התרגיל החדש,
  **אירוע `plan_updated` אחד בדיוק** לכל שמירה, איפוס, והתוכנית השמורה שמגיעה
  בפועל למסך האימון (כולל XP לחלק הגוף שנבחר).
* `sync.engine` — מנוע הסנכרון מול backend בזיכרון (`Map` + מונה `seq`), עם
  שעון וטיימרים מזויפים ו**אפס רשת**: outbox ששורד ריסטארט, קיבוץ הקשות
  (4 → 1, האחרון מנצח), מיזוג שמצייר מחדש ושומר על הטאב הנוכחי, קידום cursor
  ועימוד, התעלמות מאירועים מוכרים, שני מכשירים שמתכנסים, לוח ה‑backoff,
  התאוששות מ‑offline, `linkAccount` שמעלה את כל היומן, ו‑`stop()` שמוחק פנקס
  ולא נתונים.
* `account.dom` — כרטיס החשבון: אין כרטיס כשלא מוגדר, הנוסח בכל מצב (מחובר /
  מנותק / פג תוקף / אופליין), אישור לפני התנתקות, האזהרה על מחיקה מכל
  המכשירים, וייבוא **מצטבר** כשמחוברים מול הרסני כשמנותקים.
* `merge` — התכנסות האיחוד: שני כיוונים, סדר אקראי, כפילויות סמנטיות שמשלמות
  פעם אחת, `data_cleared` בתוך איחוד, **שני מכשירים ששדרגו את אותו פריט
  אופליין** (אותה דרגה = חיוב אחד; דרגות שונות = הגבוהה מנצחת וכל צעד משולם
  פעם אחת), ו**הנועל** שמונע ייבוא מחדש של הנתונים הישנים אחרי מחיקה + מיזוג.
* `e2e.sync` — **יום שלם, שני מכשירים, חשבון אחד**: אימון במרתף בלי קליטה →
  ריסטארט של הטאב באמצע (ה‑outbox וה‑cursor שורדים, ולא נדחף שום דבר פעמיים)
  → העלאה ומשיכה בסדר הפוך → קרבות שמוציאים אנרגיה בזמן שהמכשיר השני מתאמן →
  עריכת תוכנית פה ואחר כך שם (המאוחרת מנצחת בשני הצדדים) → ייבוא גיבוי ישן
  מצטבר → 🗑 מחיקה שמתפשטת לכל החשבון. בכל נקודת שקט נבדקים שלושה דברים:
  שני המכשירים מציגים אותו מצב, כל מכשיר שווה ל‑`rebuildFromEvents` של היומן
  שלו, וחוקי המשחק מתקיימים (אנרגיה ≥ 0 ואף מפתח הענקה לא שולם פעמיים).
  תרחיש נוסף מריץ את אותו מסלול על **שדרוג ציוד**: שני המכשירים אופליין קונים
  `+1` לאותו פריט, ואחרי הסנכרון החשבון עומד על `+1`, חויב פעם אחת, ושתי
  הדמויות מציגות אותה התקפה.
* `app.dom` — השלד והניווט הדו‑שכבתי: תמיד **שלושה** טאבים ראשיים בכל מסך,
  גזירת המרכז מכל view id (כולל `PL` ומפתח יום זר), תת‑הטאבים של כל מרכז,
  זיכרון תת‑הטאב לכל מרכז, פיצול מרכז ההגדרות (כרטיסים ופעולות ב‑`ST`, יומן
  והיסטוריה ב‑`H`), התקנה ישנה שנשארה על `'H'`, ושורת תת‑טאבים שנגללת רק מעל
  ארבעה ימים.
* `history.dom` — מסך ההיסטוריה: היומן בתוך חלונית הגלילה שלו (והכותרת מחוצה

* `*.dom` — בדיקות jsdom לשאר המסכים: טיימר, זירה (כולל עצירת הקרב במעבר
  תת‑טאב **ובמעבר מרכז**), קרב בוס, מגירות החנות, מדף הגביעים ותקינות ה‑SVG של
  כל פריט ציוד בארבעה גדלי דמות.
* `enemies` — הרוסטר המורחב: 5–6 רגילים + מיני‑בוס לכל עולם, מזהים ייחודיים,

  לכל גל, ו**יומן שנכתב בגרסת שלושת האויבים** שעושה replay למצב זהה.
* `arena.dom` — הזירה החיה עם שעון מזויף: המחלקות `.anim-attack` / `.anim-hit` /
  `.anim-hurt` / `.anim-die` / `.anim-super` / `.anim-victory` נדלקות באירוע
  הנכון **ונכבות אחריו** (שום ספרייט לא נשאר באמצע פוזה), מסלול
  `prefers-reduced-motion` שמשאיר את ה‑DOM תמים (רעידת המסך נחסמת, התוויות
  נשארות), ורצועת העולמות בכל מצביה — נעול, נוכחי‑חסום, נוכחי‑פתוח, הושלם,
